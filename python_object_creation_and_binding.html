파이썬 객체 생성과 바인딩의 기계적 실체

단 4줄의 코드 뒤에서 일어나는 CPython 메모리 공간 분리, Bound Method(PyMethodObject)의 동적 생성(m1 is m2 → False), 그리고 남몰래 소멸하는 7가지 임시 객체들

#Python #CPython #메모리모델 #BoundMethod #디스크립터 #시스템프로그래밍
🧠 CPython 엔지니어의 핵심 멘탈 모델 5원칙

1. 변수는 상자(Bucket)가 아니라 객체에 붙는 포인터 이름표(Label)다.
2. 데이터(인스턴스 상태)와 로직(클래스 함수)은 메모리상에서 완벽히 분리되어 있다.
3. my_dog.bark 접근 시 디스크립터 프로토콜에 의해 힙에 동적으로 생성되는 얇은 래퍼 객체인 Bound Method(PyMethodObject)가 찰나의 순간 탄생한다.
4. 바인딩(Binding)은 언어적 환상이 아니다. C 레벨에서 self에 인스턴스 주소를 제1인자로 주입하는 정교한 기계적 래퍼 메커니즘이다.
5. CPython 인터프리터는 한 줄의 메서드 호출을 처리하기 위해 7가지 은밀한 임시 객체를 힙과 스택에 생성했다가 즉시 증발시킨다.

프롤로그: 직관을 뒤엎는 4줄의 파이썬 코드

파이썬을 배울 때 누구나 처음 마주하는 전형적인 객체 지향 코드입니다.

Python 
class Dog:
    def bark(self):
        print("woof")

my_dog = Dog()

print(my_dog.bark)
print(my_dog.bark())

터미널에 이 스크립트를 던지면 다음과 같은 결과가 출력됩니다.

Output 
<bound method Dog.bark of <__main__.Dog object at 0x7f9a1024b310>>
woof
None

단 4줄의 지극히 평범한 코드이지만, 시스템 프로그래머의 시선으로 런타임 메모리를 들여다보면 무수히 많은 질문이 쏟아져 나옵니다:

  • 질문 1: my_dog.bark와 my_dog.bark()의 본질적 차이는 무엇인가? 왜 괄호가 없을 때는 호출되지 않고 <bound method>라는 기묘한 문자열이 출력되는가?
  • 질문 2: my_dog 인스턴스를 생성했을 때, 그 인스턴스 메모리 공간 안에 bark 함수의 바이트코드가 복사되어 들어가는가?
  • 질문 3: m1 = my_dog.bark와 m2 = my_dog.bark를 차례로 꺼내어 m1 is m2를 검사하면 왜 False가 나오는가? 메서드는 이미 인스턴스에 붙어있는 것이 아니었단 말인가?
  • 질문 4: def bark(self):에서 self는 도대체 언제, 누구에 의해, 어떤 주소값으로 전달되는가?

이 질문들에 시스템 레벨의 명쾌한 답을 내놓지 못한다면, 우리는 파이썬을 다루는 것이 아니라 파이썬이 보여주는 표면적 환상에 속고 있는 것입니다. 이제 CPython C 소스코드와 메모리 힙 레이아웃을 통해 이 4줄의 기계적 실체를 한 겹씩 벗겨보겠습니다.

제0막: 실행 전야 — 소스 코드에서 불변 PyCodeObject로

CPython 인터프리터는 텍스트 소스 코드를 그 자리에서 곧바로 기계어처럼 실행하지 않습니다. 파이썬 스크립트가 실행되는 순간, 인터프리터는 소스 코드를 파싱하여 AST(추상 구문 트리)를 구축하고 이를 불변(Immutable)의 Code Object(PyCodeObject)들로 컴파일합니다.

CPython 정적 컴파일 파이프라인 불변 구조체 계층
모듈 레벨
<module> PyCodeObject
• co_consts: (<code Dog>, None)
• co_names: ('Dog', 'my_dog', 'print')
• 전역 실행용 바이트코드 컨테이너
함수 레벨
bark PyCodeObject
• co_name: 'bark'
• co_varnames: ('self',)
• co_consts: (None, 'woof')
• co_code: LOAD_GLOBAL, LOAD_CONST, CALL...

여기서 가장 핵심적인 사실은 Code Object는 단지 '실행 명세서'일 뿐, 파이썬의 '함수(Function)'가 아니라는 점입니다. Code Object는 환경(Scope), 전역 변수 사전(__globals__), 기본값(Default values)에 대해 일절 알지 못합니다. 오직 순수한 바이트코드 열과 상수 풀, 변수 이름 튜플만을 담고 있는 불변 C 구조체입니다.

CPython 내부 C 구조체: PyCodeObject Include/cpython/code.h
C Struct 
struct PyCodeObject {
    PyObject_HEAD
    int co_flags;               /* 최적화 및 제너레이터 플래그 */
    int co_argcount;            /* 위치 인자 개수 (bark의 경우 1: self) */
    int co_posonlyargcount;
    int co_kwonlyargcount;
    int co_stacksize;           /* 평가 스택 최대 깊이 */
    PyObject *co_code;          /* 순수 바이트코드 바이트 열 (PyBytesObject) */
    PyObject *co_consts;        /* 상수 튜플: ("woof", None 등) */
    PyObject *co_names;         /* 전역/내장 이름 튜플: ("print",) */
    PyObject *co_varnames;      /* 지역 변수 이름 튜플: ("self",) */
    PyObject *co_filename;      /* 소스 파일 경로 */
    PyObject *co_name;          /* 함수/모듈 이름 ("bark") */
    /* ... CPython 3.12+ 내부 최적화 슬롯들 ... */
};

제1막: class Dog의 실행과 공간 분리 — 로직의 영구 거처

이제 인터프리터가 첫 번째 구문인 class Dog:를 실행합니다. 초보자들은 흔히 "클래스를 선언하면 틀(붕어빵 틀)이 선언되는 것이고 객체는 나중에 만들어진다"고 배웁니다. 하지만 CPython에서 클래스 선언문은 그 자체로 실행 가능한 코드이며, 실행이 끝나는 순간 힙에 클래스 객체(PyTypeObject)라는 거대한 힙 노드가 생성됩니다.

⚙️ 클래스 정의 시 CPython 내부 동작 순서

1. 네임스페이스 딕셔너리 생성 (임시 객체 ①): 클래스 본문 내부에서 선언될 속성들을 담을 임시 dict를 만듭니다.
2. 클래스 바디 바이트코드 실행: 내부의 def bark(self):를 실행합니다.
3. PyFunctionObject 힙 할당: bark의 Code Object와 현재 모듈의 globals()를 엮어 새로운 함수 객체를 만듭니다.
4. type 메타클래스 호출: type.__new__(type, "Dog", (), namespace)를 실행하여 최종적으로 Dog 클래스 객체를 완성합니다.

이 과정이 끝난 후 메모리의 형상을 살펴보면, 데이터와 로직의 엄격한 분리가 이미 시작되었음을 확인할 수 있습니다.

클래스 생성 완료 시점의 힙 메모리 구조 공간적 분리 완성

이 다이어그램이 증명하는 결정적 통찰은 다음과 같습니다:

"함수 로직(bark)은 오직 Dog 클래스의 딕셔너리에만 등록되어 존재한다."
파이썬은 클래스를 선언할 때 함수 코드를 어딘가에 복제해두지 않습니다. 단 하나의 PyFunctionObject가 힙에 만들어지고, 클래스 객체가 자신의 속성 사전(tp_dict)에 그 포인터를 쥐고 있을 뿐입니다.
CPython 내부 C 구조체: PyFunctionObject Include/cpython/funcobject.h
C Struct 
typedef struct {
    PyObject_HEAD
    PyObject *func_globals;     /* 함수가 정의된 모듈의 전역 사전 */
    PyObject *func_builtins;    /* __builtins__ 사전 포인터 */
    PyObject *func_name;        /* __name__ 문자열 ("bark") */
    PyObject *func_qualname;    /* __qualname__ 문자열 ("Dog.bark") */
    PyObject *func_code;        /* 실제 실행 바이트코드가 담긴 PyCodeObject */
    PyObject *func_defaults;    /* 기본 인자 튜플 (없으면 NULL) */
    PyObject *func_kwdefaults;  /* 키워드 기본 인자 사전 */
    PyObject *func_closure;     /* 클로저 자유 변수 튜플 */
    PyObject *func_doc;         /* __doc__ 독스트링 */
    PyObject *func_dict;        /* 임의 속성 부착용 함수 사전 */
    vectorcallfunc vectorcall;  /* 고속 호출 C 함수 포인터 */
} PyFunctionObject;

제2막: my_dog = Dog() — 인스턴스 할당(tp_new)과 초기화(tp_init)

이제 두 번째 구문인 my_dog = Dog()가 실행됩니다. 이 한 줄이 실행될 때 CPython 내부에서는 C 함수 포인터 체인이 정밀한 톱니바퀴처럼 맞물려 돌아갑니다:

  1. Dog는 메타클래스 type의 인스턴스이므로, Dog() 호출은 C 레벨에서 type_call()을 트리거합니다.
  2. type_call()은 먼저 Dog->tp_new를 호출합니다. 우리는 __new__를 오버라이딩하지 않았으므로 기본 object_new()가 호출됩니다.
  3. _PyObject_New()가 시스템 힙(PyObject Arena)에서 메모리 청크를 쪼개어 할당하고, 헤더의 ob_refcnt = 1, ob_type = &Dog_Type으로 설정합니다.
  4. 이어서 Dog->tp_init을 호출합니다. 정의된 __init__이 없으므로 빈 껍데기 인스턴스가 그대로 반환됩니다.
  5. 전역 스코프에 my_dog라는 이름표(Label)가 생성되어 방금 힙에 할당된 인스턴스 주소를 가리킵니다.
⚠️ 충격적인 진실: 인스턴스에는 bark가 없다!

생성 직후 파이썬 REPL에서 my_dog.__dict__를 확인해 보면 결과는 놀랍게도 완전히 비어 있는 빈 사전({})입니다.

Python REPL 
>>> my_dog = Dog()
>>> my_dog.__dict__
{}
>>> 'bark' in my_dog.__dict__
False

인스턴스 my_dog는 bark라는 함수 코드나 바이트코드를 단 1비트도 소유하고 있지 않습니다. 인스턴스가 가진 것은 오직:

  • 자신의 참조 횟수 (ob_refcnt)
  • 자신이 어떤 클래스 소속인지를 알려주는 타입 포인터 (ob_type → Dog)
  • 자신만의 고유한 인스턴스 속성을 담을 빈 딕셔너리 포인터 (__dict__)

이 3가지가 전부입니다. 즉, 인스턴스는 오직 상태(State)만을 담기 위한 순수한 힙 노드일 뿐, 로직(Logic)은 철저히 클래스에만 존재합니다.

제3막: print(my_dog.bark) — 디스크립터 프로토콜과 Bound Method의 탄생

이제 세 번째 줄이자, 이 글의 가장 극적인 하이라이트인 print(my_dog.bark)가 실행됩니다. 여기서 bark 뒤에는 괄호 ()가 없습니다. 즉, 함수를 호출하는 것이 아니라 속성을 조회(Attribute Lookup)하고 있습니다.

속성 탐색 알고리즘 (PyObject_GenericGetAttr)의 5단계

파이썬 인터프리터가 obj.name을 만났을 때 실행하는 CPython 내부 함수 PyObject_GenericGetAttr의 탐색 흐름은 매우 엄격합니다:

  1. 클래스 MRO 탐색: Dog 클래스 및 상위 클래스의 tp_dict에서 "bark"를 찾습니다. → PyFunctionObject 발견!
  2. 데이터 디스크립터 검사: 발견된 객체에 __set__ 슬롯이 있는지 봅니다. 일반 함수는 __set__이 없으므로 데이터 디스크립터가 아닙니다.
  3. 인스턴스 사전 검사: my_dog.__dict__에 "bark"가 있는지 찾습니다. → 없음! ({})
  4. 비-데이터 디스크립터 검사: 클래스에서 찾은 PyFunctionObject의 타입(PyFunction_Type)을 확인합니다. 함수 타입은 tp_descr_get (즉, __get__ 메서드)을 구현하고 있습니다!
  5. 디스크립터 프로토콜 발동: CPython은 함수 객체를 그냥 반환하지 않고, func->tp_descr_get(func, my_dog, Dog)를 실행합니다.

이 __get__ 호출의 결과로 힙 공간에 완전히 새로운 제3의 객체가 벼락처럼 할당됩니다. 그것이 바로 바운드 메서드(Bound Method, PyMethodObject)입니다!

Python 내부 동작 의사코드 
# my_dog.bark 접근 시 내부적으로 실행되는 디스크립터 프로토콜
bound_method = Dog.__dict__['bark'].__get__(my_dog, Dog)

# CPython C 레벨 함수 매핑:
# PyMethod_New(PyObject *func, PyObject *self) -> PyMethodObject 생성!
CPython 내부 C 구조체: PyMethodObject (Bound Method) Include/cpython/classobject.h
C Struct 
typedef struct {
    PyObject_HEAD
    PyObject *im_func;          /* 원본 함수 객체 (Dog.bark) 포인터 */
    PyObject *im_self;          /* 바인딩된 인스턴스 (my_dog) 메모리 주소 포인터 */
    vectorcallfunc vectorcall;  /* 고속 호출 벡터 콜 함수 포인터 */
} PyMethodObject;
Bound Method의 힙 메모리 결합 구조 얇은 연결 래퍼

실체 증명: 왜 m1 is m2는 항상 False인가?

메서드가 인스턴스에 고정된 정적 엔티티가 아니라는 가장 확실한 증거가 바로 is 연산자입니다.

Python 실험 검증 
my_dog = Dog()

m1 = my_dog.bark
m2 = my_dog.bark

print(m1 is m2)          # False!
print(id(m1) == id(m2))  # False!
print(hex(id(m1)), hex(id(m2))) # 서로 다른 힙 메모리 주소!

print(m1.__func__ is m2.__func__) # True (둘 다 Dog.bark 함수를 가리킴)
print(m1.__self__ is m2.__self__) # True (둘 다 my_dog 인스턴스를 가리킴)

우리가 my_dog.bark라고 점(.)을 찍어 속성을 조회할 때마다, CPython은 힙 메모리에 PyMethodObject라는 새로운 래퍼 객체를 동적으로 찍어냅니다. 따라서 m1과 m2는 속을 채운 포인터(__func__와 __self__)는 같지만, 래퍼 자체는 힙의 서로 다른 주소에 생성된 독립 객체이므로 is 비교 시 반드시 False가 반환됩니다.

💡 Dog.bark vs my_dog.bark 본질 비교
비교 항목 Dog.bark (클래스 접근) my_dog.bark (인스턴스 접근)
객체 타입 <class 'function'> <class 'method'> (Bound Method)
C 구조체 PyFunctionObject PyMethodObject
바인딩 상태 비어 있음 (Unbound) im_self가 my_dog를 가리킴
호출 방식 Dog.bark(my_dog) (수동 주입) my_dog.bark() (자동 주입)
생명 주기 프로그램 종료 시까지 영구 생존 점 접근 시 힙 할당 → 호출 후 즉시 소멸 가능

제4막: print(my_dog.bark()) — 호출 실행과 self 역방향 주입

이제 네 번째 구문인 print(my_dog.bark())입니다. 파이썬 인터프리터는 바깥의 print()를 호출하기 전에 내부 인자인 my_dog.bark()를 먼저 평가합니다.

호출 괄호 ()의 기계적 실체

앞서 생성된 PyMethodObject에 호출 괄호 ()가 붙으면, CPython은 바운드 메서드의 호출 프로토콜인 method_vectorcall을 구동합니다:

C (CPython methodobject.c) 의사코드 
static PyObject *
method_vectorcall(PyObject *method, PyObject *const *args, size_t nargsf, PyObject *kwnames)
{
    PyMethodObject *m = (PyMethodObject *)method;
    PyObject *func = m->im_func;   /* 원본 Dog.bark 함수 */
    PyObject *self = m->im_self;   /* 바인딩된 my_dog 인스턴스 */

    /* CPython 내부 스택의 인자 배열 0번째 자리에 self(my_dog)를 끼워 넣음! */
    /* 그리고 func(self, *args) 형태로 원본 함수를 호출! */
    return PyVectorcall_Call(func, self, args, nargsf, kwnames);
}

이 C 코드가 말해주는 진실은 너무나 명확합니다:

my_dog.bark()는 단 한 치의 오차도 없이 Dog.bark(my_dog)와 기계적으로 동일하다.
바인딩이란 대단한 마법이 아닙니다. C 레벨에서 PyMethodObject가 쥐고 있던 im_self 포인터를 함수의 첫 번째 매개변수 슬롯에 슬그머니 밀어 넣어 호출해 주는 호출 래퍼(Call Wrapper) 메커니즘일 뿐입니다.

self의 참조 방향: 인스턴스가 함수를 가리키는 것이 아니다

많은 개발자가 self라는 키워드를 "인스턴스가 자기 안의 함수를 참조하는 것"으로 잘못 기억합니다. 하지만 실제 메모리 화살표는 완벽한 역방향입니다:

🎯 역방향 화살표: 함수 실행 프레임 → 인스턴스

bark 함수가 호출되는 순간, 실행 스택에 프레임(_PyInterpreterFrame)이 생성됩니다.
이 프레임의 지역 변수 배열 fastlocals[0]에 "self"라는 이름표가 붙고, 그 이름표가 힙에 홀로 떠 있는 my_dog 인스턴스를 가리킵니다.
따라서 함수 내부에서 self is my_dog는 100% True입니다. 새로운 개체가 복제된 것이 아니라 기존 my_dog의 메모리 주소가 그대로 전달된 것입니다.

실행 후의 소멸 과정: 프레임과 바운드 메서드의 죽음

  1. print("woof")가 실행되어 터미널에 woof가 출력됩니다.
  2. bark 함수에는 명시적 return이 없습니다. CPython은 함수 끝에 도달하면 암묵적으로 싱글턴 객체 Py_None의 주소를 반환합니다.
  3. 함수가 종료되면서 방금 생성되었던 bark의 실행 프레임이 스택에서 팝(Pop)되어 해제됩니다.
  4. 인라인으로 임시 생성되었던 PyMethodObject 역시 호출이 끝나는 순간 참조 횟수(ob_refcnt)가 0이 되어 힙 메모리에서 즉시 deallocate됩니다.
  5. 최종적으로 반환된 None이 바깥쪽 print()에 전달되어 터미널에 None이 찍힙니다.

제5막: CPython이 무대 뒤에서 만들고 소멸시키는 7가지 은밀한 객체

사용자는 단 4줄의 코드를 작성했을 뿐이지만, CPython VM은 보이지 않는 무대 뒤에서 수많은 임시 객체들을 만들어 분주히 조작하고 파괴했습니다. 이를 추적할 수 있어야 CPython 시스템 아키텍처를 진정으로 장악했다고 할 수 있습니다.

제6막: 기계의 눈으로 본 바인딩 — "어차피 포인터인데 왜 바인딩이란 개념을 둘까?"

C/C++이나 시스템 프로그래밍에 익숙한 엔지니어는 종종 다음과 같은 날카로운 의문을 제기합니다:

"기계 입장에서야 인스턴스에 바인딩이 되든 말든, 결국 CPU가 실행하는 건 특정 함수 코드 주소에 인스턴스 메모리 주소(포인터)를 레지스터로 넘겨서 CALL하는 것 아닌가? 바인딩이라는 건 사람이 구분하려고 지어낸 허구의 개념 아닌가?"

이 질문에 대한 가장 정밀한 시스템 엔지니어의 대답은 다음과 같습니다:

💡 통찰: 바인딩은 개념이지만, 그에 대응하는 '실제 런타임 객체'가 존재한다

C 언어에서 dog->bark(dog);를 호출할 때는 컴파일 시점에 이미 호출 규약과 인자 레지스터 배치가 기계어로 고정됩니다. 중간에 '바운드 메서드'라는 객체가 끼어들 여지가 없습니다.

하지만 파이썬은 메서드가 일급 객체(First-Class Citizen)인 동적 객체지향 언어입니다. 파이썬에서는 메서드를 변수에 담거나(f = my_dog.bark), 이벤트 콜백으로 전달하거나(button.on_click = my_dog.bark), 다른 스레드로 보낼 수 있어야 합니다.

이때 함수 코드 포인터와 인스턴스 주소 포인터를 하나로 묶어 들고 다닐 수 있는 '독립적인 힙 객체(PyMethodObject)'가 반드시 존재해야만 합니다. 따라서 바인딩은 추상적 관념에 그치지 않고, CPython 런타임이 실제로 힙에 생성하는 물리적 구조체입니다.

이를 계층별로 정리하면 완벽한 퍼즐이 완성됩니다:

계층 (Level) 처리 주체 메서드 호출 시 일어나는 일
1. 인간 / 언어 레벨 파이썬 프로그래머 my_dog.bark()를 실행하여 개가 짖게 만든다.
2. 객체 모델 레벨 디스크립터 프로토콜 점(.) 접근 시 __get__을 통해 함수와 인스턴스를 묶은 바운드 메서드 객체를 합성한다.
3. CPython 가상머신 C 구조체 & 바이트코드 PyMethodObject의 im_self를 제1인자로 채워 func_code의 실행 프레임을 띄운다. (3.11+에서는 LOAD_METHOD 최적화로 인라인 바이패스 가능)
4. CPU / 하드웨어 CPU 레지스터 & 스택 인스턴스 힙 주소를 RDI(x86-64 제1인자 레지스터)에 싣고 함수 기계어 주소로 CALL 명령을 내린다.

에필로그 및 요약 치트시트

파이썬은 표면상 지극히 우아하고 단순한 문법을 제공하지만, 그 아래에는 C 언어로 정교하게 깎아 만든 강력한 동적 객체 모델과 디스크립터 프로토콜이 작동하고 있습니다. 앞으로 여러분이 파이썬 코드를 작성하거나 디버깅할 때 다음 5가지 시각적 이미지를 항상 떠올리십시오:

파이썬 코드 메모리 힙에서 실제로 일어나는 일 핵심 주의 사항
class Dog: Dog 클래스 객체와 bark 함수 객체가 힙에 독립 할당됨 함수는 오직 클래스 사전에만 등록됨
my_dog = Dog() __dict__가 비어있는 인스턴스 힙 메모리 할당 (ob_type → Dog) 인스턴스 안에 함수 코드가 복제되지 않음
my_dog.bark 디스크립터(__get__)가 호출되어 새로운 PyMethodObject 래퍼가 힙에 생성됨 m1 is m2 → False (임시 객체)
my_dog.bark() PyMethodObject가 self에 my_dog 주소를 주입하여 Dog.bark(my_dog) 실행 호출 완료 시 실행 프레임과 임시 메서드 객체 소멸
return None 명시적 반환값이 없으면 CPython 싱글턴 Py_None 주소 반환 bark() is None → True
