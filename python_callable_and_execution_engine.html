# 프롤로그: 파이썬의 ()는 문법이 아닌 객체 호출 프로토콜(Call Protocol)의 발동이다

우리가 파이썬 코드에서 가장 흔하게 마주하는 기호 중 하나는 단연 소괄호 ()입니다. 개발자는 일상적으로 add(1, 2)를 보며 "add라는 이름의 함수를 인자 1, 2와 함께 실행한다"라고 직관적으로 받아들입니다.

그러나 CPython 가상 머신의 관점에서 소괄호 ()는 단순한 구문 규칙(Syntax)이 아닙니다. 인터프리터에게 소괄호는 다음의 엄격한 객체 호출 프로토콜(Call Protocol)을 가동하라는 하드웨어 수준의 지령입니다:

"스택 위에 놓인 obj는 호출 가능한 객체(Callable)인가? 그렇다면 그 객체의 C 구조체 슬롯에 정의된 호출 함수 포인터를 찾아 인자들을 넘겨 평가하라."

이 놀라운 사실 때문에 파이썬에서는 이름 뒤에 ()를 붙여 실행할 수 있는 대상이 결코 함수에 국한되지 않습니다.

python 
# 1. 고전적인 함수 객체
def normal_func(a, b):
    return a + b

# 2. 클래스 객체 자체 (인스턴스 생성자 호출)
class Adder:
    def __init__(self, base):
        self.base = base
    def __call__(self, a, b):
        return self.base + a + b

# 3. __call__이 정의된 일반 인스턴스 객체
adder_instance = Adder(base=100)

# 모두 완전히 동일한 소괄호 () 연산자로 발동된다!
print(normal_func(1, 2))      # 3
print(Adder(base=10))         # <Adder object at 0x...>
print(adder_instance(1, 2))   # 103

위 코드의 세 대상(normal_func, Adder, adder_instance)은 메모리 상에서 서로 완전히 다른 C 구조체입니다. 그럼에도 모두 (1, 2)라는 단일한 문법으로 호출될 수 있습니다.

내장 함수 callable(x)가 진정으로 검사하는 것도 "이것이 함수인가?"가 아니라 "이 객체의 C 타입 구조체에 호출 프로토콜 진입점(tp_call 또는 vectorcall)이 열려 있는가?"입니다.

💡 핵심 멘탈 모델: 괄호 ()의 추상 연산화

파이썬에서 obj를 단독으로 쓰면 객체의 레퍼런스를 가져오는 메모리 로드 연산이지만, obj(1, 2)는 객체의 Py_TYPE(obj)를 역참조하여 그 객체의 행동표(타입 슬롯)에 등록된 실행 함수를 찾아가는 동적 디스패치(Dynamic Dispatch) 연산입니다.

# 1장: obj(1, 2)를 만난 인터프리터의 첫 걸음 — CALL 바이트코드와 스택 상태

파이썬 소스코드가 인터프리터에서 파싱되면 추상 구문 트리(AST)를 거쳐 컴파일러에 의해 바이트코드로 변환됩니다. obj(1, 2)를 dis 모듈로 역어셈블해보면 현대 파이썬(3.11+)의 진보된 내부 아키텍처가 적나라하게 드러납니다.

python bytecode 
import dis

def test():
    return obj(1, 2)

dis.dis(test)

#     32 RETURN_VALUE

Evaluation Stack과 PUSH_NULL 혁신

과거 Python 3.10 이전에는 LOAD_GLOBAL obj 이후 인자를 쌓고 CALL_FUNCTION 2를 호출했습니다. 하지만 Python 3.11부터는 PUSH_NULL 메커니즘이 도입되었습니다.

왜 NULL을 스택에 밀어 넣을까요? 이것이 바로 일반 함수 호출과 메서드 호출(instance.method(arg))의 스택 모양을 완벽하게 통일하기 위한 CPython의 기발한 승부수입니다.

구분 스택 슬롯 0 스택 슬롯 1 인자 슬롯 (2, 3) CALL 바이트코드 처리
일반 함수 호출
func(1, 2)		 NULL callable (func) arg1(1), arg2(2) 스택 0이 NULL이므로 슬롯 1의 함수를 인자 2개로 직행 호출
메서드 호출
obj.method(1, 2)		 method self (obj) arg1(1), arg2(2) 스택 0이 NULL이 아니므로 슬롯 1(self)을 첫 번째 인자로 결합하여 총 3개 인자로 실행

덕분에 인터프리터는 "이것이 바인드된 메서드인가, 일반 함수인가?"를 확인하기 위해 매번 힙에 임시 PyMethodObject(바운드 메서드 래퍼)를 동적 할당할 필요가 없어졌습니다. 단일 CALL 명령어가 스택 상태만을 보고 제로-할당(Zero-allocation)으로 양쪽을 초고속 분기 처리합니다.

C source CPython ceval.c 내부의 TARGET(CALL) 디스패치 루프
▼
c (cpython/Python/ceval.c) 
/* CPython 3.12 Python/bytecodes.c & ceval.c 발췌 */
TARGET(CALL) {
    PyObject **args = &stack_pointer[-oparg];
    PyObject *callable = stack_pointer[-1 - oparg];
    PyObject *self_or_null = stack_pointer[-2 - oparg];

    /* self_or_null이 NULL이 아니면(메서드 호출), self를 인자 목록 앞자리로 간주 */
    PyObject *res;
    if (self_or_null != NULL) {
        args--;
        oparg++;
    }
    
    /* 최적화된 vectorcall 또는 일반 호출 엔진으로 진입 */
    res = PyObject_Vectorcall(callable, args, oparg, NULL);
    ...
    STACK_SHRINK(oparg + 2);
    PUSH(res);
    DISPATCH();
}

# 2장: CPython 호출 엔진의 두 갈래 길 — tp_call vs 현대 vectorcall 프로토콜

바이트코드 실행기가 CALL을 수행하면 CPython의 호출 서브시스템으로 진입합니다. 여기서 CPython의 역사를 관통하는 가장 위대한 성능 혁신인 고전적 tp_call과 현대적 vectorcall(PEP 590)의 분기가 나타납니다.

고전적 tp_call의 비극: 불필요한 튜플 팩/언팩

과거 Python C API의 표준 호출 방식은 PyObject_Call(callable, args, kwargs)였습니다. 이 함수의 시그니처는 다음과 같은 C 함수 포인터(ternaryfunc)를 전제로 했습니다.

c 
/* PyTypeObject에 정의된 전통적인 호출 슬롯 */
typedef PyObject *(*ternaryfunc)(PyObject *self, PyObject *args, PyObject *kwargs);

이 구조에는 치명적인 병목이 도사리고 있었습니다:

  • func(1, 2)를 호출하기 위해 스택에 있는 숫자 1과 2를 꺼내 새로운 CPython 튜플 객체 (1, 2)를 힙 메모리에 PyTuple_New(2)로 무조건 할당해야 했습니다.
  • 키워드 인자가 있다면 빈 딕셔너리 객체({}) 역시 할당되었습니다.
  • 함수 바디 내부로 진입하면, 방금 만든 튜플에서 인자들을 다시 하나씩 풀어서(Unpack) 로컬 변수 슬롯에 대입했습니다.
  • 함수 호출이 끝나면 방금 쓰고 버려진 임시 튜플 객체를 메모리에서 해제해야 했습니다.

초당 수억 번씩 실행되는 파이썬 함수 호출에서 매번 힙 할당과 해제가 일어난다는 것은 엄청난 CPU 사이클 낭비이자 캐시 미스의 주범이었습니다.

구원투수: PEP 590 vectorcall 프로토콜

CPython 3.8에서 실험 도입되어 3.9+부터 코어 전체를 지배하게 된 vectorcall은 이 튜플 포장 비용을 완전히 0으로 만들었습니다.

C struct vectorcallfunc 함수 포인터 정의 (PEP 590)
▼
c 
typedef PyObject *(*vectorcallfunc)(
    PyObject *callable,               /* 호출 대상 객체 */
    PyObject *const *args,             /* 스택 상의 인자 C 포인터 연속 배열 (슬라이스) */
    size_t nargsf,                     /* 인자 개수 + 플래그 비트마스크 */
    PyObject *kwnames                  /* 키워드 인자 이름들이 담긴 튜플 (없으면 NULL) */
);

vectorcall의 핵심 비결은 세 가지입니다:

  1. 튜플 제로-할당: 스택에 이미 차례대로 쌓여 있는 포인터 메모리 주소(&stack[0])를 C 언어의 연속 포인터 배열 PyObject *const *args로 함수에 그대로 넘겨줍니다. 튜플을 새로 만들지 않습니다!
  2. 비트마스크 트릭 (nargsf): 인자의 개수 nargs에 최상위 비트 PY_VECTORCALL_ARGUMENTS_OFFSET 플래그를 결합합니다. 이를 통해 호출자가 전달한 args 배열 바로 앞자리(args[-1])를 임시로 덮어써도 안전한지를 수 피코초 단위 비트 연산으로 판별합니다.
  3. self 프리펜딩(Prepending) 제로-카피: 메서드 호출 시 self를 인자 맨 앞에 끼워 넣어야 할 때, 메모리 복사나 재할당 없이 스택 상의 args[-1](앞서 1장에서 본 PUSH_NULL 자리!)에 self를 꽂아 넣고 args--하여 포인터만 한 칸 앞으로 이동시킵니다.
⚡ 시스템 엔지니어의 통찰: PUSH_NULL과 vectorcall의 환상적 결합

1장에서 보았던 PUSH_NULL 바이트코드가 스택에 슬롯 하나를 미리 비워두는 진짜 이유가 바로 여기에 있습니다. 만약 이것이 메서드 호출로 전환될 경우, vectorcall 엔진이 인자들을 복사해 옮길 필요 없이 빈 슬롯에 self를 즉시 채워 넣어 완벽한 0-비용(Zero-overhead) 인자 리프레시를 달성하기 위함입니다.

항목 고전 tp_call 현대 vectorcall
인자 전달 방식 PyTupleObject (힙 할당) + PyDictObject PyObject *const *args (C 포인터 연속 슬라이스)
메모리 할당(malloc) 호출마다 최소 1~2회 힙 할당 발생 0회 (평가 스택 연속 메모리 재사용)
self 바인딩 새 튜플에 self를 포함하여 다시 복사 args[-1] 슬롯에 self 배치 후 포인터만 조정
CPython 적용 대상 레거시 C 확장 모듈 및 하위 호환 슬롯 모든 파이썬 함수, 내장 메서드, 클래스 생성자

# 3장: 함수 객체(PyFunctionObject)의 호출 경로 — _PyEval_EvalFrameDefault, 스택 프레임(PyFrameObject)의 동적 생성과 해제

이제 호출 대상이 순수한 파이썬 함수 def f(): ...인 경우, CPython 인터프리터 내부에서 어떤 기계적 절차가 일어나는지 들여다봅시다.

Function Object vs Code Object의 엄격한 분리

많은 파이썬 프로그래머들이 함수와 코드를 같은 것으로 혼동합니다. 하지만 CPython의 멘탈 모델에서 둘은 완벽히 분리된 서로 다른 계층의 객체입니다:

구분 PyCodeObject (코드 객체) PyFunctionObject (함수 객체)
역할 순수한 실행 청사진 (불변의 레시피) 런타임 바인딩 실행 환경 (살아있는 조리사)
포함 내용 바이트코드(co_code), 상수표(co_consts), 변수명(co_varnames) 전역 네임스페이스(func_globals), 기본값(func_defaults), 클로저(func_closure)
가변성 완전 불변(Immutable) — 컴파일 시점에 한 번 생성되어 공유됨 가변(Mutable) — def 문이 실행될 때마다 새롭게 생성 가능
C struct PyFunctionObject 구조체 정의 (cpython/Include/cpython/funcobject.h)
▼
c 
typedef struct {
    PyObject_HEAD
    PyObject *func_globals;       /* 함수가 참조할 글로벌 __dict__ */
    PyObject *func_builtins;      /* __builtins__ */
    PyObject *func_name;          /* __name__ */
    PyObject *func_qualname;      /* __qualname__ */
    PyObject *func_code;          /* PyCodeObject 포인터 (핵심 청사진) */
    PyObject *func_defaults;      /* 튜플 형태의 기본 위치 인자 */
    PyObject *func_kwdefaults;    /* 딕셔너리 형태의 기본 키워드 인자 */
    PyObject *func_closure;       /* 자유 변수 클로저 셀 튜플 */
    PyObject *func_doc;           /* __doc__ */
    PyObject *func_dict;          /* 함수 객체 임의 속성용 __dict__ */
    vectorcallfunc vectorcall;    /* 초고속 실행 포인터 (_PyFunction_Vectorcall) */
    /* ... 버전별 모듈 필드 ... */
} PyFunctionObject;

_PyInterpreterFrame과 실행 프레임 스택의 동적 라이프사이클

PyFunctionObject가 호출되면 CPython은 이 함수의 독자적인 실행 영역인 스택 프레임(Frame)을 할당해야 합니다.

Python 3.10 이전에는 매 함수 호출마다 OS의 C 힙(malloc)에서 PyFrameObject 구조체를 할당했습니다. 이 때문에 깊은 재귀 호출이나 수많은 작은 함수를 호출할 때 엄청난 메모리 할당 오버헤드가 발생했습니다.

Python 3.11+의 대혁신: Frame Chunks (연속 메모리 청크 할당)
현대 CPython은 스레드 상태(PyThreadState) 내에 미리 거대한 메모리 청크(연속 버퍼)를 마련해 두고, 함수가 호출되면 마치 CPU의 하드웨어 콜 스택처럼 포인터(datastack_top)만 쓱 올려서 _PyInterpreterFrame을 할당합니다.

text 
┌────────────────────────────────────────────────────────┐
│ _PyInterpreterFrame (연속 메모리 청크 레이아웃)         │
├────────────────────────────────────────────────────────┤
│ f_code        ──► 실행할 PyCodeObject 포인터            │
│ f_globals     ──► 전역 변수 딕셔너리                    │
│ f_locals      ──► 지역 변수 딕셔너리 (필요시 지연 생성)│
│ prev_instr    ──► 현재 실행 중인 바이트코드 오프셋      │
│ previous      ──► 호출자(Caller)의 프레임 포인터       │
├────────────────────────────────────────────────────────┤
│ localsplus[0] ──► 전달된 인자 1 (a = 1)                 │
│ localsplus[1] ──► 전달된 인자 2 (b = 2)                 │
│ localsplus[2] ──► 내부 로컬 변수 (c = a + b)           │
│ localsplus[3] ──► 함수 전용 Evaluation Stack 바닥     │
│ ...           ──► (스택 푸시/팝 공간)                  │
└────────────────────────────────────────────────────────┘

프레임이 준비되면 CPython의 심장이자 거대한 스위치문 루프인 _PyEval_EvalFrameDefault()가 가동됩니다. 프레임의 바이트코드를 한 단계씩 읽어 지역 변수를 연산하고, RETURN_VALUE를 만나면 결과를 호출자 스택에 푸시한 뒤 프레임 포인터를 이전 프레임(frame->previous)으로 복원하며 즉각 해제됩니다.

# 4장: 일반 인스턴스 객체의 호출 경로 — type(obj).__call__(obj, 1, 2) 탐색 및 이중 디스패치

많은 파이썬 입문자들이 함수가 아닌 일반 클래스의 인스턴스를 호출할 때 obj(1, 2)가 obj.__call__(1, 2)와 완전히 같다고 배웁니다. 하지만 CPython C-API 레벨에서 이 둘은 중대한 차이점을 갖습니다.

왜 obj.__dict__를 건너뛰고 type(obj)에서 직접 찾는가?

인터프리터가 obj(1, 2)를 실행할 때, 인터프리터는 인스턴스 obj의 네임스페이스(obj.__dict__)를 전혀 보지 않습니다. 대신 오직 obj의 타입인 Py_TYPE(obj)의 타입 슬롯만을 즉시 조회합니다.

개념적으로 이것은 다음과 같이 표현됩니다:

$$\text{obj}(1, 2) \implies \text{type}(\text{obj}).\_\_\text{call}\_\_(\text{obj}, 1, 2)$$

이 메커니즘을 증명하는 결정적 실험을 살펴봅시다:

python 
class A:
    def __call__(self, x, y):
        return f"클래스 __call__: {x + y}"

obj = A()

# 1. 일반적인 호출 -> 클래스의 __call__이 정상 발동
print(obj(10, 20)) # "클래스 __call__: 30"

# 2. 인스턴스 객체의 속성에 직접 __call__을 덮어써 본다!
obj.__call__ = lambda x, y: f"인스턴스 람다: {x * y}"

# 3. 명시적으로 점(.)을 찍고 속성 호출을 하면 인스턴스 람다가 실행된다
print(obj.__call__(10, 20)) # "인스턴스 람다: 200"

# 4. 하지만 원래 문법인 obj(...)로 호출하면?
print(obj(10, 20)) # 여전히 "클래스 __call__: 30"이 출력된다!
⚠️ 파이썬 스페셜 메서드(Dunder Method)의 철칙

__call__, __getitem__, __add__ 등 모든 파이썬 스페셜 메서드는 CPython에서 속도 최적화와 메타순환 일관성을 위해 인스턴스 딕셔너리를 철저히 무시하고 타입 구조체(PyTypeObject)의 슬롯에서만 직접 탐색합니다. 인스턴스에 동적으로 꽂아 넣은 스페셜 메서드는 절대 연산자 구문으로 발동되지 않습니다.

클래스 자체의 호출(Dog())과 type_call의 대칭성

그렇다면 Dog()처럼 클래스 이름을 호출하여 새로운 인스턴스를 만들 때는 무엇이 실행될까요?

파이썬의 가장 아름다운 점은 "클래스도 객체"라는 사실입니다. Dog의 타입은 type입니다. 따라서 Dog() 호출 역시 일반 인스턴스 호출과 완벽하게 동일한 공식이 적용됩니다:

$$\text{Dog}() \implies \text{type}(\text{Dog}).\_\_\text{call}\_\_(\text{Dog}) \implies \text{type}.\_\_\text{call}\_\_(\text{Dog})$$

CPython 내부에서 type의 tp_call 슬롯에는 type_call()이라는 C 함수가 연결되어 있습니다. 이 함수가 수행하는 일은 우리가 익히 아는 객체 생성 2단계입니다:

  1. Dog.__new__(Dog, *args, **kwargs)를 호출하여 힙에 빈 메모리 인스턴스를 생성.
  2. 생성된 인스턴스가 Dog의 인스턴스라면, Dog.__init__(instance, *args, **kwargs)를 호출하여 속성 초기화.
  3. 완성된 인스턴스를 반환.

결국 함수 실행, 인스턴스 실행, 클래스 인스턴스화가 모조리 Py_TYPE(x)->tp_call이라는 단 하나의 통일된 기계적 메커니즘으로 수렴하는 것입니다.

# 5장: PyObject와 PyTypeObject의 거대한 순환 메모리 구조 — 모든 객체의 ob_type 포인터, type과 object의 기묘한 뫼비우스의 띠

호출 프로토콜의 모든 경로는 결국 하나의 근원적인 질문으로 이어집니다: "CPython은 도대체 객체의 타입을 메모리에서 어떻게 표현하고 있는가?"

PyObject_HEAD: 모든 파이썬 객체의 최소 공통 헤더

CPython이 int, str, list, dict, function 등 수없이 다양한 자료형을 단일한 C 함수 포인터 PyObject*로 자유자재로 다룰 수 있는 마법의 열쇠는 바로 공통 헤더입니다.

c (cpython/Include/object.h) 
/* 파이썬의 모든 객체가 메모리 맨 첫머리에 지니는 공통 헤더 */
#define _PyObject_HEAD_EXTRA
#define PyObject_HEAD          \
    _PyObject_HEAD_EXTRA       \
    Py_ssize_t ob_refcnt;      /* 메모리 참조 카운트 (GC용) */ \
    PyTypeObject *ob_type;     /* 객체의 타입을 가리키는 C 포인터! */

struct _object {
    PyObject_HEAD
};

어떤 메모리 덩어리가 파이썬 객체라면, 그 주소를 (PyObject*)로 캐스팅했을 때 오프셋 0에는 반드시 ob_refcnt가 있고, 그 바로 다음 오프셋에는 자신의 타입 정보가 담긴 PyTypeObject의 메모리 주소(ob_type)가 존재합니다.

type과 object의 뫼비우스의 띠: 기묘한 자기참조 순환

여기서 파이썬 객체 모델의 가장 심오하고 매혹적인 영역이 등장합니다. 클래스를 정의하는 PyTypeObject 역시 CPython 힙에 존재하는 객체(Object)입니다! 즉 PyTypeObject의 메모리 첫머리에도 ob_type이 존재합니다.

그렇다면 타입 객체의 타입은 무엇일까요?

python 
d = 123
print(type(d))        # <class 'int'>
print(type(int))      # <class 'type'>
print(type(type))     # <class 'type'>  <-- 자기 자신을 가리킨다!

print(isinstance(object, type))   # True  (object는 type의 인스턴스)
print(issubclass(type, object))   # True  (type은 object를 상속)
print(isinstance(type, object))   # True  (type도 결국 object)

이 관계를 시각화하면 뫼비우스의 띠와 같은 완벽한 3계층 순환 참조가 드러납니다:

🌀 [메모리 순환도] ob_type 포인터 체인과 type-object 뫼비우스 고리

C 소스코드의 마법: 닭과 달걀의 부트스트랩

"type의 타입이 type이라면, 도대체 최초의 type 객체는 누가 만드는가?"라는 철학적 딜레마가 생깁니다.

CPython 개발자들은 이 문제를 C 언어의 정적 메모리 선언(Static Struct Initialization)을 통해 우아하게 해결했습니다.

C source typeobject.c 내부의 PyType_Type 정적 순환 초기화
▼
c (cpython/Objects/typeobject.c) 
/* CPython 소스코드에서 type의 정적 정의 */
PyTypeObject PyType_Type = {
    PyVarObject_HEAD_INIT(&PyType_Type, 0) /* ob_type에 자기 자신의 주소(&PyType_Type)를 즉시 대입! */
    "type",                                 /* tp_name */
    sizeof(PyHeapTypeObject),               /* tp_basicsize */
    0,                                      /* tp_itemsize */
    (destructor)type_dealloc,               /* tp_dealloc */
    0,                                      /* tp_vectorcall_offset */
    0,                                      /* tp_getattr */
    0,                                      /* tp_setattr */
    0,                                      /* tp_as_async */
    (reprfunc)type_repr,                    /* tp_repr */
    0,                                      /* tp_as_number */
    0,                                      /* tp_as_sequence */
    0,                                      /* tp_as_mapping */
    0,                                      /* tp_hash */
    (ternaryfunc)type_call,                 /* tp_call (클래스를 호출했을 때 실행되는 함수!) */
    ...
};

런타임에 동적으로 생성하려면 닭이 먼저냐 달걀이 먼저냐 싸워야 하지만, C 컴파일러 빌드 시점에 C 구조체 포인터 ob_type에 자기 자신의 메모리 주소 &PyType_Type을 하드코딩해 둠으로써 무한 루프의 기저점을 단숨에 완성해 버린 것입니다.

# 에필로그: 기계적 관점에서 본 파이썬 — 동적성의 진짜 실체

많은 사람들이 파이썬을 "느리고 규칙 없는 동적 언어"라고 오해합니다. 하지만 그 껍질을 한 겹 벗겨 CPython의 엔진 내부로 들어가 보면, 상상 이상으로 정교하고 규율 잡힌 C 구조체와 함수 포인터들의 기계적 교향곡이 울려 퍼지고 있음을 알게 됩니다.

파이썬의 동적성은 무질서가 아닙니다:

  • 모든 객체는 한 치의 오차도 없이 첫머리에 ob_type 포인터를 품고 있습니다.
  • 소괄호 ()는 문법이 아닌 PyTypeObject의 타입 슬롯을 격발하는 정밀한 프로토콜입니다.
  • 현대의 vectorcall과 PUSH_NULL 최적화는 동적 호출의 유연성을 100% 지키면서도 C 수준의 메모리 슬라이스 전달을 실현해 냈습니다.
  • type과 object의 순환 구조는 정적 C 구조체 선언이라는 묘수를 통해 무한 재귀를 딛고 언어 전체를 스스로 지탱합니다.

이 시스템 수준의 멘탈 모델을 장착한 개발자는 더 이상 파이썬 코드의 겉모습에 휘둘리지 않습니다. 코드가 왜 그렇게 동작하고, 어디서 병목이 발생하며, 어떻게 작성해야 인터프리터와 호흡을 맞출 수 있는지 꿰뚫어 보게 됩니다.
