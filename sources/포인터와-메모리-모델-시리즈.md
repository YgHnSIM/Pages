# 1편: 포인터는 복잡합니다, 혹은: 바이트 안에는 무엇이 들어있을까요?

- **작성일**: 2018년 7월 24일
- **원문**: [ralfj.de/blog/2018/07/24/pointers-and-bytes.html](https://www.ralfj.de/blog/2018/07/24/pointers-and-bytes.html)

C, C++, Rust와 같은 저수준 언어에서 프로그래밍을 배울 때 보통 가장 먼저 배우는 멘탈 모델 중 하나는 "메모리는 그저 바이트들의 거대한 배열일 뿐이며, 포인터는 그 배열의 인덱스(즉, 정수 주소)에 불과하다"라는 것입니다. 하드웨어 관점에서 볼 때 이것은 거의 사실에 가깝습니다. 하지만 프로그래밍 언어의 의미론(semantics) 관점, 그리고 컴파일러가 프로그램을 최적화하는 방식의 관점에서 볼 때 이 멘탈 모델은 심각하게 망가져 있습니다.

이 글에서는 "바이트"와 "포인터"가 실제로 무엇인지를 설명하고, 왜 이들이 단순한 $0$부터 $255$까지의 숫자나 정수 주소가 될 수 없는지 다루고자 합니다.

## 단순한 멘탈 모델의 붕괴

만약 포인터가 정말 단순한 정수이고 메모리가 바이트의 배열일 뿐이라면, 컴파일러는 수많은 최적화를 수행할 수 없게 됩니다. 다음 C 코드를 생각해 봅시다:

```c
int foo(int *x, int *y) {
    *x = 42;
    *y = 7;
    return *x;
}
```

컴파일러는 `*x`와 `*y`가 서로 다른 메모리 위치를 가리킨다고(즉, 앨리어싱되지 않는다고) 가정할 수 있을 때, 마지막 `return *x;`를 `return 42;`로 최적화하고 메모리 읽기를 생략하고 싶어 합니다. 하지만 포인터가 단순한 정수라면, 누군가 `foo`를 다음과 같이 호출할 수 있습니다:

```c
int a;
foo(&a, &a);
```

이 경우 `*y = 7;`은 `*x`를 덮어쓰므로 `return 7;`이 되어야 합니다. 컴파일러는 앨리어싱 분석(Alias Analysis)을 통해 두 포인터가 겹치지 않는다는 확신이 들 때만 이 최적화를 수행합니다. 하지만 문제는 여기서 끝나지 않습니다.

## 초기화되지 않은 메모리 (Uninitialized Memory)

메모리가 단순히 바이트(0~255)의 배열이라는 모델이 깨지는 첫 번째 이유는 **초기화되지 않은 메모리(uninitialized memory)** 때문입니다.

많은 사람들은 초기화되지 않은 메모리를 읽으면 "그냥 메모리에 우연히 남아있던 어떤 임의의 고정된 바이트 값"을 얻게 된다고 생각합니다. 하지만 LLVM이나 C/C++ 표준, 그리고 Rust의 추상 기계(Abstract Machine)에서 초기화되지 않은 메모리는 특정 숫자 값이 아닙니다. LLVM에서는 이를 `undef`(또는 최근의 `poison`)라는 특수한 값으로 표현합니다.

만약 초기화되지 않은 메모리가 단순히 "어떤 임의의 비트 패턴"이라면 다음과 같은 코드에서 문제가 발생합니다:

```c
// x는 초기화되지 않은 지역 변수
int x;
if (x == 0) {
    do_something();
} else {
    do_something_else();
}
```

컴파일러는 최적화 과정에서 `x`를 레지스터로 올리거나 여러 번 읽을 수 있습니다. 만약 `x`가 읽을 때마다 다른 값을 낼 수 있거나, 조건문 분기에서 결정되지 않은 값으로 취급된다면, 컴파일러는 두 분기 모두 실행되지 않거나 두 분기 모두 실행되는 형태의 기괴한 변환을 저지를 수 있습니다. 실제로 C/C++에서 초기화되지 않은 변수를 읽는 행위는 정의되지 않은 동작(Undefined Behavior, UB)입니다.

따라서 추상 기계에서 "하나의 바이트"는 $0 \dots 255$ 범위의 정수뿐만 아니라 **"초기화되지 않음(Uninit)"**이라는 특별한 상태를 표현할 수 있어야 합니다.

## 포인터는 단순한 정수가 아니다: 포인터 출처 (Pointer Provenance)

두 번째로 큰 문제는 포인터가 단순히 메모리 주소를 가리키는 정수가 아니라는 점입니다. 포인터에는 **출처(Provenance)**라는 개념이 붙어 있습니다.

다음 예시를 살펴보겠습니다:

```c
int test() {
    int x = 0, y = 0;
    uintptr_t x_addr = (uintptr_t)&x;
    uintptr_t y_addr = (uintptr_t)&y;
    
    // x와 y가 메모리상에서 우연히 연속해서 배치되었다고 가정해 봅시다.
    // x_addr + sizeof(int) == y_addr 인 상황입니다.
    int *p = (int*)(x_addr + sizeof(int));
    *p = 42; // 이것은 y를 합법적으로 수정한 것일까요?
    return y;
}
```

만약 포인터가 단순히 정수 주소라면, `p`가 가리키는 주소는 `&y`의 실제 하드웨어 주소와 완벽히 일치하므로 `*p = 42;`는 `y`의 값을 `42`로 변경해야 하고, 함수는 `42`를 반환해야 합니다.

하지만 C/C++ 및 Rust의 메모리 모델에서 이 코드는 **정의되지 않은 동작(UB)**입니다. 왜냐하면 `p`는 `x`의 주소로부터 파생되었기 때문에, `x`의 할당 영역(allocation)을 벗어난 접근 권한을 가지지 못하기 때문입니다. `p`의 "출처(Provenance)"는 `x`에 묶여 있으며, 비록 계산된 주소가 우연히 `y`의 시작 주소와 일치하더라도 `y`를 수정할 권한이 없습니다.

만약 컴파일러가 이것을 UB로 취급하지 않는다면, 컴파일러는 `x`를 수정하는 행위가 `y`에 영향을 주지 않는다는 사실을 증명할 수 없게 되어 거의 모든 최적화(루프 불변 코드 이동, 공통 부분식 제거, 상수 전파 등)를 포기해야 합니다.

## 추상 기계에서 "바이트"란 무엇인가?

이 모든 것을 종합하면, 우리가 생각하는 언어의 의미론적 추상 기계(Abstract Machine)에서 **1바이트**는 단순히 8비트 정수가 아닙니다. 추상 기계의 메모리 상에서 1바이트는 대략 다음과 같은 상태를 가질 수 있는 유니온(Sum Type) 형태여야 합니다:

1. **초기화된 구체적 데이터 바이트**: $0$부터 $255$ 사이의 구체적인 8비트 정수 값.
2. **초기화되지 않은 바이트 (Uninit)**: 아직 초기화되지 않았음을 나타내는 특수 마커.
3. **포인터의 일부 조각**: 포인터 값(포인터의 ID/할당 식별자 및 출처 + 오프셋)을 구성하는 바이트 조각.

64비트 아키텍처에서 포인터는 8바이트 크기를 가집니다. 만약 포인터를 메모리에 저장하면, 8개의 연속된 바이트 각각은 "어떤 할당(Allocation)을 가리키는 출처 정보와 오프셋을 담은 포인터의 $n$번째 바이트"라는 정보를 유지해야 합니다. 그래야 나중에 그 8바이트를 다시 포인터로 읽어 들였을 때 올바른 출처(Provenance)를 복원할 수 있습니다.

예를 들어 `memcpy`를 이용해 포인터가 저장된 메모리를 다른 곳으로 바이트 단위로 복사하더라도 포인터가 제 기능을 하는 이유는, 추상 기계가 각 바이트에 담긴 출처 정보를 함께 복사하기 때문입니다.

## 1편 결론

하드웨어 수준에서는 모든 것이 0과 1의 비트이고 주소는 정수일 뿐이지만, **프로그래밍 언어의 추상 기계 수준에서 포인터는 정수가 아니며, 바이트는 단순한 8비트 숫자가 아닙니다.**

포인터는 `(할당 ID / 출처, 오프셋)`이라는 추가적인 정보를 담고 있으며, 바이트는 초기화되지 않은 상태나 포인터의 일부분이라는 추상적 정보를 품고 있어야만 현대 컴파일러가 안전하고 공격적인 최적화를 수행할 수 있습니다.

# 2편: 포인터는 복잡합니다 II, 혹은: 포인터 출처(Provenance)란 무엇인가?

- **작성일**: 2020년 12월 14일
- **원문**: [ralfj.de/blog/2020/12/14/provenance.html](https://www.ralfj.de/blog/2020/12/14/provenance.html)

2년 전, 저는 1편을 통해 포인터가 단순히 정수 주소가 될 수 없는 이유와 메모리의 바이트가 단순히 $0 \dots 255$ 범위의 정수가 될 수 없는 이유를 다루었습니다. 이번 후속 글에서는 그 핵심 개념인 **포인터 출처(Pointer Provenance)**를 더 깊이 파고들고, 왜 C, C++, Rust와 같은 언어의 명세(Specification)에서 이를 명확히 정의하는 것이 그토록 어려운 문제인지 설명하고자 합니다.

## 기본 문제: 앨리어싱과 최적화

컴파일러 최적화의 핵심 목표 중 하나는 불필요한 메모리 접근을 제거하는 것입니다. 예를 들어 다음과 같은 코드를 봅시다:

```c
int foo(int *p, int *q) {
    *p = 1;
    *q = 2;
    return *p;
}
```

컴파일러는 `*p`를 다시 읽지 않고 즉시 `1`을 반환하도록 최적화하고 싶어 합니다. 이를 정당화하기 위해 컴파일러는 `p`와 `q`가 같은 메모리 위치를 가리키지 않는다고(서로 앨리어싱되지 않는다고) 가정할 수 있어야 합니다.

만약 두 포인터가 다음과 같이 서로 다른 변수에서 파생되었다면:

```c
int x = 0;
int y = 0;
foo(&x, &y);
```

C와 Rust의 규칙에 따라 `&x`와 `&y`는 서로 다른 할당(allocation)에 속하므로 서로 앨리어싱될 수 없으며, 컴파일러의 최적화는 완전히 유효합니다.

## 주소 추측(Guessing Addresses)과 출처의 필요성

하지만 포인터가 "단순히 정수 주소일 뿐"이라면 다음과 같은 일이 벌어질 수 있습니다:

```c
int x = 0;
int y = 0;

// x와 y의 주소가 우연히 연속해 있다고 가정하고, 정수 연산을 통해 y의 주소를 계산합니다.
uintptr_t addr_x = (uintptr_t)&x;
uintptr_t addr_y = (uintptr_t)&y;

// 만약 addr_x + sizeof(int) == addr_y 라면:
int *q = (int*)(addr_x + sizeof(int));
foo(&x, q);
```

하드웨어 관점에서 `q`가 가진 비트 패턴은 `&y`의 실제 주소와 완벽히 같습니다. 따라서 `foo` 내부의 `*q = 2;`는 물리적으로 `y`의 메모리 위치에 `2`를 쓰게 됩니다. 하지만 `foo(&x, q)`에서 컴파일러가 `*p`와 `*q`가 앨리어싱되지 않는다고 판단하여 `foo`의 반환값을 `1`로 최적화해 버렸다면, 실제 실행 결과와 컴파일러의 최적화 사이에 모순이 발생합니다.

이 모순을 해결하기 위해 프로그래밍 언어 추상 기계는 **출처(Provenance)**라는 개념을 도입합니다.

> **포인터의 정의:** 추상 기계에서 포인터는 단순히 `0x12345678` 같은 정수 주소가 아니라, **`(태그/할당 ID, 주소)`**의 쌍입니다.

포인터가 역참조(dereference)될 때, 추상 기계는 단순히 그 주소에 메모리가 존재하는지만 검사하는 것이 아니라, 해당 포인터의 **태그(출처)**가 그 주소의 메모리 할당(allocation)에 접근할 권한이 있는지를 함께 검사합니다.

위 예시에서 `&x`에서 계산되어 나온 `q`의 출처 태그는 여전히 `x`에 묶여 있습니다. 비록 `q`의 정수 주소는 `y`를 가리키고 있을지라도, `x`의 태그로는 `y`의 메모리 할당에 접근할 수 없습니다. 따라서 `*q = 2;`는 유효하지 않은 메모리 접근이며, **정의되지 않은 동작(Undefined Behavior)**이 됩니다. 이 덕분에 컴파일러는 안심하고 `foo`를 `return 1;`로 최적화할 수 있습니다.

## 진짜 난제: 정수와 포인터 간의 형변환 (int2ptr & ptr2int)

포인터 출처 모델에서 가장 다루기 어렵고 논쟁적인 부분은 바로 정수와 포인터 사이의 상호 변환입니다.

1. **포인터를 정수로 변환 (`ptr2int` / `(uintptr_t)p`)**:  
   포인터를 정수로 캐스팅하면 출처 태그는 어떻게 될까요? 정수는 순수한 수학적 숫자이므로 출처 태그를 담을 공간이 없습니다. 따라서 정수로 변환되는 순간 출처 태그는 "사라집니다".
2. **정수를 포인터로 변환 (`int2ptr` / `(int*)i`)**:  
   출처가 없는 순수한 정수를 다시 포인터로 캐스팅할 때, 그 포인터는 **어떤 출처 태그를 가져야 할까요?**

이 질문에 답하기 위해 C 표준 위원회(WG14)와 LLVM, Rust 커뮤니티에서는 여러 가지 메모리 모델을 제안하고 논의해 왔습니다.

### 1. PVI (Provenance Via Integers)

정수 타입 자체에도 보이지 않는 출처 태그를 붙여서 정수 연산을 할 때도 출처가 전파되도록 하자는 모델입니다. 하지만 이 모델은 정수 최적화(예: `x - x = 0`, 비트 연산 최적화 등)를 심각하게 망가뜨립니다. 정수 산술 연산에 포인터 출처 추적 규칙을 적용하는 것은 컴파일러 구현상 비현실적입니다.

### 2. PNVI (Provenance Not Via Integers)

정수는 순수한 숫자이며 어떠한 출처도 가지지 않는다는 모델입니다. 대신 `int2ptr`(정수에서 포인터로의 캐스트)가 일어나는 순간, 추상 기계가 "적절한 출처를 추측하거나 복원"합니다. 여기에는 세부적인 변형들이 있습니다:

- **PNVI-plain**: `int2ptr` 변환 시, 해당 주소가 현재 살아있는(live) 유효한 할당 영역 내에 속해 있다면 그 할당의 출처를 자동으로 부여받습니다. 그러나 만약 두 개의 서로 다른 할당이 0바이트 크기로 맞닿아 있거나 경계에 걸쳐 있다면 어떤 할당의 출처를 주어야 할지 모호해지는 문제가 있습니다.
- **PNVI-ae (Address-Exposed)**: 아무 정수나 포인터로 둔갑할 수 있는 것이 아니라, 이전에 `ptr2int` 캐스팅을 통해 **주소가 노출된(exposed)** 적이 있는 할당에 대해서만 `int2ptr`를 통해 출처를 복원할 수 있도록 제한하는 방식입니다.
- **PNVI-ae-udi (User-Disambiguation)**: 주소 경계가 겹쳐서 모호할 때, 프로그래머가 나중에 해당 포인터를 실제로 어떻게 사용하는지를 보고 추상 기계가 사후적으로 출처를 결정(Disambiguation)하는 방식입니다. 하지만 이는 형식화하기가 대단히 복잡합니다.

### 3. 엄격한 출처 모델 (Strict Provenance)

현재 Rust 커뮤니티(및 저와 여러 연구자들)가 적극적으로 추진하고 있는 대안은 **엄격한 출처(Strict Provenance)** 모델입니다.

이 모델에서는 정수를 다시 포인터로 변환하는 마법 같은 `int2ptr` 캐스팅을 지양합니다. 대신 포인터의 주소를 조작할 때 기존 유효한 포인터의 출처를 명시적으로 유지하는 새로운 API를 제공합니다:

- `ptr.addr() -> usize`: 포인터에서 순수한 정수 주소만 읽어옵니다 (출처 노출 없음).
- `ptr.with_addr(addr: usize) -> *T`: `ptr`가 가지고 있던 기존 출처(Provenance) 태그를 그대로 유지하면서 주소 부분만 새로운 `addr`로 교체합니다.
- `ptr.expose_addr()` 및 `from_exposed_addr(addr)`: 하위 호환성을 위해 전통적인 정수-포인터 캐스팅이 필요한 경우에만 제한적으로 명시적 노출을 사용합니다.

엄격한 출처 모델을 사용하면 포인터와 정수의 경계가 명확해지며, 컴파일러는 모호한 추측 없이 공격적인 최적화를 수행할 수 있고, Miri와 같은 정적/동적 검증 도구가 정의되지 않은 동작을 정확하게 감지할 수 있습니다.

## 2편 요약 및 결론

1. **포인터는 정수가 아닙니다**: 포인터는 메모리 주소뿐만 아니라, 특정 메모리 할당에 접근할 수 있는 자격을 부여하는 **출처(Provenance)**를 담고 있습니다.
2. **출처는 컴파일러 최적화의 필수 조건입니다**: 출처 개념이 없다면 컴파일러는 포인터 간의 앨리어싱 여부를 신뢰할 수 없으며, 대부분의 핵심 최적화가 불가능해집니다.
3. **정수와 포인터의 변환은 매우 까다롭습니다**: 임의의 정수를 포인터로 변환하는 동작은 언어 명세상 가장 정의하기 어려운 부분 중 하나이며, 이를 깔끔하게 해결하기 위해 **Strict Provenance**와 같은 새로운 모델이 표준화되고 있습니다.

우리가 안전하고 빠른 저수준 코드를 작성하기 위해서는, 하드웨어의 단순한 바이트 배열 너머에 존재하는 프로그래밍 언어의 엄밀한 메모리 모델과 포인터 출처의 규칙을 이해하는 것이 필수적입니다.
