# LLM 에이전트 스킬 아키텍처와 실전 엔지니어링

2024년이 에이전트의 **행동 패턴**(반추, 도구 사용, 기획, 멀티 에이전트)을 탐색하던 해였고, 2025년이 이들을 정량적으로 측정하는 **평가**(Evals)의 해였다면, 2026년은 **에이전트 스킬(Agent Skills)이 소프트웨어 엔지니어링의 표준 운영 스택으로 안착한 해**입니다.

앤드류 응(Andrew Ng) 교수는 2026년에 들어서며 일관되게 한 가지 명제를 강조해 왔습니다. 

> “**에이전트 스킬은 수천 줄짜리 시스템 프롬프트가 아니다. 필요할 때만 호출되는 온디맨드(On-demand) 지식과 워크플로를 담은 이식 가능한 지시사항 폴더다.**”

본 글에서는 바이브 코딩(Vibe Coding)의 혼돈과 컨텍스트 비대화(Context Bloat)를 극복하기 위해 등장한 **에이전트 스킬 아키텍처**의 본질을 파헤칩니다. 앤드류 응의 2026년 연표부터 도구 중립적 하네스(Harness) 실행 메커니즘, 3대 핵심 시각화 모델, 실전 `SKILL.md` 보일러플레이트, 그리고 모델 진화에 따른 ‘스킬 가지치기(Pruning)’ 철학까지 한 편에 정리합니다.

---

## 1. 진화의 궤적: 패턴에서 운영 스택으로

AI 에이전트를 다루는 개발자의 패러다임은 지난 3년간 급격히 성숙했습니다.

| 시기 | 중심 패러다임 | 핵심 질문과 병목 | 도달한 결론 |
|---|---|---|---|
| **2024년** | **Agentic Patterns** | "LLM이 스스로 생각하고 도구를 쓰게 하려면?" | 4대 기본 패턴 (Reflection, Tool Use, Planning, Multi-Agent) 정립 |
| **2025년** | **Evals & Harness** | "에이전트가 내놓은 코드를 어떻게 신뢰하고 측정할 것인가?" | 벤치마크, 단위 테스트 하네스, 지속적 성능 평가 체계 |
| **2026년 상반기** | **Portable Skills** | "거대해진 지시사항을 어떻게 컨텍스트 손실 없이 재사용할 것인가?" | 오픈 표준 폴더 규격(`SKILL.md`), Context Hub(`chub`), 스펙 주도 개발 |
| **2026년 하반기** | **Operational Stack** | "수많은 스킬과 도구를 어떻게 관리하고 정리할 것인가?" | 상주 운영 레이어 편입(Skills + MCP + Subagents), 정기적 가지치기(Pruning) |

과거에는 에이전트가 똑똑해지길 바라며 모든 프로젝트 규칙, 코딩 컨벤션, API 문서, 도메인 지식을 `system prompt`나 거대한 단일 지침 파일(`CLAUDE.md`, `AGENTS.md`)에 몰아넣었습니다. 그러나 컨텍스트 윈도우가 아무리 1M, 2M 토큰으로 늘어나더라도, **모든 정보를 항상 주입하는 방식은 세 가지 치명적인 결함**을 낳았습니다.

1. **주의력 분산 (Attention Dilution / "Lost in the Middle")**: 불필요한 규칙이 섞여 있을 때 모델이 당장 수행해야 할 작업의 핵심 제약을 놓침.
2. **토큰 비용 및 지연 시간 폭증**: 단순한 파일 수정 작업 하나에도 매 턴 수만 토큰의 정적 지침이 왕복함.
3. **지식의 부패(Staleness)**: API 버전이 올라가거나 컨벤션이 바뀔 때 단일 프롬프트를 유지보수하기가 불가능에 가까워짐.

이를 해결하기 위해 탄생한 개념이 바로 **점진적 컨텍스트 주입**(Progressive Context Loading)에 기반한 **에이전트 스킬**(Agent Skills)입니다.

## 2. 두 가지 "스킬"의 엄밀한 분리

앤드류 응의 2026년 발표와 The Batch 기고문을 읽을 때 가장 먼저 짚어야 할 지점은 ‘**스킬’이라는 단어가 전혀 다른 두 개의 층위**’(Layer)에서 사용된다는 점입니다.

앤드류 응은 2026년 8~9월 연재한 *AI Engineering Skills Map*을 통해 개발자의 핵심 역량을 4개 축으로 정리했습니다:
1. **AI 애플리케이션 구축 및 배포 (Building & Deploying)**: LLM 기초, 그라운딩, 파이프라인.
2. **소프트웨어 공학 기초 (Software Fundamentals)**: 아키텍처 트레이드오프, 모듈 분리, 테스트.
3. **코딩 에이전트 운영 (Using Coding Agents)**: 워크플로 조율, 자율성 통제, **스킬·플러그인·MCP 커스터마이징**.
4. **빌드 형상화 (Shaping the Build)**: 만들 것과 차용할 것을 선별하는 제품 엔지니어링 시각.

즉, 에이전트 스킬을 잘 다루는 것은 더 이상 보조 도구 사용법이 아니라, 현대 소프트웨어 엔지니어가 갖춰야 할 본질적 역량의 한 축입니다.

## 4. 도구 중립적 하네스(Harness) 실행 메커니즘

어떤 CLI나 에이전트 런타임을 사용하든(Claude Code, OpenAI Codex, Antigravity 등), 오픈 표준 에이전트 스킬을 처리하는 하네스 엔진의 내부 동작 파이프라인은 일관된 원리를 따릅니다.

### 파이프라인 4단계

1. **디렉터리 스캔 (Discovery Phase)**:
   - 하네스가 시작될 때 글로벌 디렉터리(`~/.config/.../skills`) 및 프로젝트 로컬 디렉터리(`.agents/skills/`, `.skills/`)를 탐색합니다.
   - 각 스킬 디렉터리의 루트에 있는 `SKILL.md`의 **YAML Frontmatter**만 파싱합니다.
   - 이때 본문 전체를 읽지 않고 오직 `name`, `description` 메타데이터만 메모리 색인(In-memory Index)에 등록합니다.
2. **트리거 매칭 (Intent Evaluation Phase)**:
   - 사용자의 프롬프트가 들어오면, 에이전트는 색인된 스킬 요약 목록과 사용자 의도를 비교합니다.
   - 정규식이나 키워드뿐 아니라 시맨틱 라우팅을 통해 가장 적합한 스킬을 식별합니다.
3. **온디맨드 인젝션 (Dynamic Context Injection)**:
   - 해당 스킬이 필요하다고 판단된 순간에만 `SKILL.md` 본문 지침을 모델의 프롬프트 윈도우에 주입합니다.
   - 보조 자료(상세 매뉴얼, 리소스 템플릿)가 필요한 경우, `references/` 디렉터리의 개별 파일을 읽도록 에이전트에게 도구 호출 경로를 안내합니다.
4. **결정론적 실행 및 격리 (Deterministic Execution)**:
   - 복잡한 수치 계산이나 반복 검증은 LLM의 자연어 생성에 의존하지 않고, 스킬 폴더 내 `scripts/`에 포함된 검증 스크립트를 하네스 셸에서 직접 구동합니다.

## 5. 실전 `SKILL.md` 표준 규격과 보일러플레이트

오픈 표준 스킬은 단순한 메모장이 아닙니다. 메타데이터와 명확한 제약 조건, 행동 양식이 구조화되어 있어야 합니다.

### 권장 디렉터리 구조

```text
my-awesome-skill/
├── SKILL.md              # [필수] 메인 진입점 및 행동 지침
├── scripts/              # [선택] 결정론적 검증 및 실행용 스크립트 (Python, Node 등)
│   └── verify.py
├── references/           # [선택] 필요할 때만 열람하는 도메인 심층 문서
│   └── architecture.md
└── templates/            # [선택] 보일러플레이트 코드 또는 출력 서식
    └── report.md
```

### 범용 `SKILL.md` 보일러플레이트

```markdown
---
name: my-awesome-skill
description: "스킬의 명확한 역할과 실행 트리거 조건을 한두 문장으로 기술합니다. (하네스가 색인할 때 읽는 핵심 요약문)"
version: 1.0.0
---

# 역할 및 목적 (Role & Goal)
이 스킬이 해결하고자 하는 구체적인 문제와 최종 도달해야 할 상태를 3줄 이내로 명시합니다.

## 트리거 조건 (When to use)
- 사용자가 "○○ 작업을 해줘", "△△를 검증해줘"라고 요청할 때
- 특정 파일 확장자나 패턴이 감지되었을 때

## 핵심 작업 절차 (Workflow)
1. **사전 점검**: 현재 워크스페이스의 상태를 확인하고 필요한 파일을 읽는다.
2. **실행 단계**:
   - `scripts/verify.py`를 실행하여 정량적 데이터를 수집한다.
   - 수집된 데이터에 기반해 코드를 최소 단위로 수정한다.
3. **결과 검증**: 회귀 테스트를 구동하여 기존 기능의 무결성을 증명한다.

## 금지 사항 및 제약 (Guardrails)
- ❌ 추측에 기반하여 존재하지 않는 API 파라미터를 사용하지 말 것.
- ❌ 사용자의 명시적 동의 없이 데이터베이스 마이그레이션을 실행하지 말 것.
- ❌ 250줄을 초과하는 모놀리식 파일을 생성하지 말 것.

## 참조 자료
- 세부 에러 규격: `references/error-codes.md` 참조
```

## 6. 앤드류 응의 2대 대표 실전 사례 해부

### 사례 A: Context Hub (`chub`) API 최신화 스킬

앤드류 응은 2026년 3월, 모델의 학습 데이터 단절로 인한 구식 API 호출 및 파라미터 환각 문제를 원천 차단하기 위해 **Context Hub**(`chub`)를 공개했습니다.

예컨대 에이전트가 최신 AI 라이브러리를 작성할 때, 이미 폐기된 1년 전의 `chat.completions` API를 부르거나 바뀐 옵션을 틀리게 적는 일이 빈번합니다. Context Hub 스킬은 에이전트가 코드를 작성하기 전에 최신 공식 API 레퍼런스를 CLI로 가져오도록 강제합니다.

#### `get-api-docs/SKILL.md` 실무 구현

```markdown
---
name: get-api-docs
description: "최신 라이브러리 및 API 호출 전 Context Hub(chub)를 통해 검증된 공식 문서를 검색하고 환각을 방지하는 스킬"
---

# 최신 API 레퍼런스 온디맨드 조회

## Why
모델 내부 학습 데이터의 컷오프로 인해 변경된 SDK 메서드 시그니처나 폐기된 파라미터를 작성하는 오류를 방지한다.

## Workflow
1. **API 호출 감지**: 코드 작성 중 외부 서비스(예: OpenAI, Anthropic, Supabase 등)의 SDK 호출이 필요할 때 즉시 발동한다.
2. **chub 검색 실행**:
   ```bash
   chub search "<library-name> <feature-name>"
   chub get "<doc-id>"
   ```
3. **인자 교차 검증**: 검색된 최신 마크다운 명세의 파라미터 목록과 작성할 코드의 인자를 1:1로 매핑하여 일치 여부를 확인한다.
4. **어노테이션 기록**:
   - 만약 문서와 실제 동작 간 괴리가 발견되거나 우회책(Workaround)이 필요했던 경우, 다음 명령어로 피드백을 기록해 팀 내 에이전트끼리 지식을 공유한다:
   ```bash
   chub annotate <doc-id> --note "v2.4부터는 authHeader 대신 bearerToken 키를 사용해야 함"
   ```

## Rules
- 공식 레퍼런스 없이 상상으로 SDK 옵션 객체를 조합하지 않는다.
```

### 사례 B: 스펙 주도 개발 (Spec-Driven Development) 스킬

2026년 4월 앤드류 응이 JetBrains와 함께 발표한 *Spec-Driven Development* 코스는 이른바 '바이브 코딩(Vibe Coding)'의 한계를 정면으로 다룹니다.

> "자연어로 대충 지시하고 코드를 마구잡이로 찍어내는 방식은 초기 프로토타입에는 빠르지만, 프로젝트가 커지면 컨텍스트 불일치와 미묘한 아키텍처 붕괴를 초래한다."

스펙 주도 개발 스킬은 “**스펙 작성 $\rightarrow$ 계획 수립 $\rightarrow$ 사용자 검토 $\rightarrow$ 코드 작성 $\rightarrow$ 테스트 검증**”의 파이프라인을 에이전트의 불변 규칙으로 강제합니다.

#### `spec-driven-dev/SKILL.md` 실무 구현

```markdown
---
name: spec-driven-dev
description: "즉흥적 코드 수정을 금지하고 명시적 사양서(Spec)와 회귀 테스트를 거쳐 구현하도록 통제하는 엔지니어링 스킬"
---

# 스펙 주도 개발 (SDD) 파이프라인

## Phase 1: 스펙 작성 (Specification)
- 구현을 시작하기 전, 기능의 입력/출력 인터페이스와 경계 조건(Edge Cases)을 담은 `SPEC.md`를 작성한다.
- 모호한 요구사항이 있다면 코드를 작성하지 말고 즉시 인터뷰 질문을 던져 사양을 확정한다.

## Phase 2: 구현 계획 승인 (Plan & Review)
- 영향을 받는 파일 목록과 의존성 그래프를 정리한 `implementation_plan.md`를 생성한다.
- **사용자의 명시적 승인 전까지 절대로 소스 코드를 편집하지 않는다.**

## Phase 3: 테스트 주도 구현 (Test-First Execution)
1. 새로운 스펙을 검증하는 실패하는 테스트(Red)를 먼저 작성한다.
2. 테스트를 통과시키는 최소한의 프로덕션 코드(Green)를 작성한다.
3. 코드의 복잡성을 줄이고 중복을 제거한다(Refactor).

## Phase 4: 증거 기반 완료 (Evidence Verification)
- 테스트 러너의 실행 로그와 터미널 종료 코드(Exit code 0)를 직접 확인하고, 검증 결과 보고서(`walkthrough.md`)를 남긴다.
```

## 7. 스킬 운영의 백미: 과감한 가지치기 (Pruning)

스킬 시스템을 도입한 팀이 가장 흔하게 저지르는 실수는 “**스킬의 개수를 끝없이 늘리는 것**”입니다.

새로운 모델(예: Claude 3.5 Sonnet에서 3.7 Sonnet, 혹은 GPT-5로의 전환)이 출시되면, 과거에 모델의 실수를 보완하기 위해 덧붙였던 수많은 방어적 프롬프트와 땜질식 워크어라운드 스킬들은 **오히려 새로운 모델의 최적 추론 경로를 방해하는 노이즈**로 변질됩니다.

앤드류 응은 2026년 9월 기고에서 이를 명확히 경고했습니다:

> *"Occasionally you will prune them when they are no longer necessary (such as when a new model obviates an old skill)."*

### 스킬 수명 주기 관리 수칙

1. **모델 메이저 업그레이드 시 스킬 감사(Audit)**:
   - 새로운 파운데이션 모델을 도입할 때 기존 스킬 목록을 전수 조사합니다.
   - 모델의 자체 추론 능력으로 기본 해결되는 문제(예: 간단한 파이썬 타입 힌팅, 기본적인 JSON 포맷팅 등)를 다루는 스킬은 즉각 보관(Archive)하거나 삭제합니다.
2. **스킬 250줄 법칙 (Simplicity Ceiling)**:
   - 하나의 `SKILL.md`가 250줄을 넘어가기 시작하면, 해당 스킬이 너무 많은 책임을 지고 있다는 신호입니다.
   - 도메인 지식은 `references/`로 분리하고, 절차는 3~5단계의 명확한 서브 태스크로 모듈화하십시오.
3. **증거 기반 주석(Annotation)**:
   - 스킬에 변경을 가할 때는 단순한 주관적 느낌이 아니라, 실제 에이전트 실패 로그와 회귀 테스트 데이터를 근거로 커밋해야 합니다.

## 8. 요약: 마스터를 위한 6가지 핵심 테제

1. **스킬은 폴더다**: 긴 프롬프트 대신, 메타데이터로 인덱싱되고 필요할 때만 호출되는 온디맨드 패키지(`SKILL.md`)를 구성하라.
2. **한 번 만들고 어디서나 구동하라**: 특정 벤더의 전유물이 아닌 오픈 표준 규격을 따라 IDE와 CLI를 넘나드는 이식성을 확보하라.
3. **삼위일체를 구분하라**: 스킬(절차와 지식), MCP(도구와 리소스), 서브에이전트(격리 실행)의 경계를 명확히 나눠 설계하라.
4. **최신 지식을 주입하고 공유하라**: Context Hub처럼 모델의 지식 단절을 메우고, 실행 결과를 주석으로 남겨 다음 에이전트에게 전달하라.
5. **바이브 코딩을 스펙으로 통제하라**: 빠르지만 깨지기 쉬운 직관 대신, 명세-계획-검증 루프를 스킬로 묶어 팀의 소프트웨어 품질을 수호하라.
6. **주기적으로 가지치기하라**: 모델이 발전하여 기본으로 해낼 수 있게 된 옛 지식은 과감히 도려내어 컨텍스트의 순도를 유지하라.
