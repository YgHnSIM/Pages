가비지 컬렉션 심화 분석: 수동 관리에서 마크 앤 스윕(Mark & Sweep)까지

킹스 칼리지 런던 Laurence Tratt 교수의 Computerphile 강의를 바탕으로, 왜 인간의 기억력에 기댄 수동 메모리 제어가 한계에 부딪혔는지, 그리고 "나를 몇 명이 가리키는가"에서 "루트로부터 나에게 닿을 수 있는가"로 질문을 바꾼 마크 앤 스윕(Mark & Sweep) 알고리즘이 현대 프로그래밍 언어의 메모리 관리를 어떻게 완성했는지 인터랙티브 시뮬레이션과 함께 해부합니다.

Core Thesis • 핵심 논증 구조

자동 메모리 관리의 역사는 곧 "질문을 바꾸는 과정"이다

프로그램이 실행 중에 메모리를 빌려 쓰고 반납하는 일은 단순해 보이지만, 수십 년간 소프트웨어 공학에서 가장 치명적인 버그와 보안 취약점의 온상이었습니다. 이 글은 메모리 관리가 발전해 온 세 단계의 패러다임을 하나의 일관된 논증 흐름으로 추적합니다.

STAGE 01 · 수동 관리 (C)
"내가 언제 다 썼는가?"

개발자가 malloc과 free로 직접 수명을 결정합니다. 최고 성능을 내지만 메모리 누수, Use-After-Free, Double Free라는 3대 재앙을 피하기 어렵습니다.

STAGE 02 · 참조 횟수 계산
"나를 몇 명이 가리키는가?"

객체마다 참조 카운터를 두어 count == 0이 되는 순간 즉시 회수합니다. 직관적이지만 순환 참조(Circular Reference) 덩어리를 스스로 회수하지 못합니다.

STAGE 03 · 마크 앤 스윕 GC
"루트에서 닿을 수 있는가?"

국소적 카운터 대신 스택·전역 변수 등 루트(Root Set)에서 출발해 그래프 탐색으로 생존 여부를 판별합니다. 고립된 순환 참조까지 완벽히 청소합니다.

PART 01 동적 할당과 운영체제 생태계

1. 왜 메모리를 처음부터 미리 정해 둘 수 없을까?

1.1 실행 전에는 알 수 없는 세계: 정적 할당의 한계

컴파일러가 프로그램을 기계어로 번역할 때, 모든 변수의 크기를 미리 알 수 있다면 메모리 관리는 놀라울 만큼 단순할 것입니다. 그러나 현실의 소프트웨어는 실행되기 전까지 사용자가 어떤 데이터를 입력할지 전혀 예측할 수 없습니다.

  • 이미지 편집기: 사용자가 100×100 픽셀짜리 작은 아이콘을 열지, 8K 해상도의 수백 메가바이트짜리 원본 사진 20장을 동시에 열어 레이어를 합성할지 미리 알 수 없습니다.
  • 웹 브라우저: 텍스트만 있는 가벼운 문서를 띄울 때와 수천 개의 DOM 노드 및 고화질 비디오 스트림이 포함된 웹앱을 실행할 때 필요한 메모리는 수백 배 차이 납니다.
  • 전자상거래 장바구니: 사용자가 물건을 1개 담을지 500개 담을지, 혹은 담았다가 다시 삭제할지는 오직 런타임(Runtime, 실행 시간)에만 결정됩니다.

따라서 프로그램은 실행 도중 데이터가 늘어날 때마다 운영체제(OS) 및 언어 런타임의 힙(Heap) 영역에 필요한 만큼 메모리를 요청하여 할당받고, 작업이 끝나면 이를 다시 반납하는 동적 메모리 할당(Dynamic Memory Allocation) 모델을 사용해야만 합니다.

1.2 운영체제 위의 "좋은 시민(Good Citizen)" 딜레마

그렇다면 왜 프로그램이 시작할 때 아예 시스템의 여유 메모리를 수십 기가바이트씩 미리 독점해 두지 않을까요? 현대 컴퓨터는 수십~수백 개의 프로세스가 제한된 물리 RAM을 나누어 쓰는 멀티태스킹 환경이기 때문입니다. Laurence Tratt 교수는 이를 "좋은 시민(Good Citizen)의 균형"이라는 비유로 설명합니다.

"좋은 시민인 프로세스는 자신이 당장 처리해야 할 작업에 필요한 만큼만 메모리를 요청해 사용하고, 그 작업이 끝나는 즉시 메모리를 반납하여 컴퓨터 안의 다른 프로세스들이 자원을 쓸 수 있게 양보해야 합니다."

📊 프로세스 메모리 파동 비교: 좋은 시민 vs 나쁜 시민

작업 단계에 따라 동적 메모리를 할당·반납할 때와 반납을 잊었을 때(누수)의 시스템 RAM 점유율 비교

✅ 정상 반납 시: 사진 편집이나 필터 연산이 끝날 때마다 임시 버퍼를 즉시 반납하므로 메모리 사용량이 파도처럼 오르내리며 안정적인 수준을 유지합니다.

PART 02 명시적 제어의 양날의 검

2. 수동 관리의 시대: malloc과 free, 그리고 세 가지 고전적 재앙

2.1 두 개의 기본 동작으로 이루어진 계약

C 언어를 비롯한 전통적인 시스템 프로그래밍 언어에서는 개발자가 직접 메모리 할당기(Allocator)와 계약을 맺습니다. 이 계약은 단 두 개의 기본 함수로 요약됩니다.

void* ptr = malloc(32 * 1024); 할당 (Allocate)

"나에게 32KB(32,768바이트)의 여유 메모리 블록을 찾아 빌려달라." 할당기는 힙의 빈 공간(Free List)에서 적당한 블록을 찾아 시작 메모리 주소(포인터)를 반환합니다.

free(ptr); 반납 (Deallocate)

"이 주소(ptr)가 가리키는 메모리 블록을 다 썼으니 반납한다." 할당기는 해당 영역을 다시 빈 공간 목록에 등록해 다른 malloc 요청이 재사용할 수 있게 합니다.

2.2 인간이기에 범하는 세 가지 치명적 오류 (The 3 Deadly Sins)

코드가 수십만 줄로 늘어나고 조건문, 예외 처리, 비동기 콜백이 얽히기 시작하면 "정확히 모든 실행 경로에서, 단 한 번씩만, 더 이상 쓰지 않는 시점에 free를 호출한다"는 규칙을 지키는 것은 사실상 불가능에 가까워집니다. 여기서 세 가지 고전적 재앙이 탄생합니다. 아래 탭을 클릭해 각 오류가 실제 메모리 주소 공간에서 어떤 참사를 일으키는지 확인해 보세요.

자원 고갈형 버그

free() 호출을 잊어버린 경우

void process_image() {
  uint8_t* buf = malloc(32 * 1024); // 0x4A00 할당
  if (header_invalid(buf)) {
    return; // ❌ 조기 리턴하며 free(buf) 누락!
  }
  free(buf);
}

함수에서 조기 리턴하거나 포인터 변수 buf가 스코프를 벗어나 사라지면, 힙의 0x4A00 블록은 주소를 아는 변수가 없는데도 할당 상태로 남습니다. 누수가 누적되면 시스템 RAM이 바닥나 디스크 스왑(Swap)으로 급격히 느려지거나 OS의 OOM Killer에 의해 강제 종료됩니다.

HEAP MEMORY STATE (Address 0x4A00)

💡 왜 Use-After-Free와 Double Free가 특히 위험한가요?
Laurence Tratt 교수가 비유했듯, 이중 반환(Double Free)은 "내가 이미 판 집을 부동산에 또 팔아넘겨서, 그 집을 새로 사서 입주해 살던 고담시의 선량한 시민(다른 정상 객체)이 갑자기 철거반에 의해 길거리로 내쫓기는 상황"과 같습니다. 특히 해제된 주소에 보안 인증 정보나 함수 포인터가 새로 들어왔을 때 예전 포인터로 값을 덮어쓰면 심각한 원격 코드 실행(RCE) 보안 취약점이나 타 데이터 오염으로 직결됩니다. Microsoft와 Google 크롬 보안팀의 통계에 따르면 전체 심각한 보안 취약점의 약 70%가 이러한 수동 메모리 안전성 오류에서 비롯됩니다.

PART 03 자동화의 첫 번째 시도

3. 참조 횟수 계산(Reference Counting): 직관적인 자동화와 순환 참조의 덫

3.1 왜 운영체제(OS)가 아니라 프로그래밍 언어가 나섰는가?

인간에게 free()를 맡기는 것이 위험하다면, 왜 운영체제가 알아서 안 쓰는 메모리를 회수해 주지 않을까요? 운영체제 입장에서는 프로세스의 메모리가 그저 수십억 개의 바이트 배열(0x00~0xFF)로 보일 뿐입니다. 어떤 8바이트 숫자가 단순한 정수 데이터(long)인지, 아니면 다른 힙 객체를 가리키는 메모리 주소(포인터)인지 OS 커널은 구분할 수 없습니다.

반면 프로그래밍 언어의 컴파일러와 런타임(Runtime)은 변수의 타입, 스코프(Scope), 객체 간 참조 구조를 정확히 알고 있습니다. 그래서 1960년 조지 콜린스(George E. Collins)가 제안한 참조 횟수 계산(Reference Counting)을 시작으로, 메모리 관리의 책임은 인간 개발자에서 언어 런타임으로 넘어오게 됩니다.

3.2 원리: "나를 가리키는 화살표가 몇 개인가?"

참조 횟수 계산의 규칙은 매우 단순합니다. 모든 힙 객체 헤더에 참조 카운터(ref_count)라는 정수 칸을 하나 추가합니다.

  • 새로운 변수나 다른 객체의 필드가 이 객체를 가리키면 ref_count += 1
  • 가리키던 변수가 다른 값으로 덮어써지거나 함수가 종료되어 스코프를 벗어나면 ref_count -= 1
  • ref_count == 0이 되는 그 즉시, 아무도 이 객체를 참조하지 않는다고 판단하여 메모리를 해제합니다.

3.3 참조 횟수 계산이 치러야 하는 네 가지 대가

참조 카운팅은 객체가 쓸모없어지는 즉시 회수된다는 큰 장점이 있어 오늘날에도 Python(CPython의 기본 메모리 관리자), Swift/Objective-C(ARC), C++(std::shared_ptr), Rust(Rc/Arc) 등에서 널리 쓰입니다. 하지만 그 대가로 네 가지 무거운 한계를 안고 있습니다.

COST 01 · 구현 복잡성
컴파일러·런타임의 엄격한 장부 관리

모든 포인터 대입, 인자 전달, 스코프 이탈 시점마다 증감 코드를 한 치의 오차도 없이 삽입해야 합니다. 런타임 내부 코드에서 실수가 나면 즉시 Use-After-Free나 누수로 이어집니다.

COST 02 · 공간 오버헤드
모든 객체마다 붙는 카운터 필드

극단적으로 수억 개의 객체가 한 객체를 가리킬 수도 있으므로, 각 객체 헤더마다 워드 크기(64비트 기준 8바이트, 최소 4바이트)의 카운터 공간이 추가로 소비됩니다.

COST 03 · 시간 및 멀티스레드 오버헤드
단순 대입조차 메모리 쓰기 연산을 유발

p = q 한 줄을 실행할 때도 이전 객체의 카운터를 깎고 새 객체의 카운터를 올려야 합니다. 특히 멀티스레드 환경에서는 원자적 연산(Atomic Increment/Decrement)과 CPU 캐시 라인 무효화가 발생해 처리량이 크게 저하됩니다.

COST 04 · 구조적 아킬레스건
순환 참조 (Circular Reference) 회수 불능

객체 A가 B를 가리키고 B가 다시 A를 가리키면(A ↔ B), 외부의 모든 스택 변수가 연결을 끊어도 서로가 서로의 카운터를 1로 지탱해 주어 영원히 0이 되지 않는 고립된 섬(Isolated Island)이 됩니다.

🔄 순환 참조의 함정 직접 실험하기

스택 변수 root가 끊어졌을 때 일반 연결과 순환 참조(Node A ↔ Node B)의 참조 카운트 비교

상태 설명: 스택의 root 변수가 A를 가리키고(ref_cnt=1), A가 B를 가리킵니다(ref_cnt=1). 이 상태에서 root = null이 되면 A와 B는 차례대로 카운트가 0이 되어 정상 회수됩니다. '2. 순환 고리 생성' 버튼을 눌러보세요!
PART 04 추적 기반 가비지 컬렉션(Tracing GC)의 핵심

4. 마크 앤 스윕(Mark & Sweep): "루트로부터 닿을 수 있는가?"

4.1 국소적 카운터에서 전역적 도달 가능성(Reachability)으로

1960년 존 매카시(John McCarthy)가 Lisp 언어를 위해 고안한 마크 앤 스윕(Mark & Sweep) 알고리즘은 참조 횟수 계산이 빠졌던 함정을 정면으로 돌파합니다. 흔히 학술 문헌과 현업에서 좁은 의미로 "가비지 컬렉션(Garbage Collection, GC)"이라 부를 때는 바로 이 마크 앤 스윕 계열의 추적 기반 가비지 컬렉션(Tracing GC)을 가리킵니다.

핵심 통찰은 질문을 완전히 바꾸는 데 있습니다. 각 객체에게 "너를 가리키는 화살표가 몇 개니?"라고 묻는 대신, "현재 실행 중인 프로그램의 출발점(Root)에서 시작해 포인터 사슬을 따라가면 저 객체에 도달할 수 있는가(Reachable)?"를 묻는 것입니다. 아무리 객체 A와 B가 서로를 백 번씩 참조하고 있더라도, 프로그램의 출발점(Root)에서 그 섬으로 건너가는 다리가 끊어졌다면 프로그램은 절대로 그 객체들을 다시 읽거나 쓸 수 없습니다. 즉, 도달 불가능(Unreachable)한 객체는 곧 가비지(Garbage)입니다.

4.2 루트 집합(Root Set)이란 무엇인가?

그렇다면 탐색의 출발점이 되는 루트(Roots)는 구체적으로 어디에 있는 변수들일까요? 가비지 컬렉터가 마크(Mark) 단계를 시작할 때 가장 먼저 스캔하는 Root Set은 다른 객체를 거치지 않고 코드에서 즉시 접근할 수 있는 네 가지 영역으로 구성됩니다.

ROOT 01
콜 스택 프레임 (Call Stack)

현재 실행 중인 모든 함수들의 지역 변수(Local Variables)와 매개변수(Parameters)

ROOT 02
CPU 레지스터 (Registers)

현재 스레드가 연산을 위해 CPU 레지스터에 올려둔 객체 참조 포인터

ROOT 03
전역·정적 변수 (Globals/Statics)

프로그램 종료 시까지 수명이 유지되는 모듈 전역 변수, 클래스 정적 필드, 싱글톤

ROOT 04
런타임·네이티브 핸들 (JNI 등)

C/C++ 네이티브 확장 코드나 VM 내부 시스템이 직접 붙잡고 있는 외부 참조

4.3 두 단계의 협주곡: Mark(표시)와 Sweep(청소), 그리고 삼색 추상화

평소에는 참조 횟수 계산처럼 매번 카운터를 증감하며 실행 속도를 깎아먹지 않고, 프로그램이 빠르게 메모리를 할당하며 달리게 둡니다. 그러다 힙의 여유 공간이 일정 임계치 아래로 떨어지면 가비지 컬렉터가 깨어나 Mark와 Sweep의 두 단계를 수행합니다.

PHASE 1 · MARK 시간 복잡도: O(살아있는 객체 수 + 간선 수)

루트에서 출발하는 그래프 탐색 (DFS / Worklist)

모든 루트 변수에서 출발하여 포인터를 따라가며 도달 가능한 모든 객체의 헤더에 마크 비트(mark = 1)를 켭니다. 이때 실제 GC 엔진은 삼색 마킹(Tri-color Marking) 추상화를 사용합니다:
• ⚪ White(백색): 아직 방문하지 않은 객체 (Mark 종료 시까지 백색이면 가비지 확정)
• 🟡 Grey(회색): 자신은 방문되어 마크되었으나, 자신이 가리키는 자식 객체들을 아직 다 확인하지 않아 탐색 대기열(Worklist)에 들어있는 객체
• 🟢 Black(흑색): 자신과 직속 자식들까지 모두 탐색을 마친 생존 확정 객체

PHASE 2 · SWEEP 시간 복잡도: O(전체 힙 크기)

전체 힙의 선형 스캔 및 일괄 회수

그래프 탐색(Mark)이 끝나 더 이상 회색(Grey) 노드가 남지 않으면, 가비지 컬렉터는 힙 메모리의 처음 주소부터 끝 주소까지 선형으로 훑습니다(Sweep).
• 마크가 없는(White) 객체: 루트에서 도달할 수 없는 가비지이므로 즉시 해제하여 자유 공간 연결 리스트(Free List)에 반환합니다.
• 마크가 있는(Black) 객체: 살아남은 객체이므로 그대로 보존하고, 다음 GC 주기를 위해 마크 상태를 초기화합니다.

4.4 표시는 메모리를 얼마나 쓰나: 객체 헤더의 1비트와 '불리언 플립(Boolean Flip)' 최적화

참조 횟수 계산에서는 객체마다 최소 32~64비트의 카운터 공간이 필요했습니다. 반면 마크 앤 스윕은 "루트에서 닿았는가, 아닌가"라는 예/아니오(Boolean)만 기록하면 되므로, 각 객체 헤더(Object Header)에 단 1비트(Mark Bit)만 있으면 충분합니다. 게다가 실제 가상머신(JVM, V8 등)에서는 객체 크기가 8바이트 단위로 정렬(Alignment)되면서 남는 하위 여유 비트에 이 1비트를 숨겨 넣기 때문에 추가 메모리 오버헤드가 사실상 0바이트에 가깝습니다.

여기서 한 가지 날카로운 질문이 등장합니다: "Sweep이 끝난 뒤, 살아남은 객체들에 켜져 있는 mark = 1 비트를 다음 GC 주기 전에 다시 0으로 리셋하려면 또 시간을 써야 하지 않나요?"

이를 해결하는 우아한 기법이 바로 불리언 플립(Boolean Flip, 비트 의미 뒤집기)입니다. 살아남은 객체의 비트를 매번 초기화하는 대신, 가비지 컬렉터가 전역 변수 하나(ALIVE_BIT_MEANING)만 들고 있다가 GC 주기가 끝날 때마다 '살아있음(Marked)'을 뜻하는 비트 값(1 또는 0)의 해석을 정반대로 뒤집는 것입니다!

⚡ 불리언 플립(Boolean Flip) 인터랙티브 토글

살아남은 객체들의 비트를 0으로 일일이 지우지 않고, 사이클의 기준 비트만 1 ↔ 0으로 뒤집어 초기화 비용을 O(1)로 만듭니다.

CURRENT GC CYCLE
홀수 주기 (Cycle #1)
현재 생존 기준: mark_bit == 1 이면 생존!
SURVIVING OBJECT A (새 주기 시작 직후)
헤더 저장 비트: 0 미방문 (Unmarked)

이전 주기를 통과하며 비트가 그대로 남아있지만, 새 주기에서는 기준이 바뀌었으므로 별도의 초기화 없이도 자동으로 '미방문' 상태가 됩니다!

MARK 단계에서 방문 시 동작
obj.mark_bit = 1 로 기록

Sweep 후에도 비트 초기화 루프를 돌릴 필요가 없어 힙 스캔 오버헤드가 절감됩니다.

PART 05 현실 세계의 한계와 현대 GC의 진화

5. GC가 있어도 왜 메모리가 새고 멈칫거릴까? (잊힌 루트, 단편화, Stop-The-World)

마크 앤 스윕은 수동 관리의 Use-After-Free와 Double Free를 원천 차단하고 순환 참조까지 깔끔히 해결했습니다. 그렇다면 마크 앤 스윕 언어를 쓰면 메모리 걱정은 완전히 끝난 것일까요? 현업 엔지니어들이 겪는 세 가지 현실적 문제를 통해 GC의 한계와 진화 방향을 짚어봅니다.

5.1 "잊힌 루트(Forgotten Roots)"와 왜 '껐다 켜면' 고쳐지는가

Java, JavaScript, Python으로 작성된 서버나 웹앱에서도 여전히 메모리 누수(Memory Leak)가 발생합니다. 왜일까요? 컴퓨터과학에서는 쓰레기 객체를 두 종류로 구분합니다.

  • 구문적 가비지 (Syntactic Garbage): 루트에서 포인터 경로로 도달 불가능한 객체. 마크 앤 스윕이 100% 완벽하게 회수합니다.
  • 의미적 가비지 (Semantic Garbage): 루트에서 여전히 도달 가능하지만, 개발자의 논리상 앞으로 다시는 읽지 않을 객체. 어떤 자동 GC도 프로그램의 미래 의도를 독심술로 읽을 수 없으므로 절대 회수하지 못합니다!

가장 흔한 원인은 잊힌 루트(Forgotten Root)입니다. 예를 들어 전역 Map이나 캐시 리스트에 데이터를 계속 넣기만 하고 삭제(Eviction)하지 않거나, DOM 요소를 지웠는데 전역 이벤트 리스너가 그 요소를 참조하고 있는 경우입니다. 단 하나의 잊힌 루트 화살표가 남아 있으면, 그 끝에 매달린 수백 메가바이트짜리 객체 그래프 전체가 매번 Mark 단계에서 성실하게 체크 표시를 받아 살아남습니다.

그렇다면 왜 프로그램을 껐다 켜면(프로세스 재시작) 감쪽같이 해결될까요?
개별 객체를 하나씩 추적하던 언어 런타임과 달리, 운영체제(OS) 커널은 프로세스 단위로 가상 주소 공간(Virtual Address Space)의 페이지 테이블을 관리합니다. 프로세스가 종료되는 순간 OS는 그 안에 있던 잊힌 루트든 순환 참조든 상관하지 않고 해당 프로세스에 매핑된 물리 RAM 프레임 전체를 단번에 회수하기 때문입니다.

5.2 스위스 치즈가 된 힙: 메모리 단편화(Fragmentation)와 Compaction

순수한 마크 앤 스윕에는 또 하나의 물리적 약점이 있습니다. 살아있는 객체는 원래 자리에 그대로 둔 채 중간중간의 가비지만 지우다 보면(Sweep), 힙 메모리가 구멍 뚫린 스위스 치즈처럼 잘게 쪼개지는 외부 단편화(External Fragmentation)가 발생합니다.

아래 시뮬레이터에서 확인하듯, 힙 전체의 빈칸 합계는 6칸(24KB)으로 충분한데도, 빈칸들이 2칸씩 흩어져 있어 연속된 4칸(16KB)짜리 배열 할당 요청이 들어오면 할당에 실패(OutOfMemoryError)합니다. 이를 해결하기 위해 현대 GC는 살아남은 객체들을 힙의 한쪽 끝으로 차곡차곡 밀어 모으고 포인터 주소를 일괄 갱신하는 컴팩션(Compaction, Mark-Sweep-Compact) 단계를 결합합니다.

5.3 Stop-The-World(STW)와 세대별 가설(Generational Hypothesis)로의 도약

만약 가비지 컬렉터가 루트에서부터 객체 그래프를 한창 탐색(Mark)하고 있는데, 동시에 사용자 프로그램(Mutator)이 뒤에서 포인터 연결을 이리저리 바꿔버리면 어떻게 될까요? 방금 살아있다고 판단해야 할 객체를 미처 마크하지 못해 살아있는 객체를 Sweep에서 지워버리는 대참사가 일어납니다.

그래서 고전적인 마크 앤 스윕은 GC가 도는 동안 애플리케이션의 모든 작업 스레드를 일시 정지시키는 Stop-The-World(STW) 방식을 택합니다. 힙이 수십 기가바이트로 커지면 이 멈춤 시간이 수백 밀리초에서 수 초에 달해 게임 프레임이 끊기거나 금융·웹 서버 응답 지연이 발생합니다. 이를 극복하기 위해 현대 런타임(JVM의 G1/ZGC, V8, Go, .NET 등)은 마크 앤 스윕 위에 세 가지 핵심 기법을 얹어 진화했습니다.

EVOLUTION 01
세대별 GC (Generational GC)

"대부분의 객체는 생성된 직후 금방 죽는다(Weak Generational Hypothesis)." 힙을 신생(Young) 영역과 고령(Old) 영역으로 나누어, 금방 죽는 작은 Young 영역만 자주 빠르게 청소(Minor GC)합니다.

EVOLUTION 02
점진적·동시성 마킹 (Concurrent GC)

프로그램을 통째로 멈추는 대신, 쓰기 장벽(Write Barrier)을 통해 애플리케이션이 포인터를 바꿀 때마다 회색(Grey) 큐에 기록하게 하여 프로그램 실행과 마킹을 동시에 수행합니다.

EVOLUTION 03
하이브리드 조합 (RC + Cycle GC)

CPython처럼 평소에는 참조 카운팅으로 90% 이상의 객체를 즉시 회수하고, 컨테이너 객체들 사이에 생기는 순환 참조만 주기적인 추적(Tracing) 알고리즘으로 잡아내는 절충안입니다.

(Use-After-Free / Double Free)		 발생 가능 (치명적 보안 취약점) 런타임이 원천 차단 런타임이 원천 차단
순환 참조 (A ↔ B) 개발자가 순서를 맞춰 직접 해제해야 함 자체 회수 불가 (weak 참조나 보조 GC 필요) 루트에서 끊기면 자연스럽게 일괄 회수
객체당 공간 오버헤드 할당기 블록 헤더만 존재 객체마다 정수 카운터(4~8B) 필수 객체당 1비트 (Boolean Flip 적용 시 최소)
런타임 성능 특성 런타임 오버헤드 최소, 예측 가능 포인터 변경마다 상시 증감 비용 분산 평소엔 최고 속도, GC 시 일시 정지(Pause) 발생
대표 언어 및 환경 C, C++(Raw), Zig (cf. Rust는 컴파일 타임 소유권) Swift(ARC), Objective-C, C++ shared_ptr Java(JVM), JS(V8), Go, C#, Python(보조 Cycle GC)

🎯 개발자에게 남는 마지막 질문: "내가 어떤 참조를 붙잡고 있는가?"

가비지 컬렉션은 개발자의 어깨에서 "이 객체를 정확히 언제 파괴할 것인가?"라는 무거운 짐을 내려주었습니다. 그러나 그 대신 개발자의 책임을 "더 이상 쓰지 않는 객체로 향하는 루트 참조(전역 컬렉션, 캐시, 클로저, 리스너)를 제때 끊어주었는가?"라는 아키텍처적 질문으로 이동시켰습니다. 도달 가능성(Reachability)의 원리를 이해하는 순간, GC는 더 이상 알 수 없는 블랙박스가 아니라 내 코드의 참조 그래프를 따라 움직이는 투명하고 든든한 동반자가 됩니다.
