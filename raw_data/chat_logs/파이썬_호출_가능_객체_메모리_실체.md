파이썬 인터프리터가 obj(1, 2) 형태의 호출을 만났을 때의 내부 처리 과정입니다.

[바이트코드: CALL]
       │
       ▼
[CPython C-API: PyObject_Call(callable, args, kwargs)]
       │
       ▼
[tp_call 슬롯 검사: Py_TYPE(callable)->tp_call]
       │
       ├─► (1) function 객체인 경우: PyFunction_Call() 진입 -> 스택 프레임 생성
       └─► (2) 일반 클래스 인스턴스인 경우: type(obj).__call__(obj, 1, 2) 실행

### 🤖 Assistant

좋습니다. 이 부분은 **“파이썬에서 `()`가 단순한 문법이 아니라, 객체의 호출 프로토콜(call protocol)을 발동시키는 것”**으로 이해하면 한 단계 깊어집니다.

다만 먼저 제시하신 그림에는 **현대 CPython 기준으로 중요한 수정점이 하나** 있습니다.

> `CALL → PyObject_Call → tp_call`이라는 설명은 개념적으로는 맞지만, 최신 CPython의 실제 바이트코드 실행 경로는 버전별로 `CALL`, `CALL_FUNCTION_EX`, `vectorcall` 등을 거치며, 일반적인 함수 호출에서 항상 `PyObject_Call()`이 직접 호출되는 것은 아닙니다.

즉, **개념적 호출 모델**과 **실제 CPython 최적화 경로**를 분리해서 이해해야 합니다.

# 1. 가장 먼저 핵심부터

파이썬에서

```python
obj(1, 2)
```

를 보면 우리는 보통

> "`obj`라는 함수를 인자 1, 2와 함께 실행한다."

라고 생각합니다.

하지만 인터프리터의 관점에서는 더 정확히:

> **"`obj`가 호출 가능한 객체(callable)인가? 그렇다면 그 객체가 제공하는 호출 프로토콜을 실행하라."**

입니다.

따라서 다음이 모두 가능합니다.

```python
def f(a, b):
    return a + b

f(1, 2)
```

여기서 `f`는 함수 객체입니다.

그런데:

```python
class A:
    def __call__(self, a, b):
        return a + b

obj = A()

obj(1, 2)
```

여기서 `obj`는 **함수가 아닙니다.**

그럼에도:

```python
obj(1, 2)
```

가 됩니다.

왜냐하면 `A`의 인스턴스인 `obj`가 **호출 가능하도록 설계되어 있기 때문**입니다.

# 2. `()`의 본질: 호출 연산자

다음 두 코드를 비교합시다.

```python
obj
```

와

```python
obj(1, 2)
```

첫 번째는 단순히 `obj`라는 객체를 가져옵니다.

두 번째는 **call operation**을 요청합니다.

개념적으로:

```text
obj(1, 2)
     │
     ▼
"obj야, 너 호출 가능하니?"
     │
     ▼
호출 프로토콜 실행
     │
     ▼
결과 객체 반환
```

여기서 중요한 점은:

## `obj`가 반드시 함수일 필요가 없습니다.

호출 가능하기만 하면 됩니다.

예:

```python
f(1, 2)
```

```python
A()(1, 2)
```

```python
callable_object(1, 2)
```

모두 같은 **"호출(call)"이라는 추상 연산**을 사용합니다.

# 3. Python 객체를 C 구조체 관점에서 보면 갑자기 이해된다

CPython은 Python 객체를 내부적으로 C 구조체 형태로 관리합니다.

개념적으로 객체에는 이런 정보가 있다고 생각하면 됩니다.

```c
typedef struct _object {
    Py_ssize_t ob_refcnt;
    PyTypeObject *ob_type;
} PyObject;
```

핵심은 이것입니다.

```c
ob_type
```

즉,

> **이 객체는 무슨 타입인가?**

를 가리킵니다.

Python으로 보면:

```python
type(obj)
```

입니다.

예:

```python
class A:
    pass

obj = A()
```

그러면:

```python
type(obj)
```

는

```text
A
```

입니다.

C 내부적으로는 대략:

```text
obj
 │
 ▼
PyObject
 │
 └── ob_type ──────► A라는 PyTypeObject
```

라는 관계입니다.

# 4. 그런데 타입에는 "어떻게 호출할 것인가?" 정보가 있다

여기서 `PyTypeObject`가 등장합니다.

CPython의 타입 객체에는 수많은 슬롯(slot)이 있습니다.

개념적으로:

```c
typedef struct _typeobject {
    ...
    unaryfunc tp_call;
    ...
} PyTypeObject;
```

중요한 것이:

```c
tp_call
```

입니다.

이것을 아주 쉽게 표현하면:

> **"이 타입의 객체가 `()`로 호출되었을 때 무엇을 실행할 것인가?"**

입니다.

따라서:

```text
obj(1, 2)
```

를 내부적으로 개념화하면:

```text
obj
 │
 ▼
PyObject
 │
 ▼
Py_TYPE(obj)
 │
 ▼
PyTypeObject
 │
 ▼
tp_call
 │
 ▼
호출 구현
```

입니다.

# 5. `__call__`은 이 메커니즘의 Python 레벨 표현이다

예를 들어:

```python
class A:
    def __call__(self, x, y):
        return x + y
```

그리고:

```python
obj = A()
```

이제:

```python
obj(10, 20)
```

이 가능합니다.

우리가 Python 레벨에서 볼 때는:

```python
obj.__call__(10, 20)
```

와 비슷한 의미를 갖습니다.

즉:

```text
obj(10, 20)
       │
       ▼
obj의 호출 프로토콜
       │
       ▼
A.__call__(obj, 10, 20)
```

입니다.

여기서 아주 중요한 부분이 있습니다.

# 6. `self`가 왜 들어가는가?

다음 코드:

```python
class A:
    def __call__(self, x, y):
        return x + y
```

에서:

```python
obj = A()
obj(10, 20)
```

를 호출하면 `A.__call__()`에는 실제로:

```text
self = obj
x = 10
y = 20
```

가 전달됩니다.

개념적으로:

```python
A.__call__(obj, 10, 20)
```

입니다.

따라서 사용자가 제시한:

```text
type(obj).__call__(obj, 1, 2)
```

라는 표현은 **Python 레벨의 이해를 위해 상당히 좋은 모델**입니다.

# 7. 여기서 "클래스도 객체"라는 사실이 폭발적으로 중요해진다

이제 더 깊이 들어가겠습니다.

Python에서는:

```python
class A:
    ...
```

로 만든 `A` 역시 객체입니다.

즉:

```python
A
```

도 객체입니다.

그리고:

```python
type(A)
```

를 해보면 일반적으로:

```python
type
```

이 나옵니다.

따라서 구조는:

```text
obj
 │
 ▼
A의 인스턴스
 │
 ▼
type(obj) == A
```

그리고:

```text
A
 │
 ▼
클래스 객체
 │
 ▼
type(A) == type
```

입니다.

이것이 Python 객체 모델의 핵심입니다.

# 8. 그러면 `A()`는 무엇인가?

다음 코드를 봅시다.

```python
class A:
    pass

obj = A()
```

여기서:

```python
A()
```

가 호출입니다.

그런데 `A`는 함수가 아닙니다.

`A`는 **클래스 객체**입니다.

그럼 왜 호출할 수 있을까요?

바로 `A`의 타입인 `type`이 호출 가능하기 때문입니다.

개념적으로:

```text
A()
 │
 ▼
A라는 객체
 │
 ▼
type(A) == type
 │
 ▼
type의 호출 메커니즘
 │
 ▼
A 인스턴스 생성
```

입니다.

즉:

> **클래스를 호출한다는 것은 결국 클래스 객체에 대한 호출이다.**

# 9. 여기서 두 종류의 호출을 구별해야 한다

이제 매우 중요한 구분입니다.

## 경우 ① 함수 호출

```python
def add(a, b):
    return a + b

add(1, 2)
```

여기서:

```text
add
 ↓
function object
 ↓
function 호출 메커니즘
 ↓
Python 함수 실행
```

입니다.

## 경우 ② 인스턴스 호출



입니다.

둘 다:

```python
obj(1, 2)
```

라는 동일한 Python 문법을 사용하지만 **실제 내부 구현은 다를 수 있습니다.**

# 11. `tp_call`을 아주 중요한 개념으로 이해하라

이제 CPython 내부 관점으로 들어갑니다.

어떤 객체를:

```python
obj(...)
```

형태로 호출하면 CPython은 결국 **호출 가능한 객체인지 판단하고 호출 구현을 찾아 실행**해야 합니다.

전통적인 C API 모델에서는 다음과 같은 형태를 생각할 수 있습니다.

```c
PyObject_Call(callable, args, kwargs)
```

개념적으로:

```text
PyObject_Call()
      │
      ▼
callable의 타입 확인
      │
      ▼
Py_TYPE(callable)
      │
      ▼
tp_call
      │
      ▼
실제 호출 구현
```

입니다.

따라서:

```c
Py_TYPE(callable)->tp_call
```

가 핵심적인 연결고리입니다.

# 12. 그런데 최신 CPython에서는 `vectorcall`이 중요하다

여기서 현대 CPython을 이해하려면 반드시 하나를 더 알아야 합니다.

바로:

> **vectorcall**

입니다.

과거의 일반적인 호출 모델을 단순화하면:

```text
obj(...)
   ↓
인자들을 tuple로 구성
   ↓
kwargs 구성
   ↓
PyObject_Call()
   ↓
tp_call
```

같은 형태로 이해할 수 있습니다.

그런데 함수 호출은 프로그램에서 엄청나게 많이 발생합니다.

예:

```python
f(a, b)
```

가 수억 번 실행될 수도 있습니다.

매번 인자를 tuple로 만들고 dictionary를 만들고 다시 해석한다면 상당히 비쌉니다.

그래서 CPython은 호출 비용을 줄이기 위해 **vectorcall 호출 규약**을 적극적으로 사용합니다.

개념적으로:

```text
기존 방식

a, b
 ↓
tuple 생성
 ↓
kwargs dictionary
 ↓
호출
```

보다:

```text
vectorcall

a
b
│
├── 직접 인자 배열
│
▼
호출 함수
```

처럼 불필요한 객체 생성과 포장을 줄이는 방향입니다.

# 13. 따라서 실제 현대 CPython의 그림은 이렇게 보는 것이 좋다

사용자가 처음 제시한 그림을 현대적으로 보완하면:

```text
Python source
     │
     │
     ▼
obj(1, 2)
     │
     ▼
Compiler
     │
     ▼
Bytecode
     │
     ▼
CALL 계열 opcode
     │
     ▼
CPython call machinery
     │
     ├───────────────┐
     │               │
     ▼               ▼
vectorcall        일반 호출 경로
     │               │
     │               ▼
     │             tp_call
     │
     ▼
callable의 실제 구현
     │
     ├── Python function
     ├── type/class
     ├── Python instance with __call__
     ├── builtin function
     └── 기타 callable
```

이것이 훨씬 정확한 정신 모델입니다.

# 14. Python 함수도 결국 객체다

이 문장을 반드시 기억하십시오.

```python
def f():
    pass
```

를 실행했다고 해서 `f`가 특별히 "함수가 아닌 어떤 실행 명령"인 것은 아닙니다.

`f`는 **function object**입니다.

즉:

```python
type(f)
```

는 대략:

```python
function
```

입니다.

그리고 이 function object 자체가 callable입니다.

따라서:

```python
f()
```

는:

```text
f라는 객체
 ↓
호출 가능
 ↓
function 호출 구현

Python 코드 실행
```

입니다.

# 15. 여기서 프레임(frame)이 등장한다

Python 함수가 실행되면 중요한 내부 객체가 등장합니다.

바로:

```text
frame
```

입니다.

예:

```python
def add(a, b):
    c = a + b
    return c

add(10, 20)
```

호출되면 개념적으로 실행 환경이 필요합니다.

```text
add
 │
 ▼
function object
 │
 ▼
function 실행
 │
 ▼
frame / execution state
 │
 ├── local variables
 │      ├── a = 10
 │      ├── b = 20
 │      └── c = 30
 │
 ├── instruction position
 │
 ├── evaluation stack
 │
 └── code object
```

그리고 Python bytecode가 이 실행 상태를 이용해서:

```python
c = a + b
```

등을 실행합니다.

# 16. `function object`와 `code object`를 구별해야 한다

이 부분은 고급 Python에서 매우 중요합니다.

다음:

```python
def add(a, b):
    return a + b
```

에서 내부적으로 대략 두 개념을 구별할 수 있습니다.

### Function object

```text
function
```

실행에 필요한 여러 정보와 연결되어 있습니다.

### Code object

```text
code
```

실제로 컴파일된 bytecode 및 코드 메타데이터를 담습니다.

개념적으로:

```text
function object
      │
      ├── code object
      │      │
      │      └── bytecode
      │
      ├── globals
      ├── defaults
      ├── annotations
      └── 기타 상태
```

입니다.

그래서 함수 호출은 단순히:

> "코드를 실행한다."

가 아닙니다.

보다 정확하게는:

> **function object가 가진 실행 정보를 이용하여 새로운 실행 상태를 구성하고 코드를 평가한다.**

입니다.

# 17. 그런데 `__call__`은 어디에서 찾는가?

이것도 매우 중요합니다.

```python
class A:
    def __call__(self, x):
        return x * 2
```

그리고:

```python
obj = A()
```

일 때:

```python
obj(10)
```

을 실행합니다.

Python 레벨에서 단순화하면:

```python
obj.__call__(10)
```

처럼 생각할 수 있습니다.

그런데 CPython의 special method lookup은 일반적인:

```python
obj.__getattribute__("__call__")
```

와 완전히 동일한 방식으로 이해하면 안 됩니다.

`__call__`, `__add__`, `__len__`, `__iter__` 같은 **special method**는 타입의 슬롯과 연결되어 특별한 호출 경로를 갖습니다.

즉:

```text
obj(10)
```

은 단순히:

```text
obj.__dict__["__call__"]
```

를 찾아 실행하는 구조가 아닙니다.

이 차이가 매우 중요합니다.

# 18. 그래서 이런 실험을 해보면 좋다

```python
class A:
    def __call__(self, x):
        return x * 2

obj = A()

print(obj(10))
```

결과:

```text
20
```

그런데:

```python
obj.__call__
```

을 출력해보면 bound method 형태가 나옵니다.

즉:

```text
obj.__call__
```

은 Python 레벨에서 method binding이 일어난 결과입니다.

개념적으로:

```text
A.__call__
     │
     ▼
function descriptor
     │
     ▼
obj에 binding
     │
     ▼
bound method
```

입니다.

---

# 19. `obj(10)`과 `obj.__call__(10)`은 "같아 보이지만" 내부적으로 동일한 경로라고 단정하면 안 된다

이것은 아주 중요한 고급 포인트입니다.

```python
obj(10)
```

은 **call syntax**입니다.

반면:

```python
obj.__call__(10)
```

은:

1. `__call__`이라는 attribute를 조회하고
2. 그 결과 얻은 callable을
3. 다시 호출

하는 것입니다.

즉 개념적으로:

```text
obj(10)

   ↓

special call protocol
```

과

```text
obj.__call__(10)

   ↓

attribute lookup
   ↓
bound method
   ↓
call
```

는 서로 다른 경로입니다.

따라서 성능과 특수 메서드 lookup semantics까지 들어가면 둘을 완전히 같은 것으로 취급하면 안 됩니다.

# 20. `__call__`을 바꿔도 재미있는 현상이 발생한다

예를 들어:

```python

    def __call__(self):
        return "A"

obj = A()
```

그리고 인스턴스에:

```python

```

를 넣어봅시다.

그러면:

```python

```

은 경우에 따라 `"B"`가 될 수 있습니다.

하지만:

```python

```

의 special method dispatch는 **타입 수준의 special method lookup**과 연결되어 있기 때문에 단순히 인스턴스 속성 하나를 바꿨다고 동일하게 동작한다고 생각하면 안 됩니다.

이것이 Python의 special method 시스템을 이해하는 핵심입니다.

# 28. `A()`는 실제로 무엇을 하는가?


는 개념적으로:

```text

      │
      ▼

      │
      ▼

```

입니다.

**클래스 객체에 대한 호출이며, 그 호출은 객체 생성 프로토콜을 발동시킵니다.**

# 30. `tp_call`은 Python의 "함수 포인터" 같은 것으로 생각하면 좋다

C 언어 경험이 있다면 이렇게 생각하면 직관적입니다.

```c
tp_call
```

은 개념적으로:

```text
"이 타입의 객체가 호출되면 이 함수를 실행해라"
```

라는 함수 포인터 역할을 합니다.

예를 들어 아주 개념적으로:

```c
if (type->tp_call != NULL) {
    return type->tp_call(obj, args, kwargs);
}
```

같은 구조를 상상할 수 있습니다.

실제 CPython 소스의 정확한 구현은 버전과 호출 경로에 따라 더 복잡하지만, **객체 타입 → 호출 슬롯 → 실제 호출 구현**이라는 연결을 이해하기 위한 모델로는 매우 좋습니다.

# 40. 마지막으로 반드시 수정해야 할 원래 도식

처음 제시하신:

```text
[바이트코드: CALL]
       │
       ▼
[CPython C-API: PyObject_Call(callable, args, kwargs)]
       │
       ▼
[tp_call 슬롯 검사: Py_TYPE(callable)->tp_call]
       │
       ├─► (1) function 객체인 경우: PyFunction_Call() 진입 -> 스택 프레임 생성
       └─► (2) 일반 클래스 인스턴스인 경우: type(obj).__call__(obj, 1, 2) 실행
```

은 **개념 교육용으로는 상당히 좋은 출발점**이지만, CPython 내부를 정확히 배우려면 다음처럼 수정하는 것을 권합니다.

```text
Python source
    │
    ▼
obj(1, 2)
    │
    ▼
Compiler
    │
    ▼
CALL 계열 bytecode
    │
    ▼
CPython call machinery
    │
    ├───────────────┐
    │               │
    ▼               ▼
vectorcall       fallback/general
    │               │
    │               ▼
    │             tp_call
    │
    ▼
callable-specific implementation
    │
    ├── Python function
    │       │
    │       ▼
    │   Python execution
    │
    ├── class/type
    │       │
    │       ▼
    │   object creation
    │       ├── __new__
    │       └── __init__
    │
    └── instance with __call__
            │
            ▼
        __call__
            │
            ▼
       Python execution
```

그리고 **가장 중요한 5문장**만 압축하면:

1. **`obj(...)`는 "함수 호출"이 아니라 "callable 객체 호출"이다.**
2. **모든 함수는 객체이며, 함수 객체는 callable이다.**
3. **`__call__`을 정의한 일반 인스턴스도 callable이 된다.**
4. **CPython에서는 객체의 타입과 호출 슬롯/호출 규약을 통해 실제 호출 구현이 결정된다.**
5. **현대 CPython에서는 성능 때문에 `tp_call`만 보는 것보다 `vectorcall`까지 이해해야 실제 구현에 가까워진다.**

다음 단계로 제대로 **“슈퍼 구루 수준”**까지 가려면 여기서 바로 **`obj(1,2)`의 바이트코드를 `dis.dis()`로 직접 뜯고 → CPython 평가 루프의 `CALL` 처리 → `vectorcall` → `PyFunctionObject` → frame/interpreter state → `__call__`/descriptor → `type.__call__ → __new__ → __init__`** 순서로 내려가면 됩니다. 이 순서를 따라가면 Python의 **함수 호출·메서드 호출·클래스 인스턴스 생성·`super()`·descriptor**가 사실상 하나의 객체 모델로 통합됩니다.

### 👤 User

PyObject랑 PyTypeObject 관계를 도식화 등 시각화해서 설명해줘

### 🤖 Assistant

좋습니다. 여기서는 **`PyObject`와 `PyTypeObject`의 관계를 “모든 Python 객체가 어떻게 자기 타입을 가리키고, 그 타입이 객체의 행동을 어떻게 결정하는가”**라는 관점에서 잡으면 됩니다.

## 1. 가장 중요한 그림

CPython 내부를 극도로 단순화하면:

```text
┌───────────────────────────────┐
│          Python 객체           │
│                               │
│  PyObject                     │
│  ┌─────────────────────────┐  │
│  │ ob_refcnt               │  │
│  │ ob_type ─────────────┐   │  │
│  └─────────────────────│───┘  │
└────────────────────────│──────┘
                         │
                         │ "나는 어떤 타입인가?"
                         ▼
              ┌──────────────────────┐
              │     PyTypeObject      │
              │                      │
              │ tp_name              │
              │ tp_call ──────────┐  │
              │ tp_getattro       │  │
              │ tp_repr           │  │
              │ tp_hash           │  │
              │ tp_iter           │  │
              │ ...               │  │
              └───────────────────│──┘
                                  │
                                  ▼
                         객체의 행동을 결정
```

**핵심은 딱 하나입니다.**

```c
PyObject.ob_type
```

이 포인터가

```c
PyTypeObject
```

를 가리킵니다.

즉:

> **`PyObject`는 "나 자신"이고, `PyTypeObject`는 "나는 어떤 종류의 객체이며 어떻게 행동하는가"를 설명하는 객체입니다.**

---

# 2. 그런데 `PyTypeObject`도 객체다

여기서 Python 객체 모델이 재미있어집니다.

`PyTypeObject` 역시 결국 Python 객체입니다.

따라서:

```text
PyTypeObject
       │
       └── PyObject의 공통 헤더를 포함
```

합니다.

개념적으로 구조를 이렇게 볼 수 있습니다.

```text
                 ┌──────────────────────────┐
                 │       PyTypeObject       │
                 ├──────────────────────────┤
                 │ PyObject_HEAD            │
                 │   ├─ ob_refcnt           │
                 │   └─ ob_type             │
                 ├──────────────────────────┤
                 │ tp_name                  │
                 │ tp_call                  │
                 │ tp_repr                  │
                 │ tp_hash                  │
                 │ tp_getattro              │
                 │ ...                      │
                 └──────────────────────────┘
```

즉:

> **`PyTypeObject`는 `PyObject`를 포함하면서 타입에 필요한 추가 정보를 가진 특별한 객체 구조체입니다.**

C의 구조체 관점에서는 흔히 다음과 같은 관계로 이해합니다.

```c
typedef struct _object {
    Py_ssize_t ob_refcnt;
    PyTypeObject *ob_type;
} PyObject;
```

그리고 `PyTypeObject`는 이 공통 객체 헤더를 포함하고 그 뒤에 타입 전용 필드를 더 갖습니다.

---

# 3. 그래서 `PyObject`와 `PyTypeObject`를 "부모-자식"으로만 이해하면 안 된다

여기서 초보자가 가장 많이 헷갈립니다.

다음처럼 생각하면 **절반만 맞습니다.**

```text
PyObject
   ▲
   │
PyTypeObject
```

C 구조체 메모리 레이아웃 측면에서는 `PyTypeObject`가 `PyObject`의 공통 헤더를 갖는다는 의미가 있지만,

더 중요한 관계는 **포인터 관계**입니다.

```text
객체 ──────────► 자신의 타입
```

즉:

```text
obj
 │
 │ ob_type
 ▼
PyTypeObject
```

입니다.

# 4. 실제 Python 코드와 연결해보자

다음 코드를 보겠습니다.

```python
class Dog:
    pass

d = Dog()
```

Python 관점:

```text
d
 │
 ▼
Dog 인스턴스
```

CPython 관점에서 개념적으로:

```text
┌────────────────────┐
│ d                  │
│                    │
│ PyObject           │
│                    │
│ ob_refcnt          │
│ ob_type ───────────────┐
└────────────────────┘   │
                         │
                         ▼
              ┌─────────────────────┐
              │ PyTypeObject         │
              │                     │
              │ tp_name = "Dog"     │
              │ tp_call = ...       │
              │ ...                 │
              └─────────────────────┘
```

Python에서:

```python
type(d)
```

라고 하면 개념적으로 바로 이 관계를 따라갑니다.

```text
d
│
└── ob_type
       │
       ▼
      Dog
```

그래서:

```python
type(d) is Dog
```

가 성립합니다.

# 5. 그런데 `Dog`도 객체다

여기서 한 단계 더 올라갑니다.

```python
type(Dog)
```

를 해보면:

```python
type
```

입니다.

따라서 구조는:

```text
d
│
│ type
▼
Dog
│
│ type
▼
type
```

가 됩니다.

이를 C 내부 관계로 표현하면:

```text
┌─────────────┐
│ d           │
│ PyObject    │
│             │
│ ob_type ────────────────┐
└─────────────┘           │
                          ▼
                    ┌─────────────┐
                    │ Dog         │
                    │ PyTypeObject│
                    │             │
                    │ ob_type ─────────────┐
                    └─────────────┘        │
                                           ▼
                                      ┌─────────────┐
                                      │ type        │
                                      │ PyTypeObject│
                                      └─────────────┘
```

즉:

```python
type(d)  is Dog
type(Dog) is type
```

입니다.

# 6. 이것이 Python 객체 모델의 핵심 순환 구조다

아주 중요합니다.

```text
             ┌───────────────────┐
             │       type        │
             │  PyTypeObject     │
             └─────────┬─────────┘
                       │
                       │ type(type)
                       │
                       ▼
                  ┌─────────┐
                  │  type   │
                  └─────────┘

             ┌───────────────────┐
             │       Dog        │
             │  PyTypeObject    │
             └─────────┬─────────┘
                       │
                       │ type(Dog)
                       ▼
                      type

             ┌───────────────────┐
             │        d         │
             │     PyObject     │
             └─────────┬─────────┘
                       │
                       │ type(d)
                       ▼
                      Dog
```

이를 한 줄로 압축하면:

```text
d ──type──► Dog ──type──► type
```

입니다.

그리고 일반적으로:

```text
type ──type──► type
```

이라는 자기참조 구조도 존재합니다.

이것이 처음 보면 굉장히 이상하지만, Python의 메타객체 모델에서는 정상입니다.

---

# 7. `PyObject`는 "모든 객체의 공통 기반"이다

CPython에서 거의 모든 객체는 공통적으로 객체 헤더를 갖습니다.

개념적으로:

```c
typedef struct {
    Py_ssize_t ob_refcnt;
    PyTypeObject *ob_type;
} PyObject;
```

이 두 정보가 특히 중요합니다.

### `ob_refcnt`

```text
"이 객체를 몇 군데에서 참조하고 있는가?"
```

와 관련된 참조 카운트입니다.

### `ob_type`

```text
"이 객체의 타입은 무엇인가?"
```

를 가리킵니다.

그래서 모든 Python 객체를 다음처럼 생각할 수 있습니다.

```text
                 Python Object
                      │
          ┌───────────┴───────────┐
          ▼                       ▼
     reference count          object type
       ob_refcnt                ob_type
                                  │
                                  ▼
                           PyTypeObject
```

---

# 8. `PyTypeObject`는 "객체의 행동표"라고 생각하면 좋다

이 비유가 상당히 강력합니다.

예를 들어 객체가:

```python
x + y
```

를 수행하려면 CPython은 타입 정보를 통해 덧셈 연산을 어떻게 처리할지 알아야 합니다.

또:

```python
len(x)
```

이면 길이를 어떻게 얻을지 알아야 합니다.

또:

```python
x()
```

이면 호출을 어떻게 처리할지 알아야 합니다.

따라서 타입 객체에는 여러 **slot**이 있습니다.

개념적으로:

```text
                    PyTypeObject
                         │
        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
     tp_call          tp_repr          tp_hash
        │                │                │
        ▼                ▼                ▼
      x()             repr(x)          hash(x)

        ┌────────────────┼────────────────┐
        ▼                ▼                ▼
     tp_iter         tp_getattro       numeric slots
        │                │                │
        ▼                ▼                ▼
      iter(x)         x.attr            x + y
```

따라서:

> **`PyObject`가 데이터의 실체라면 `PyTypeObject`는 그 실체의 "행동 규칙표"에 가깝습니다.**

---

# 9. `obj()`를 다시 연결해보자

앞에서 공부했던 내용과 정확히 연결됩니다.

```python
obj(1, 2)
```

가 있으면:

```text
                   obj(1, 2)
                       │
                       ▼
                  obj의 객체
                       │
                       │ ob_type
                       ▼
                 PyTypeObject
                       │
                       │ tp_call / call protocol
                       ▼
                  호출 구현
```

즉 `PyObject`와 `PyTypeObject`의 관계를 이해하면 앞에서 봤던:

```c
Py_TYPE(obj)->tp_call
```

이라는 표현이 갑자기 명확해집니다.

`Py_TYPE(obj)`는 개념적으로:

```text
obj
 │
 └── ob_type ──► PyTypeObject
```

입니다.

따라서:

```c
Py_TYPE(obj)->tp_call
```

은 사실상:

```text
obj
 ↓
obj의 타입
 ↓
그 타입의 호출 슬롯
```

입니다.

# 10. `Py_TYPE(obj)`와 `type(obj)`를 연결해보자

Python:

```python
type(obj)
```

C API:

```c
Py_TYPE(obj)
```

를 개념적으로 대응시켜 생각할 수 있습니다.

예:

```python
class A:
    pass

obj = A()
```

그러면:

```text
Python:

type(obj)
   │
   ▼
   A
```

C 레벨 정신 모델:

```text
obj
 │
 └── ob_type
       │
       ▼
   PyTypeObject(A)
```

즉:

```text
type(obj)
      ≈
Py_TYPE(obj)
```

라고 생각하면 객체 모델을 공부하기 매우 편합니다.

단, **Python 함수 `type()`과 C 매크로/매크로성 접근인 `Py_TYPE()`이 구현적으로 완전히 동일한 것은 아닙니다.** 여기서는 객체 관계를 이해하기 위한 대응입니다.

이 두 개를 머릿속에서 분리해야 합니다.



### `Dog`

```text
클래스 객체
```

입니다.

따라서:

```text
d
│
└── ob_type ──► Dog
```

이고:

```text
Dog
│

```

입니다.

그림:


# 13. 그러면 `type`은 누가 만드는가?

여기서 메타클래스가 등장합니다.

```python
class Dog:
    pass
```

를 실행하면 `Dog`라는 클래스 객체가 만들어집니다.

그 클래스 객체의 타입은 기본적으로 `type`입니다.

즉:

```text
class Dog
    │
    ▼
클래스 객체 Dog 생성
    │
    ▼
type(Dog) == type
```

따라서:

```text
인스턴스 생성

d = Dog()
      │
      ▼
Dog 객체

클래스 생성

class Dog:
      │
      ▼
type 객체의 메커니즘을 이용하여
Dog라는 클래스 객체 생성
```

이라는 두 층의 객체 생성이 있습니다.

# 14. `type`은 특별한 `PyTypeObject`다

입니다.

# 17. 실제로는 객체의 "데이터"와 타입의 "행동"이 결합한다

예를 들어:

```python
class Person:
    def __init__(self, name):
        self.name = name

p = Person("Kim")
```

개념적으로:

```text
                 p
        ┌─────────────────┐
        │ PyObject        │
        │                 │
        │ ob_refcnt       │
        │ ob_type ──────────────┐
        │                 │     │
        │ instance data   │     │
        │ name = "Kim"    │     │
        └─────────────────┘     │
                                │
                                ▼
                       ┌──────────────────┐
                       │ Person           │
                       │ PyTypeObject     │
                       │                  │
                       │ tp_call          │
                       │ tp_getattro      │
                       │ tp_repr          │
                       │ ...              │
                       └──────────────────┘
```

즉:

```text
p
=
"실제 데이터"
+
"Person 타입이 정의하는 행동"
```

이라고 볼 수 있습니다.

# 18. 그런데 Python의 메서드는 어디에 있는가?

여기서 한 단계 더 깊어집니다.

```python
class Person:
    def hello(self):
        return "hello"
```

를 생각해봅시다.

`hello`라는 함수가 각 `Person` 인스턴스 안에 복사되어 있는 것은 아닙니다.

개념적으로:

```text
Person 클래스
      │
      ▼
┌────────────────────┐
│ class dictionary   │
│                    │
│ "hello" ──► 함수   │
└────────────────────┘
```

그리고:

```python
p.hello()
```

를 하면 attribute lookup과 descriptor/bound-method 메커니즘이 관여합니다.

즉:

```text
p.hello()
 │
 ▼
attribute lookup
 │
 ▼
Person의 namespace
 │
 ▼
hello function
 │
 ▼
descriptor binding
 │
 ▼
bound method
 │
 ▼
호출
```

입니다.

따라서 `PyTypeObject`를 이해하기 시작하면 자연스럽게 다음 핵심 개념으로 연결됩니다.

```text
PyObject
   ↓
PyTypeObject
   ↓
type lookup
   ↓
attribute lookup
   ↓
descriptor
   ↓
method binding
```

# 19. 여기서 "타입은 행동을 가지고 있다"의 정확한 의미

조금 정교하게 표현하면:

> **타입 객체가 직접 모든 Python 메서드의 구현을 가지고 있다는 뜻이 아니라, 타입의 구조와 slot 및 namespace/descriptor 등의 메커니즘을 통해 해당 타입의 객체가 어떻게 동작할지를 결정한다는 뜻입니다.**

예를 들어:

```python
len(p)
```

에서는 길이 프로토콜이,

```python
p()
```

에서는 호출 프로토콜이,

```python
repr(p)
```

에서는 representation 프로토콜이,

```python
p + q
```

에서는 numeric protocol이 관여합니다.

# 20. 전체 구조를 한 장으로 합치면

이 그림을 저장해두고 계속 보시면 됩니다.

```text
                         ┌────────────────────────┐
                         │          type          │
                         │      PyTypeObject      │
                         │                        │
                         │  ob_type ──────────────┼──┐
                         │                        │  │
                         │  tp_call               │  │
                         │  tp_repr               │  │
                         │  tp_hash               │  │
                         │  tp_iter               │  │
                         │  tp_getattro           │  │
                         │  ...                   │  │
                         └────────────────────────┘  │
                              ▲                      │
                              │ ob_type              │
                              │                      │
                  ┌───────────┴──────────────┐       │
                  │          Dog             │       │
                  │     PyTypeObject         │       │
                  │                          │       │
                  │  ob_type ────────────────┼───────┘
                  │  tp_call                 │
                  │  tp_repr                 │
                  │  ...                    │
                  └───────────▲──────────────┘
                              │
                              │ ob_type
                              │
                  ┌───────────┴──────────────┐
                  │            d             │
                  │        PyObject          │
                  │                          │
                  │  ob_refcnt               │

                  │                          │
                  │  instance data           │
                  └──────────────────────────┘
```

```text
ob_type
```

즉,

> **"이 객체의 타입은 저 객체다."**

입니다.

# 21. 그리고 `PyObject`는 실제로 하나의 "최소 공통 헤더"라고 이해하라

아주 중요한 관점입니다.

CPython에는:

```text
int
float
str
list
dict
function
class
instance
...
```

등 수많은 객체가 있습니다.

이들이 서로 완전히 다른 C 구조체라면 인터프리터가 다루기 매우 어렵습니다.

그래서 공통적인 객체 헤더를 둡니다.

개념적으로:

```text
                  PyObject_HEAD
                 ┌──────────────┐
                 │ ob_refcnt    │
                 │ ob_type      │
                 └──────────────┘
                        ▲
         ┌──────────────┼──────────────┐
         │              │              │
         ▼              ▼              ▼
      int object     list object    function object
```

즉 CPython은 객체를 최소한:

```text
"이건 Python 객체이고,
 참조 카운트가 있고,
 무슨 타입인지 알 수 있다."
```

라는 공통 형태로 다룰 수 있습니다.

# 22. 이것이 C API의 엄청난 힘이다

그래서 C 코드에서:

```c
PyObject *obj;
```

라고 하면 매우 일반적인 의미가 됩니다.

`obj`가 실제로:

```text
int
str
list
dict
function
사용자 정의 객체
type
...
```

중 무엇인지 몰라도 일단 `PyObject *`로 다룰 수 있습니다.

그리고:

```c
Py_TYPE(obj)
```

를 통해 객체의 타입을 확인할 수 있습니다.

그 다음 타입에 따라:

```text
tp_call
tp_repr
tp_hash
tp_iter
...
```

같은 동작 규약으로 접근할 수 있습니다.

# 23. 이 때문에 Python은 "동적 타입 언어"이면서 내부적으로는 매우 강하게 구조화되어 있다

Python 코드에서는:

```python
obj.foo()
```

라고 쓸 때 `obj`가 어떤 타입인지 컴파일 시점에 고정할 필요가 없습니다.

실행 시점에 객체를 보고:

```text
obj
 ↓
type(obj)
 ↓
해당 타입의 동작/namespace
 ↓
foo
 ↓
호출
```

이라는 동적 dispatch가 가능합니다.

하지만 CPython 내부에는:

```text
PyObject
   ↓
ob_type
   ↓
PyTypeObject
   ↓
slots / namespace / descriptor
```

라는 매우 명확한 구조가 있습니다.

# 24. 마지막으로 세 개의 `type`을 구별하면 완성된다

Python을 깊이 파고들 때 다음 세 가지를 구분해야 합니다.

### ① 객체

```python
d
```

```text
PyObject
```

### ② 클래스

```python
Dog
```

```text
PyTypeObject
```

### ③ 메타클래스

```python
type
```

```text
PyTypeObject
```

관계는:

```text
d
│
│ type(d)
▼
Dog
│
│ type(Dog)
▼
type
│
│ type(type)
▼
type
```

즉:

```text
             type
              ▲
              │
             type
              ▲
              │
             Dog
              ▲
              │
              │
              d
```

보다 정확히는 **`type` 자체가 `type`을 타입으로 갖는 자기참조 구조**입니다.

# 25. 최종적으로 이것만 머릿속에 박아두면 된다

```text
                 ┌───────────────────┐
                 │   PyTypeObject     │
                 │                   │
                 │ "너는 누구냐?"     │
                 │ "어떻게 행동하냐?" │
                 │                   │
                 │ tp_call           │
                 │ tp_repr           │
                 │ tp_iter           │
                 │ ...               │
                 └─────────▲─────────┘
                           │
                           │ ob_type
                           │
                 ┌─────────┴─────────┐
                 │     PyObject      │
                 │                   │
                 │ "나는 객체다."     │
                 │                   │
                 │ ob_refcnt         │
                 │ ob_type ──────────┘
                 └───────────────────┘
```

**한 문장으로:**

> **`PyObject`는 "객체의 실체", `PyTypeObject`는 "그 객체가 어떤 타입이며 어떤 방식으로 동작하는지를 정의하는 타입 객체"이고, 모든 일반 객체의 `ob_type`이 자신의 `PyTypeObject`를 가리킨다.**

그리고 이 관계가 바로 우리가 앞에서 본:

```python
obj(1, 2)
```

를

```text
obj
 ↓
PyObject
 ↓ ob_type
PyTypeObject
 ↓ call protocol / slot
호출 구현
 ↓
__call__ 또는 함수/타입의 호출 로직
```

으로 추적할 수 있게 해주는 **CPython 객체 모델의 중심축**입니다.

다음으로는 이걸 **실제 메모리 레이아웃 수준에서 `PyObject_HEAD → PyVarObject_HEAD → PyTypeObject → PyLongObject → PyUnicodeObject`까지 그림으로 확장**하면, `int`, `str`, `list`가 왜 서로 다른 C 구조체인데도 전부 `PyObject *`로 취급될 수 있는지가 완전히 보입니다.
