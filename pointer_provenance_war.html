# 도입 — 같은 속도를 원하지만, 서로 다른 세계를 본다

책상 위의 컴퓨터, 주머니 속 스마트폰, 전 세계를 잇는 클라우드 서버는 모두 메모리를 읽고 쓰며 움직입니다. 그 밑바닥에는 아주 오래된 약속 하나가 있습니다. 프로그래머는 메모리의 바이트와 CPU의 클럭을 최대한 직접 다루고 싶어 하고, 컴파일러는 그 프로그램을 더 빠른 프로그램으로 과감하게 다시 만들고 싶어 한다는 약속입니다. 두 쪽 모두 성능을 원하지만, “무엇이 같은 메모리인가”를 판단하는 방식이 다릅니다.

이 글은 syh 채널의 영상 「포인터의 혈통과 컴파일러의 보이지 않는 전쟁」을 바탕으로 합니다. 이 글은 영상의 줄거리를 뼈대로 하되, 표준·논문으로 보강한 강의록입니다. 영상의 설명을 그대로 옮기는 대신, 예시의 의미를 다시 정리하고, LLVM IR에서 실제로 어떤 문제가 생겼는지와 C 표준화의 현재까지 연결해 보겠습니다.

앞뒤의 감각을 잡는 데는 기존 Pages도 도움이 됩니다. 포인터의 기본 배경은 pointer.html, 주소·메모리·점프의 기초는 box_page_jump_memo.html에서 이어 읽을 수 있습니다. 이 문서는 그 페이지들의 내용을 반복하는 대신, “주소 숫자가 맞는데도 왜 틀린 접근이 되는가?”라는 한 질문을 중심으로 새로 쓴 독립 강의록입니다.

먼저 기억할 한 문장

하드웨어는 주소의 비트 패턴을 보지만, 프로그래밍 언어와 컴파일러는 그 포인터가 어느 메모리 객체에서 유래했는지까지 본다. 이 유래 정보가 바로 provenance(출처·혈통)다.

# 두 기둥의 충돌 — 성능이라는 같은 목적, 다른 경로

한쪽에는 시스템 프로그래머가 있습니다. C/C++의 포인터, Rust의 unsafe 블록, 운영체제 커널과 런타임의 낮은 수준 인터페이스를 통해 메모리의 배치와 접근 순서를 세밀하게 통제합니다. 캐시 한 번, 복사 한 번, 분기 한 번이 비용이 되므로 “이 바이트를 어디에 놓고 언제 읽을 것인가”를 직접 결정하려 합니다.

다른 쪽에는 GCC와 LLVM/Clang 같은 컴파일러가 있습니다. 컴파일러는 소스의 문장을 충실히 기계어로 번역하는 도구에 머물지 않습니다. 프로그램 전체에서 어떤 값이 변하지 않는지, 두 포인터가 같은 곳을 만질 수 있는지, 계산을 앞당길 수 있는지를 분석해 실행 순서를 재구성합니다. 필요하다면 메모리 읽기를 없애고, 중복 계산을 합치고, 도달할 수 없는 분기를 삭제합니다.

1970년대의 C와 초기 컴파일러를 떠올리면 “컴파일러는 시킨 일을 수행하는 성실한 번역기”라는 직관이 자연스럽습니다. 당시에는 CPU와 메모리의 격차가 지금만큼 크지 않았고, 생성된 코드도 훨씬 단순했습니다. 하지만 CPU의 연산 장치는 빠르게 발전한 반면 메모리에서 값을 가져오는 지연은 상대적으로 줄어들지 않았습니다. 이른바 메모리 장벽(memory wall)입니다.

그래서 현대 컴파일러는 메모리 접근을 줄이는 방향으로 프로그램을 다시 씁니다. 최근 저장한 값이 레지스터에 있다면 RAM에 다시 가지 않고 그 값을 사용합니다. 루프 안에서 반복되는 주소 계산은 바깥으로 끌어냅니다. 두 식이 같은 결과를 낸다면 하나를 버립니다. 이 모든 변환은 “정상적인 프로그램이라면 언어의 규칙을 어기지 않는다”는 전제 위에서만 안전합니다.

miscompilation은 조용히 온다

여기서 문제는 컴파일러가 항상 오류를 보고하지 않는다는 점이다. 표준상 정의되지 않은 동작(Undefined Behavior, UB)이 포함되었다고 판단하면, 컴파일러는 그 실행을 보존할 의무가 없다. 결과는 컴파일 실패가 아니라 에러 메시지 없이 다른 값을 내는 miscompilation일 수 있다.

# 앨리어싱과 스토어 포워딩 — “혹시 같은 곳이면?”이라는 의심

앨리어싱(aliasing)은 서로 다른 포인터나 이름이 같은 메모리 위치를 가리키는 현상입니다. 예를 들어 함수가 두 포인터를 받아 첫 번째 위치에 저장하고 두 번째 위치를 읽는다고 합시다. 두 포인터가 결코 같은 객체를 가리키지 않는다는 사실을 증명할 수 있다면, 컴파일러는 읽기와 쓰기를 재배치하거나 값을 레지스터에 보관할 수 있습니다.

c 
int read_after_store(int *x, int *y) {
    *x = 10;
    return *y;
}

x와 y가 같은 위치일 가능성이 있다면 *x = 10은 *y의 결과를 바꿀 수 있습니다. 반대로 서로 별개의 객체라는 전제가 있으면 컴파일러는 두 메모리 접근의 순서를 조정하거나, 방금 저장한 값을 레지스터에서 이어 사용할 수 있습니다. 저장(store)한 값을 메모리로 내려보내지 않고 다음 계산에 전달하는 효과를 넓은 의미에서 스토어 포워딩(store forwarding)이라고 부를 수 있습니다.

컴파일러의 기준은 “대체로 다르다”가 아닙니다. 단 1%라도 같은 위치일 가능성이 남아 있고 그 경우가 언어상 유효하다면, 변환은 안전하지 않습니다. 그래서 앨리어싱 분석기는 의심이 생기면 보수적으로 물러납니다. 매번 메모리를 다시 읽고, 순서를 지키고, 최적화를 하지 않는 쪽을 택합니다. 이때 손해는 작은 함수 하나가 아니라 루프와 전체 프로그램의 실행 시간으로 누적됩니다.

그렇다면 컴파일러는 어떻게 “서로 다른 객체에서 온 포인터는 남의 객체를 바꾸지 않는다”고 확신할까요? 단순한 주소 숫자만으로는 답이 나오지 않습니다. 그 질문이 다음 장의 출발점입니다.

# 평면 메모리 모델의 붕괴 — 포인터는 왜 정수가 아닌가

초보적인 모델에서 메모리는 0번 바이트부터 차례로 놓인 거대한 배열입니다. 포인터는 그 배열의 위치를 나타내는 정수이고, 주소에 숫자를 더하면 다른 주소가 됩니다. 실제 CPU가 주소 버스를 통해 비트 패턴을 전달한다는 점에서는 그럴듯한 설명입니다.

그러나 언어의 추상 기계에서 포인터는 단순한 정수가 아닙니다. 포인터에는 보통 다음 두 층의 정보가 함께 있다고 생각할 수 있습니다.

  • 물리적 주소 또는 오프셋: 실제 실행 환경에서 어느 위치를 가리키는가.
  • 출처(provenance): 어떤 할당(allocation) 또는 메모리 객체에서 파생되었으며, 어느 범위에 접근할 권한이 있는가.

이를 간단히 (객체 식별자, 오프셋)이라고 적을 수 있습니다. 실제 표준 문서나 컴파일러 구현이 모두 이 자료구조를 그대로 저장한다는 뜻은 아닙니다. 이것은 의미론을 설명하는 모델입니다. 주소가 우연히 같아도 출처가 다르면 두 포인터는 같은 권한을 가진 값이 아닐 수 있습니다.

이 구분은 “프로그래머가 주소를 숫자로 계산해 다른 객체에 도달할 수 있는가?”라는 문제를 다룹니다. 계산 결과가 실제 RAM의 주소와 같다는 사실과, 그 결과를 유효한 포인터로 역참조할 권리가 있다는 사실은 서로 다릅니다.

# 숫자만 같은 두 포인터 — P와 Q의 이웃집 사건

malloc으로 길이 4인 두 배열 p와 q를 얻었다고 합시다. 할당기는 우연히 두 블록을 이웃하게 배치할 수 있습니다. 평면 메모리에서 p의 끝 바로 다음이 q의 시작이라면, p + 6과 q + 2가 같은 물리적 주소를 가질 수 있습니다. 아래 표기에서 배열 원소가 아니라 바이트 단위 포인터 산술을 생각하면 숫자 관계가 더 분명합니다.

c 
char *p = malloc(4), *q = malloc(4);
q[2] = 0;
p[6] = 1;                 // p에서 파생된 주소
printf("%d\\n", q[2]);

하드웨어의 평면 모델만 따르면 p[6]이 실제로 q[2]와 같은 주소에 닿는 경우 출력은 1입니다. 하지만 provenance 모델에서는 p[6]의 출처가 여전히 p입니다. 길이 4인 p의 바깥으로 나간 뒤 q의 영역에 쓰는 것은, 주소 숫자를 맞혔더라도 q에 대한 접근 권한이 없는 침입입니다. 그 저장은 UB가 됩니다.

이 규칙이 있으면 컴파일러는 q[2] = 0과 printf 사이에 유효한 q[2] 저장이 없다고 판단할 수 있습니다. p[6] 저장을 실제 실행에서 남겨둘지와 별개로, 정의된 프로그램의 의미만 보존하면 출력은 0으로 전파할 수 있습니다. 즉 메모리 읽기를 제거하고 상수 0을 직접 넘겨도 됩니다.

이것이 사용자에게는 황당해 보이는 이유는 물리적 실행의 한 장면과 언어의 법적 의미가 어긋나기 때문입니다. 메모리 칩에는 “이 비트는 p 출신, 저 비트는 q 출신”이라는 표지가 없습니다. 그 표지는 추상 기계와 컴파일러가 최적화의 근거로 관리하는 의미 정보입니다.

포인터의 산술이 항상 허용되지 않는다는 뜻은 아닙니다. 배열 내부를 순회하거나 배열의 끝을 가리키는 one-past-the-end 포인터를 만드는 일처럼, 객체의 규칙 안에서 이루어지는 계산은 중요한 C 관용구입니다. 문제는 하나의 객체에서 출발한 포인터를 숫자 이동만으로 다른 독립 객체의 권한으로 바꿀 수 있다고 가정하는 데 있습니다.

# 컴파일러 내부 내전 — GVN이 저지른 “같은 값”의 실수

소스 언어의 규칙을 LLVM IR로 옮겼다고 해서 문제가 끝나지 않습니다. LLVM IR에서는 여러 최적화 패스가 같은 값을 다시 찾아내고 제거합니다. 그중 GVN(Global Value Numbering)은 식이나 값에 번호를 붙여, 이미 계산한 것과 동등한 결과를 재사용하는 최적화입니다.

정수에 대해서는 “두 값이 같다는 조건문을 통과했으니 앞으로 하나로 치환하자”가 강력하고 유용한 규칙입니다. 하지만 포인터에서는 물리적 숫자가 같다는 것과 포인터 값 전체가 같은 의미라는 것이 다를 수 있습니다. 출처, 수명, 경계, 함수 호출 시점 같은 정보가 포인터에 붙어 있기 때문입니다.

논문에 보고된 Rust 사례를 직관적으로 축약하면 이렇습니다. 한 포인터 p는 어떤 객체의 끝 바깥을 가리키는 방식으로 계산되고, 다른 포인터 q는 조건에 따라 실제로 수정해야 할 객체를 가리킵니다. 둘의 주소 숫자가 특정 조건에서 같아질 수 있습니다. 원래 코드에서는 q를 통한 저장이 유효하지만, GVN이 조건문의 포인터 동등성을 근거로 q를 p로 바꾸면 상황이 달라집니다.

이제 후속 앨리어싱 분석은 p에서 파생된 포인터가 다른 객체를 건드리는 것으로 봅니다. 그것은 UB이므로 저장을 무시하거나, 다른 값이 유지된다고 전파할 수 있습니다. 결과적으로 원본의 안전한 Rust 코드가 잘못된 결과를 내는 LLVM miscompilation이 됩니다. 핵심은 GVN이 “주소가 같은 포인터”와 “서로 바꾸어도 되는 포인터”를 혼동했다는 데 있습니다.

GVN 사고의 교훈

포인터 비교가 참이라는 사실은 주소 숫자에 대한 정보일 수 있지만, 모든 출처·경계·수명 정보까지 동일하다는 보증은 아니다. 포인터 치환은 정수 치환보다 훨씬 강한 조건을 요구한다.

따라서 해결책은 GVN을 없애는 것이 아니었습니다. LLVM의 중간 표현이 포인터의 여러 의미를 구분하고, GVN이 그 구분을 존중하는 메모리 모델을 갖추는 것이 해법이었습니다.

# LLVM의 수술 — 논리 포인터와 물리 포인터를 갈라 세우기

Juneyoung Lee, Chung-Kil Hur, Ralf Jung, Zhengyang Liu, John Regehr, Nuno P. Lopes는 LLVM IR의 이 문제를 체계적으로 분석했습니다. 그들의 논문은 “Reconciling High-Level Optimizations and Low-Level Code in LLVM”, Proceedings of the ACM on Programming Languages 2, OOPSLA, Article 125 (2018)입니다.

이 논문이 제안한 큰 방향은 포인터를 한 종류의 “주소를 담은 정수”로 뭉뚱그리지 않는 것입니다.

# 논리 포인터

할당에서 태어나거나 논리 포인터에 대한 포인터 산술로 얻은 값입니다. 논리 포인터에는 블록 식별자와 그 블록 안의 오프셋이 있다고 생각할 수 있습니다. 산술은 오프셋을 바꾸지만 블록 식별자를 다른 객체의 것으로 바꾸지 않습니다. 그러므로 p에서 출발한 논리 포인터는 숫자가 q의 위치와 같아져도 q의 저장을 합법화하지 않습니다.

# 물리 포인터

정수에서 포인터로 변환된 값처럼, 데이터 흐름만으로 단일 객체의 출처를 추적하기 어려운 포인터입니다. 이런 포인터를 “어느 객체에도 접근할 수 있다”고 단순하게 허용하면 저수준 코드와 정수·포인터 변환을 지원할 수 있지만, 앨리어싱 분석이 지나치게 보수적으로 변합니다. 제안된 모델은 물리 포인터에도 주소, 지연 경계 검사에 필요한 정보, 함수 인자로 들어온 시점 같은 제한 정보를 함께 두어 정밀도를 회복합니다.

이 분리는 모든 구현의 사용자에게 “포인터가 두 개의 C 타입으로 바뀐다”는 의미가 아닙니다. LLVM IR의 의미론과 최적화 규칙이 포인터의 출처를 보존하면서도 주소를 정수로 다루는 저수준 관용구를 모델링하기 위한 내부 설계입니다. 가장 중요한 효과는 GVN이 숫자만 같다는 이유로 논리 포인터와 물리 포인터를 함부로 합치지 못하게 하는 것입니다.

# 지연된 경계 검사 — 계산하는 순간과 들어가는 순간

포인터의 경계 검사는 또 다른 난제를 만듭니다. LLVM의 getelementptr(GEP)는 포인터에 인덱스를 더해 새 포인터를 만드는 IR 명령입니다. 기존의 inbounds 의미에서는 GEP를 계산하는 바로 그 순간, 입력과 결과가 객체 내부 또는 one-past 범위에 있어야 한다고 판단했습니다. 범위를 벗어난 결과는 poison이 되고, 그 값을 나중에 사용하면 UB로 이어질 수 있습니다.

안전해 보이는 이 즉시 검사는 코드 이동을 가로막습니다. 루프 안에서 매번 하는 주소 계산을 루프 바깥으로 끌어내는 LICM(Loop-Invariant Code Motion)을 생각해 보세요. 원래 실행 시점에는 아직 유효한 객체가 할당되지 않았거나 조건이 정해지지 않았더라도, 실제 역참조 시점에는 올바른 주소가 될 수 있습니다. 그런데 계산을 미리 옮기면 “계산 당시”에는 범위 밖인 포인터가 만들어져 poison이 됩니다.

논문이 제안한 지연된 경계 검사(deferred bounds checking)는 포인터 계산 자체를 순수한 연산으로 둡니다. 범위 밖의 포인터를 만들고 전달하고 다른 계산에 넣는 일은 당장 실패시키지 않습니다. 대신 그 포인터로 실제 메모리를 읽거나 쓰는 역참조 시점에, 포인터가 유효한 객체의 범위에 들어오는지 검사합니다. inbounds 연산을 거쳤다면 입력과 결과가 같은 객체의 범위에 들어와야 한다는 제약을 별도 정보로 기록해 두었다가 접근 시 확인합니다.

지도에 경로를 그리는 일과 금지 구역의 문을 여는 일을 분리한다고 생각하면 쉽습니다. 경로 계산은 컴파일러가 자유롭게 앞뒤로 옮길 수 있습니다. 그러나 실제 문을 여는 순간에는 출입 권한과 경계를 검사합니다. 이 설계는 경계 보호를 포기한 것이 아니라, 보호의 시점을 최적화와 충돌하지 않게 재배치한 것입니다.

# 쌍둥이 할당(twin allocation) — 주소를 맞혀도 확신할 수 없게 하기

물리 포인터를 허용하면 또 하나의 질문이 남습니다. 프로그램이 직접 q의 주소를 받지 않았더라도, 다른 정보로 그 주소를 추측해 맞힐 수 있다면 어떻게 할까요?

보통은 할당 주소가 비결정적이라고 설명합니다. malloc이 어떤 주소를 반환할지 프로그램이 미리 알 수 없다면, 임의의 정수 주소를 포인터로 바꾸어 객체를 맞히는 코드는 어느 실행에서는 틀릴 것입니다. 틀리는 실행에서 UB가 된다면 컴파일러는 그런 추측을 정의된 별칭으로 보지 않을 수 있습니다.

하지만 메모리가 거의 꽉 찬 상황에서는 새 객체가 들어갈 수 있는 자리가 두 곳뿐일 수 있습니다. p가 첫 번째 자리를 받으면 q는 두 번째, p가 두 번째면 q는 첫 번째입니다. 프로그램이 p의 주소와 할당 성공 여부를 관찰하면 q의 주소를 직접 전달받지 않고도 알아낼 수 있습니다. 유한한 주소 공간이 일종의 사이드 채널이 되는 것입니다.

여기서 등장하는 해법이 쌍둥이 할당입니다. 추상적인 할당 모델에서 요청된 블록 하나만 예약하지 않고, 적어도 하나 이상의 쌍둥이 블록을 함께 예약합니다. 실제 프로그램에는 그중 하나의 주소만 관찰 가능하게 돌려주고, 다른 후보 블록은 접근 불가능한 그림자로 남겨 둡니다. 그러면 메모리가 꽉 차더라도 관찰된 p 하나만으로 다른 객체의 주소를 100% 확정할 수 없습니다. 확률이 아니라 의미론적 가능성 하나만 남아도, 그 포인터 추측은 정의된 별칭이 되지 못합니다.

이 아이디어를 정확히 말하면 “실제로 런타임이 매번 메모리를 두 배로 쓴다”는 주장이 아닙니다. 컴파일러가 주소 추측을 정의된 프로그램 행동으로 취급하지 않도록, 할당의 비결정성을 형식화하는 의미론적 장치입니다. 논문에서는 twin allocation이 고수준 최적화와 정수-포인터 변환을 동시에 지지하는 방법으로 제시됩니다.

쌍둥이 할당의 핵심

관찰되지 않은 객체의 주소를 프로그램이 맞혀도 되는 세계를 만들면 앨리어싱 분석이 무너진다. 할당마다 숨은 후보를 남겨 두면, 프로그램이 실제 주소를 관찰하지 않은 한 “맞혔다”는 사실을 모든 가능한 실행에 대해 보장할 수 없게 된다.

이 설계는 물리적 메모리의 한계를 부정하는 대신, 컴파일러가 추론하는 세계에 숨은 선택지를 보존합니다. 그래서 “주소를 봤다”와 “주소를 추측했다”를 구분할 수 있습니다.

# 모호함이 사라진 뒤의 속도 — 안전을 넣었는데 왜 빨라지는가

새 메모리 모델은 처음부터 모든 최적화를 되살린 것이 아닙니다. 안전성을 우선한 프로토타입에서는 일부 포인터 최적화를 끄기 때문에 성능 하락이 나타납니다. 논문은 SPEC CPU 2017을 포함한 실험에서 첫 번째 sound 프로토타입의 평균 성능 저하를 약 0.2%로 보고합니다. 이후 포인터 뺄셈을 위한 psub과 안전한 경우의 GVN 재활성화 등을 적용했고, 평균 저하는 약 0.1% 수준으로 줄었으며 mcf에서는 1.7% speedup도 관찰했습니다.

여기서 중요한 주의점이 있습니다. 0.2%와 1.7%는 이 글의 절대적인 보장 수치가 아니라, 해당 논문과 영상에서 소개된 특정 실험의 수치입니다. 하드웨어, 컴파일러 버전, 옵션, 벤치마크와 측정 방법에 따라 달라집니다.

속도가 회복된 까닭은 단순히 안전 검사를 더 빠르게 실행했기 때문이 아닙니다. 기존 IR에서는 포인터 간 거리를 구할 때 포인터를 정수로 바꾼 뒤 정수 뺄셈을 하는 경로가 흔했습니다. 그런데 분석기 입장에서는 그 순간 provenance가 사라진 것처럼 보이고, 이후의 최적화를 중단해야 했습니다. 의미상 포인터 간 연산인 것을 정수 연산으로 낮춘 탓에 스스로 모호함을 만든 셈입니다.

논문은 포인터 전용 뺄셈 명령인 psub을 도입하는 방향을 제시합니다. 같은 논리 객체 안의 두 포인터라면 오프셋 차이를 반환하고, 서로 다른 논리 객체라면 poison과 같은 정의되지 않은 결과를 모델링할 수 있습니다. 물리 포인터가 관여하면 주소 숫자 기반의 계산을 적용할 수 있습니다. 이렇게 하면 단순히 거리를 계산하려고 provenance를 버리지 않아도 됩니다.

규칙이 모호하면 컴파일러는 안전을 위해 멈춥니다. 반대로 어떤 경우에 치환이 안전하고 어떤 경우에 UB인지 명확하면, 컴파일러는 더 대담하게 코드를 움직일 수 있습니다. 안전성과 최적화는 꼭 반대말이 아닙니다. 잘 정의된 경계가 오히려 최적화의 발판이 되기도 합니다.

# 표준의 도착 — ISO/IEC TS 6010:2025

이 논쟁은 논문과 컴파일러 내부 문서에만 머물지 않았습니다. WG14에서는 C의 메모리 객체와 포인터 출처를 명시하려는 오랜 작업이 진행되었고, 그 흐름의 중요한 결과가 ISO/IEC TS 6010:2025, Programming languages — C — A provenance-aware memory object model for C입니다.

TS 6010은 C 전체를 새로 정의하는 완전한 언어 표준이 아닙니다. ISO/IEC 9899:2018(C18)을 바탕으로 하면서, 그 표준에서 열어 둔 메모리 객체 모델의 해석을 제한하고 명확히 하는 기술 사양입니다. ISO 페이지의 판본 정보는 2025-05이며, 출판일은 2025년 5월 15일입니다. 따라서 “C18 메모리 객체 모델을 보완하는 provenance-aware TS”라고 이해하는 것이 정확합니다.

그 배경에는 WG14 문서 N3057이 있습니다. N3057은 2022년 9월 20일자 초안 계열 문서로, C18에 대한 확장 형태로 provenance-aware memory object model을 제안합니다. N3057과 이후 TS의 논의에서 중요한 계열이 PNVI(Provenance Not Via Integers)입니다.

# PVI와 PNVI를 한 번에 비교하기

  • PVI(Provenance Via Integers): 포인터를 정수로 바꾸어도 출처를 정수 값 뒤에 붙여 추적합니다. 포인터가 정수 상태에서 산술·비트 연산을 거쳐도 혈통을 보존하려는 발상입니다. 그러나 정수의 등식 전파, 재결합, 비트 연산 같은 보편적 최적화와 충돌하기 쉽습니다. 출처가 다른 두 정수를 빼면 결과의 출처를 어떻게 정할지, 연산 괄호를 바꾸어도 같은 의미인지가 복잡해집니다.
  • PNVI(Provenance Not Via Integers): 정수는 정수로서 다루며, 정수 상태를 지나는 동안 출처를 계속 운반하지 않습니다. 대신 정수를 포인터로 바꾸는 시점에 출처를 어떻게 복원할지 규칙을 둡니다.

PNVI에도 plain, address-exposed(PNVI-ae), user-disambiguation을 포함한 여러 변형이 논의되었습니다. 직관적으로는 실제 주소가 관찰된(exposed) 객체만 정수-포인터 변환으로 되살릴 수 있게 하거나, 여러 객체가 후보일 때 프로그램의 사용 방식으로 모호성을 해결하는 식입니다. TS 6010의 구체적 조항은 표준 원문을 확인해야 하며, 여기서는 역사적 설계 공간을 설명하는 수준으로만 요약합니다.

PNVI는 저수준 C의 정수-포인터 왕복을 완전히 금지하지 않으면서, 정수 연산 전체에 provenance를 매다는 부담도 피하려는 타협입니다. 그래서 “정수로 바꾸는 순간 모든 규칙이 끝난다”도 아니고, “정수의 모든 비트 연산을 출처 추적 대상으로 만든다”도 아닙니다. 주소의 관찰, 객체의 수명, 포인터 합성(synthesis), 실제 역참조를 분리해 다루려는 시도입니다.

# Rust Strict Provenance는 이웃 트랙

Rust 커뮤니티의 Strict Provenance는 같은 문제를 다른 언어 설계의 자리에서 다루는 이웃 트랙입니다. 핵심 아이디어는 주소 숫자를 얻는 행위와 포인터의 출처를 보존한 채 주소만 바꾸는 행위를 API 수준에서 구분하는 것입니다. 예컨대 addr로 숫자 주소를 관찰하고, with_addr 계열로 기존 포인터의 출처를 유지하면서 주소를 조정하는 식입니다. 이는 C의 TS 6010과 동일한 표준이나 동일한 모델이라는 뜻은 아닙니다. 다만 “주소 숫자”와 “접근 권한”을 분리해야 한다는 공통 문제의식이 있습니다.

# 짧은 맺음 — 보이지 않는 방어선에 감사하기

포인터의 혈통이라는 말은 처음 들으면 물리적 컴퓨터와 동떨어진 철학처럼 보입니다. CPU는 결국 주소 비트를 내보내고 RAM은 비트를 저장할 뿐입니다. 그러나 컴파일러가 그 단순한 하드웨어를 안전하고 빠른 프로그램으로 바꾸려면, 주소 숫자만으로는 “이 저장이 무엇을 바꿀 수 있는가”를 증명할 수 없습니다.

앨리어싱 분석은 스토어 포워딩과 레지스터 유지의 근거를 원합니다. GVN은 같은 숫자와 같은 권한을 구분해야 합니다. LLVM은 논리 포인터와 물리 포인터를 나누고, 경계 검사를 역참조까지 늦추고, 쌍둥이 할당으로 주소 추측의 빈틈을 막으려 했습니다. C 표준화는 PNVI 계열의 질문을 다듬어 TS 6010이라는 공적인 문서에 담았습니다.

프로그래머의 자유와 컴파일러의 최적화는 어느 한쪽이 완전히 이기는 싸움이 아닙니다. 자유를 보장하되 그 자유가 무엇을 의미하는지 엄밀히 적고, 컴파일러는 그 경계 안에서 최대한 멀리 달립니다. 우리가 별다른 오류 없이 빠른 시스템을 사용하는 동안에도, 그 경계와 보이지 않는 출처를 지키는 방어전은 계속됩니다. 그러니 다음에 컴파일러가 메모리 읽기 하나를 조용히 없애는 것을 볼 때는, 그 냉정함 뒤에 있는 보이지 않는 방어에도 잠시 감사해 봅시다.
