# 🌟 프롤로그: "상자"를 부수고 "메모리 광장"으로

C, C++, Java 같은 전통적인 정적 타입 언어를 먼저 경험한 사람들은 변수를 ‘데이터를 담는 메모리 상자(Bucket)’로 생각하는 강한 관성을 가지고 있습니다.

평문 
[C 언어적 사고: 변수 = 상자]
int x = 10;
┌─────────────┐
│     10      │  <-- 스택 프레임 내 4바이트 상자 자체가 x
└─────────────┘

하지만 파이썬의 세계에서 변수는 절대로 상자가 아닙니다.

파이썬 세상의 모든 데이터는 컴퓨터 메모리의 거대한 힙(Heap) 광장에 독립적으로 존재하는 ‘살아있는 생명체(객체, PyObject)’입니다. 그리고 우리가 코드에서 작성하는 변수는 그 독립 객체의 손목에 매달아 둔 ‘이름표(Label / Pointer)’에 불과합니다.

평문 
[파이썬의 실제 모델: 변수 = 이름표, 데이터 = 힙 객체]

[ 전역 네임스페이스 ]               [ 메모리 힙(Heap) 광장 ]
  ┌───────────┐      끈(참조 포인터)    ┌───────────────────────────────┐
  │     x     │ ────────────────────▶ │  PyLongObject (정수 10)       │
  └───────────┘                       │  - ob_refcnt : 1              │
                                      │  - ob_type   : <class 'int'>  │
                                      │  - ob_digit  : 10             │
                                      └───────────────────────────────┘

이 사소해 보이는 관점의 전환 하나가, 파이썬의 모든 동작을 지배하는 만유인력의 법칙이 됩니다:

  1. x = 20을 대입하면 상자의 내용물이 바뀌는 것이 아니라, x 이름표를 떼어 새로 만든 20 객체에 다시 묶습니다.
  2. y = x를 실행하면 숫자가 복사되는 것이 아니라, 0x... 주소의 동일한 10 객체에 y라는 두 번째 이름표를 하나 더 달 뿐입니다.
  3. 리스트에 값을 추가해도 리스트 컨테이너 객체의 주소는 그대로 유지됩니다.

# 1. 정수 10000의 해부: 파이썬 객체의 실체는 C 구조체다

파이썬(표준 CPython 구현체 기준)에는 하드웨어 직결형 원시 타입(Primitive Type)이 존재하지 않습니다. 숫자 10000 하나조차 64비트 CPython에서는 무려 28바이트를 차지하는 독립 C 구조체입니다.

# CPython의 PyLongObject 내부 레이아웃

c 
// CPython 내부 헤더 (의사 코드)
struct _longobject {
    PyObject_VAR_HEAD
    digit ob_digit[1];
};

이 구조체가 메모리에 할당되면 다음과 같이 배치됩니다:

평문 
+-------------------------------------------------------------------------+
|                PyObject_VAR_HEAD (메타데이터 헤더: 24 Bytes)              |
+-------------------------------------------------------------------------+
|  ob_refcnt : 8 Bytes  (이 객체를 가리키는 이름표 개수 = 참조 카운트)         |
|  *ob_type  : 8 Bytes  (객체의 규격서: PyLong_Type 포인터)                  |
|  ob_size   : 8 Bytes  (가변 길이 정수 배열의 크기/부호 정보)                 |
+-------------------------------------------------------------------------+
|                Payload (실제 데이터 페이로드: 4 Bytes)                   |
+-------------------------------------------------------------------------+
|  ob_digit  : 4 Bytes  (실제 정수 데이터 값: 10000)                       |
+-------------------------------------------------------------------------+
  총 메모리 크기: 28 Bytes

# C 표준 추상 기계의 객체 vs 파이썬 객체의 본질적 차이

  • C 표준(ISO C)의 객체: 실행 환경에서 값을 저장할 수 있는 "연속된 메모리 영역(Region of data storage)"에 불과합니다. 스택에 잡힌 int a; 4바이트도 C 표준에서는 객체이며, 런타임 메타데이터나 타입 정보가 전혀 들어있지 않습니다.
  • 파이썬의 객체: Identity(메모리 주소), Type(타입 포인터), RefCount(참조 카운트)라는 신분증(Header)을 반드시 목에 걸고 힙에 상주하는 풍부한 객체 지향 엔티티입니다.

# 2. 불변(Immutable)과 가변(Mutable)의 동역학

파이썬의 객체는 크게 두 가지 종족으로 나뉩니다:

구분 해당 자료형 값 변경 시 CPython 내부 동작 메모리 주소 (id())
불변 (Immutable) int, float, str, tuple, frozenset 기존 메모리 수정 불가. 새 객체 생성 후 이름표 재바인딩 완전히 변경됨
가변 (Mutable) list, dict, set, 사용자 정의 인스턴스 기존 메모리 유지. 내부 포인터 배열을 인플레이스(In-place) 수정 불변 (유지됨)

# 컨테이너 객체의 실체: "포인터 주머니"

파이썬의 list는 숫자나 문자열을 직접 품고 있지 않습니다. 리스트는 단지 다른 객체들의 메모리 주소를 가리키는 C 레벨 포인터 배열입니다.

평문 
x = [1, 2, 3]

[ 이름표 x ] ──▶ [ List 컨테이너 객체 (0xAAA) ]
                  ├─ [0] 포인터 ──▶ [ 정수 1 객체 (0x100) ]
                  ├─ [1] 포인터 ──▶ [ 정수 2 객체 (0x200) ]
                  └─ [2] 포인터 ──▶ [ 정수 3 객체 (0x300) ]

x.append(4)를 실행하면 리스트 객체 0xAAA의 메모리 주소는 그대로 유지된 채, 내부 슬롯의 포인터 하나만 4 객체로 추가 연결될 뿐입니다.

# 3. 데이터와 로직의 이산가족: 인스턴스와 클래스의 역할 분담

객체 지향 프로그래밍을 할 때 많은 사람들이 무의식중에 다음과 같은 오해를 합니다:

"인스턴스를 만들면 그 안에 메서드 함수들도 함께 복사되어 들어있겠지?"

만약 강아지 클래스 Dog로 1만 마리의 인스턴스를 만들었는데 메서드가 복사된다면, 동일한 기계어 코드가 1만 번 중복 생성되어 메모리가 폭발할 것입니다.

파이썬은 이를 철저하게 방지하기 위해 데이터(상태)와 로직(함수)을 완벽하게 분리합니다:

평문 
[ 힙 메모리 광장 ]

  (공용 로직 공구함)
  ┌──────────────────────────────────────────────────────────┐
  │ 클래스 객체 Dog (0x800)                                  │
  │  - ob_type  : <class 'type'>                             │
  │  - __dict__ : { 'bark': <function Dog.bark at 0x900> }   │
  └──────────────────────────────────────────────────────────┘
       ▲
       │ ob_type (소속 클래스 포인터)
       │
  ┌──────────────────────────────────────────────────────────┐
  │ 인스턴스 객체 my_dog (0x500)                              │
  │  - ob_type  : 0x800 (Dog 클래스를 가리킴)                 │
  │  - __dict__ : { 'name': '바둑이', 'age': 3 }             │
  │  ※ 함수 바이트코드는 1바이트도 들어있지 않음!              │
  └──────────────────────────────────────────────────────────┘
  • 인스턴스(my_dog): 오직 자신의 이름, 나이 같은 순수한 고유 데이터(속성)만 담고 있는 데이터 창고입니다.
  • 클래스(Dog): 모든 인스턴스가 함께 사용하는 공유 함수들을 딱 한 벌만 보관하는 공용 공구함입니다.

# 4. 점(.)을 찍는 순간 벌어지는 마법: Bound Method의 런타임 탄생

인스턴스에 함수가 없다면, 도대체 파이썬은 어떻게 my_dog.bark()를 실행할 수 있을까요?

그 해답은 바로 점(.) 연산자와 디스크립터 프로토콜(Descriptor Protocol: __get__)에 있습니다.

우리가 코드에서 my_dog.bark를 적는 바로 그 찰나의 순간, 파이썬 인터프리터 내부에서는 놀라운 일이 벌어집니다:

평문 
1. my_dog 뒤에 점(.)을 찍고 bark를 찾는다.
2. my_dog.__dict__에 'bark'가 없으므로 ob_type을 타고 Dog 클래스로 올라간다.
3. Dog.__dict__['bark']에서 원본 함수 객체를 찾아낸다.
4. 파이썬의 함수 객체는 디스크립터이므로 __get__ 메서드를 내장하고 있다!
5. CPython이 Dog.__dict__['bark'].__get__(my_dog, Dog)를 자동 호출한다.
6. 힙 메모리에 <bound method>라는 새로운 임시 래퍼 객체가 즉석에서 생성된다!
평문 
[ 점(.)을 찍는 순간 힙에 방금 태어난 임시 래퍼 객체 ]
+-----------------------------------------------------------------+
| <bound method Dog.bark of <Dog object at 0x500>>                |
+-----------------------------------------------------------------+
|  __func__ : 0x900 (Dog 클래스 내부의 bark 원본 함수 포인터)        |
|  __self__ : 0x500 (방금 점을 찍고 접근한 my_dog 인스턴스 포인터)  |
+-----------------------------------------------------------------+

# 증명: 정말로 새 객체가 찍혀 나오는가?

두 번 점을 찍어 변수에 담고 is 연산자로 비교해보면 완벽하게 입증됩니다:

python 
m1 = my_dog.bark
m2 = my_dog.bark

print(m1 is m2)  # False! (서로 다른 독립된 힙 메모리 주소에 생성된 객체)
print(m1 == m2)  # True!  (안에 쥐고 있는 __func__와 __self__가 같으므로 동등함)

이 래퍼 객체는 스스로 실행되는 함수가 아니라, “나중에 괄호 ()를 붙여 부르면 내가 쥐고 있는 __self__를 첫 번째 인자로 밀어 넣어서 __func__를 실행해주마” 하고 기다리는 포장지 객체입니다.

# 5. self 매개변수 화살표의 올바른 종착점

초보자뿐 아니라 숙련된 개발자들도 종종 다음과 같은 오개념을 품습니다:

"인스턴스 입장에서 self는 클래스에 정의된 함수를 가리키는 화살표인가요?"

정반대입니다!

self는 함수를 가리키는 것이 아니라, 함수가 실행될 때 그 함수를 호출한 대상 인스턴스 자신을 가리키는 화살표입니다.

평문 
[ my_dog.bark() 실행 시 CPython 스택 프레임 ]

  Dog.bark 실행 프레임 내부:
    매개변수 self ────────(C 포인터)────────▶ [ 힙의 my_dog 인스턴스 본체 ]
                                                     │
                                                     │ (ob_type 포인터)
                                                     ▼
                                            [ 힙의 Dog 클래스 객체 ]

파이썬에서 메서드 호출은 사실 문법적 설탕(Syntactic Sugar)에 불과합니다. 아래의 두 코드는 기계적으로 100% 동일하게 동작합니다:

python 
# 우리가 작성하는 객체지향 표기법
my_dog.bark("멍멍")

# CPython이 내부적으로 변환하여 실행하는 실제 메커니즘
Dog.bark(my_dog, "멍멍")

Java나 C++은 컴파일러가 this 포인터를 암묵적으로 레지스터에 숨겨 넘겨주지만, 파이썬은 “명시적인 것이 암묵적인 것보다 낫다(Explicit is better than implicit)”는 철학에 따라 첫 번째 매개변수 자리에 self를 명시적으로 선언하도록 설계된 것입니다.

# 6. 파이썬 세계의 전모: 거대한 객체 그래프 (Object Graph)

파이썬 프로그램이 실행되는 런타임 공간은 수많은 노드(객체)들과 이들을 잇는 방향성 간선(참조 포인터)들로 가득 찬 거대한 하나의 은하계(Object Graph)입니다.

평문 
[ Global Namespace (전역 사전) ]
  ├─ "math"       ───▶ [ 모듈 객체 (math) ]
  │                       └─ "sqrt" ───▶ [ 내장 함수 객체 (sqrt) ]
  │
  ├─ "Dog"        ───▶ [ 클래스 타입 객체 (Dog) ]
  │                       └─ "bark" ───▶ [ 함수 객체 (bark) ]
  │
  ├─ "my_dog"     ───▶ [ 인스턴스 객체 (my_dog) ]
  │                       ├─ "ob_type" ───▶ (Dog 클래스 가리킴)
  │                       └─ "name"    ───▶ [ 문자열 객체 ('바둑이') ]
  │
  └─ "numbers"    ───▶ [ 리스트 객체 ]
                          ├─ [0] ───▶ [ 정수 10000 객체 ]
                          └─ [1] ───▶ [ 정수 20000 객체 ]

파이썬에서 가비지 컬렉터(Garbage Collector)는 이 거대한 그래프에서 어떤 이름표나 포인터로도 도달할 수 없는(Unreachable) 고립된 객체 섬들을 찾아내어 메모리에서 회수하는 청소기 역할을 수행합니다.

# 🎯 멘탈 모델 자가 점검 4문 4답

  1. “변수는 무엇인가?”
    👉 값을 담는 상자가 아니라, 힙에 뜬 객체의 주소를 가리키는 이름표(Label) 포인터입니다.
  2. “인스턴스와 클래스의 차이는?”
    👉 인스턴스는 오직 고유 상태값만 쥐고 있는 데이터 창고이며, 클래스는 공용 함수 바이트코드를 보관하는 공구함입니다.
  3. “Bound Method는 언제 만들어지는가?”
    👉 인스턴스 뒤에 점(.)을 찍어 메서드를 참조하는 바로 그 순간, 디스크립터 프로토콜에 의해 힙에 새로운 래퍼 객체가 즉석 생성됩니다.
  4. “self는 어디를 가리키는가?”
    👉 함수 코드를 가리키는 것이 아니라, 함수가 실행될 때 전달받은 대상 인스턴스 본체(my_dog)를 가리킵니다.
