코딩 에이전트 직접 만들기, 300줄 루프를 6단계로 따라가기

Geoffrey Huntley의 무료 워크숍 「how to build a coding agent」와 Go 실습 저장소 심층 학습

#AI #코딩에이전트 #Go #Anthropic #워크숍 #루프엔지니어링

코딩 에이전트는 어렵지 않다. LLM 토큰과 함께 루프를 도는 300줄 코드다. Geoffrey Huntley는 2025년 8월 24일 공개한 워크숍 글에서 Cursor, Windsurf, Claude Code, GitHub Copilot, Amp가 모두 "LLM 토큰과 함께 루프를 도는 적은 줄 수의 코드"라고 말한다. 무거운 일은 모델이 다 한다. 그래서 직접 만들어 보면 AI의 소비자에서 생산자로 바뀐다는 것이 워크숍의 주장이다.

# 핵심 요약

  1. 루프가 전부다: 사용자 입력을 대화에 쌓고, 모델에 보내고, 모델이 도구를 요청하면 실행해서 결과를 다시 보낸다. 도구 요청이 없을 때까지 반복한다.
  2. 도구는 설명이 붙은 함수다: 이름, 설명, 입력 스키마, 함수 네 가지로 정의한다. 헌틀리는 이를 "LLM이 그 함수를 부르도록 떠미는 광고판이 달린 함수"라고 부른다.
  3. 다섯 가지 기본 도구: 파일 읽기, 목록 보기, bash, 편집, 코드 검색. 저장소는 이를 6개의 Go 파일로 한 단계씩 늘려 간다.
  4. 맥락 창은 작다: 한 맥락 창은 한 가지 일에만 쓰고, 도구와 MCP를 과하게 넣지 않는다.

읽는 법. 1절에서 워크숍의 개념(에이전트형 모델, 맥락 창)을 보고, 2절에서 이벤트 루프 그림을 익힌다. 3절부터 8절까지가 6단계 실습이며, 단계마다 "이전 단계에서 바뀐 것"과 저장소 코드 발췌를 붙였다. 코드는 저장소(커밋 fa3dd49, 2026년 10월 10일)에서 그대로 옮겼다. 9절은 6단계 요약표, 10절은 실습 준비, 11절은 원문과 저장소가 어긋나는 곳, 12절은 시작 순서다. 슬라이드는 블로그 글에 실린 워크숍 슬라이드이며 누르면 크게 보인다. "우리 메모" 라고 적은 부분은 이 페이지의 분석이고 원문 내용이 아니다.

# 1. 먼저 알아 둘 개념

# 1.1 모든 LLM이 에이전트형은 아니다

헌틀리는 모델의 행동을 네 사분면에 놓는다. 높은 안전성, 낮은 안전성, 오라클, 에이전트형이다. 한 모델이 둘 이상을 겸하지는 않는다고 그는 말한다.

사분면 원문의 설명
높은 안전성 "윤리 정렬"을 원하면 Anthropic이나 OpenAI
낮은 안전성 보안 연구에는 Grok
오라클 에이전트형의 정반대. 요약이나 깊은 사고가 필요한 일
에이전트형 도구 호출을 좇는다. 오래 고민하기보다 행동 쪽으로 기운다
  • 에이전트형(agentic): 보상 함수로 도구 호출을 하도록 훈련된 모델. 헌틀리는 Claude Sonnet을 "도구 호출만 좇는 작은 뇌의 기계 다람쥐"라고 부른다.
  • 에이전트를 만들 때 첫 단계는 에이전트형이 강한 모델을 고르는 것이고, 원문 시점에는 Claude Sonnet이나 Kimi K2였다.
  • 더 깊은 추론이 필요하면 다른 LLM을 에이전트형 LLM의 도구로 연결하면 된다. Amp의 "Oracle"은 GPT를 Claude Sonnet이 부를 수 있는 도구로 등록한 것이라고 한다.

# 1.2 맥락 창은 한 가지 일에만

  • 맥락 창(context window): 모델이 한 번에 볼 수 있는 입력의 최대 크기(토큰 수).
  • 원문은 맥락 창을 "Commodore 64"처럼, 메모리가 적은 컴퓨터로 대하라고 한다. 많이 할당할수록 결과와 성능이 나빠진다.
  • 백엔드 API 작업을 하던 세션에서 미어캣 조사를 하고, 이어서 웹사이트를 고치라고 하면 웹사이트에 API나 미어캣 이야기가 섞여도 놀랄 일이 아니다.
  • Sonnet의 광고된 맥락 창은 200k 토큰이지만 시스템 프롬프트와 하네스 몫을 빼면 약 176k가 쓸 수 있는 양이라고 한다. 원문은 워크숍 이후 Sonnet 맥락 창이 1m으로 늘었다고 덧붙인다.
  • MCP 도구에만 76k 토큰을 더 할당하면 쓸 수 있는 양이 100k로 준다. "적을수록 좋다"가 원문의 결론이다.

# 2. 이벤트 루프 한 장으로 보기

원문은 에이전트의 핵심을 의사 코드 8줄로 보여 준다. 도구가 없을 때는 "입력 받기, 모델에 보내기, 출력"뿐이고, 도구가 생기면 5~7번 줄이 더해진다. 모델이 도구를 원하면 실행하고, 그 결과를 다시 모델에 보낸다.

저장소 README는 같은 루프를 이렇게 적는다.

  1. 입력을 기다린다.
  2. Claude에 보낸다.
  3. Claude가 바로 답하거나 도구 사용을 요청한다.
  4. 에이전트가 도구를 실행한다(예: 파일 읽기).
  5. 결과를 Claude에 돌려보낸다.
  6. Claude가 최종 답을 준다.

아래 그림은 README의 이벤트 루프 다이어그램을 이 페이지에서 다시 그린 것이다.

  • 왼쪽 세로줄이 바깥 루프(사용자와 대화)이고, 오른쪽 고리가 안쪽 루프(도구 실행)다. 안쪽 루프는 모델이 더는 도구를 요청하지 않을 때 끝난다.
  • 그림에서 "텍스트 출력"으로 가는 화살표는 단순화한 것이다. 실제 코드는 응답의 텍스트 블록을 안쪽 루프 안에서 바로 출력한다(4절 코드 참고). 우리 메모.

# 3. 1단계 chat.go: 도구 없는 대화

하는 일: Claude와 대화만 한다. 146줄이다.

핵심: 대화 기록 conversation을 슬라이스로 들고 있으면서 사용자 메시지와 모델 응답을 계속 덧붙인다. 모델에는 매번 전체 기록을 보낸다.

go 
userMessage := anthropic.NewUserMessage(anthropic.NewTextBlock(userInput))
conversation = append(conversation, userMessage)
go 
message, err := a.client.Messages.New(ctx, anthropic.MessageNewParams{
	Model:     anthropic.ModelClaudeOpus4_6,
	MaxTokens: int64(1024),
	Messages:  conversation,
})
  • 모델은 anthropic.ModelClaudeOpus4_6, 응답 최대 길이는 MaxTokens: int64(1024)로 고정돼 있다. 여섯 파일 모두 같다.
  • 워크숍 글은 이 단계에서 prompts/00-weather.md로 "날씨를 물으면 get_weather(<location_name>)로 답하라"고 지시해 본다. 모델이 실제로 get_weather(Melbourne, Australia)라고 답하는 것을 보여 주며, 도구 호출이 무엇인지 감을 잡게 한다. 이때는 실제로 실행되는 함수가 없다.

# 4. 2단계 read.go: 첫 도구와 안쪽 루프

하는 일: Claude가 파일을 읽는다.

chat.go에서 바뀐 것 (우리 메모: diff chat.go read.go로 확인)

  1. ToolDefinition 구조체와 GenerateSchema 함수가 생긴다.
  2. 에이전트가 도구 목록을 받는다: tools := []ToolDefinition{ReadFileDefinition}.
  3. API 호출에 Tools: anthropicTools가 붙는다.
  4. 응답 처리가 안쪽 루프로 바뀐다. 이 부분이 에이전트의 심장이다.

도구 정의의 틀이다.

go 
type ToolDefinition struct {
	Name        string                         `json:"name"`
	Description string                         `json:"description"`
	InputSchema anthropic.ToolInputSchemaParam `json:"input_schema"`
	Function    func(input json.RawMessage) (string, error)
}

첫 도구 read_file이다. 입력은 경로 하나이고, 함수는 os.ReadFile로 내용을 돌려준다.

go 
var ReadFileDefinition = ToolDefinition{
	Name:        "read_file",
	Description: "Read the contents of a given relative file path. Use this when you want to see what's inside a file. Do not use this with directory names.",
	InputSchema: ReadFileInputSchema,
	Function:    ReadFile,
}

type ReadFileInput struct {
	Path string `json:"path" jsonschema_description:"The relative path of a file in the working directory."`
}

var ReadFileInputSchema = GenerateSchema[ReadFileInput]()

입력 스키마는 Go 구조체에서 자동으로 만든다.

go 
func GenerateSchema[T any]() anthropic.ToolInputSchemaParam {
	reflector := jsonschema.Reflector{
		AllowAdditionalProperties: false,
		DoNotReference:            true,
	}
	var v T

	schema := reflector.Reflect(v)

	return anthropic.ToolInputSchemaParam{
		Properties: schema.Properties,
	}
}

안쪽 루프의 뼈대다. 응답에 tool_use 블록이 있으면 이름이 같은 도구를 찾아 실행하고, 결과를 NewToolResultBlock으로 모은다. 도구 사용이 없으면 루프를 빠져나간다.

go 
case "tool_use":
	hasToolUse = true
	toolUse := content.AsToolUse()
go 
toolResult, toolError = tool.Function(toolUse.Input)
go 
// If there were no tool uses, we're done
if !hasToolUse {
	break
}

// Send all tool results back and get Claude's response
if a.verbose {
	log.Printf("Sending %d tool results back to Claude", len(toolResults))
}
toolResultMessage := anthropic.NewUserMessage(toolResults...)
conversation = append(conversation, toolResultMessage)

// Get Claude's response after tool execution
message, err = a.runInference(ctx, conversation)
if err != nil {
	if a.verbose {
		log.Printf("Error during followup inference: %v", err)
	}
	return err
}
conversation = append(conversation, message.ToParam())
  • 오류가 나도 루프는 멈추지 않는다. 오류 메시지를 NewToolResultBlock(toolUse.ID, toolError.Error(), true)로 모델에 돌려준다. 모델이 오류를 보고 다시 시도할 수 있게 하는 방식이다. 우리 메모.
  • 실습 프롬프트(prompts/01-read_file.md): "Claude, mate. What's the answer to this riddle in riddle.txt?" 원문 실행 기록에서 Claude는 read_file({"path":"riddle.txt"})를 부르고 답을 "a horse"로 낸다.

# 5. 3단계 list_files.go: 목록 보기와 도구 연쇄

하는 일: 디렉터리 안의 파일과 폴더를 나열한다.

read.go에서 바뀐 것: 도구 목록에 ListFilesDefinition이 더해진다. 루프는 그대로다. 도구를 늘리는 데 루프를 고칠 필요가 없다는 점이 이 구조의 장점이다. 우리 메모.

go 
var ListFilesDefinition = ToolDefinition{
	Name:        "list_files",
	Description: "List files and directories at a given path. If no path is provided, lists files in the current directory.",
	InputSchema: ListFilesInputSchema,
	Function:    ListFiles,
}
  • 함수는 filepath.Walk로 하위까지 훑고, 폴더에는 끝에 /를 붙이며, .devenv 폴더는 건너뛴다. 결과는 JSON 배열 문자열이다.
  • 실습 프롬프트(prompts/02-list_files.md): 파일 목록과 riddle.txt 내용을 함께 묻는다. 원문 기록에서 Claude는 list_files({}) 다음에 read_file을 이어 부른다. 원문은 이를 "한 프롬프트에서 함수들이 호출되고 연쇄된다"고 설명한다.

# 6. 4단계 bash_tool.go: 셸 명령 실행

하는 일: LLM이 컴퓨터에서 명령을 실행한다.

list_files.go에서 바뀐 것: BashDefinition이 더해진다.

go 
var BashDefinition = ToolDefinition{
	Name:        "bash",
	Description: "Execute a bash command and return its output. Use this to run shell commands.",
	InputSchema: BashInputSchema,
	Function:    Bash,
}
go 
func Bash(input json.RawMessage) (string, error) {
	bashInput := BashInput{}
	err := json.Unmarshal(input, &bashInput)
	if err != nil {
		return "", err
	}

	log.Printf("Executing bash command: %s", bashInput.Command)
	cmd := exec.Command("bash", "-c", bashInput.Command)
	output, err := cmd.CombinedOutput()
	if err != nil {
		log.Printf("Bash command failed: %s, error: %v", bashInput.Command, err)
		return fmt.Sprintf("Command failed with error: %s\nOutput: %s", err.Error(), string(output)), nil
	}

	log.Printf("Bash command succeeded: %s (output: %d bytes)", bashInput.Command, len(output))
	return strings.TrimSpace(string(output)), nil
}
  • bash -c로 명령을 그대로 실행한다. 명령이 실패해도 Go 오류로 돌려주지 않고, "Command failed with error"로 시작하는 문자열을 정상 결과로 돌려준다. 모델이 실패 출력을 읽게 하려는 설계로 보인다. 우리 메모.
  • README는 이 단계를 "safe terminal commands"를 실행한다고 소개하지만, 코드에는 명령을 거르는 장치가 없다. 직접 돌릴 때는 버려도 되는 폴더나 격리된 환경에서 실행하는 편이 안전하다. 우리 메모.
  • 실습 프롬프트(prompts/03-bash_tool.md): 실행 중인 프로세스 요약. 원문 기록에서 Claude는 bash({"command":"ps aux"})를 부른다.

# 7. 5단계 edit_tool.go: 파일 편집, 이제 코딩 에이전트

하는 일: 파일을 만들고 고친다.

bash_tool.go에서 바뀐 것: EditFileDefinition이 더해진다. 편집 방식은 "문자열 바꾸기"다.

go 
var EditFileDefinition = ToolDefinition{
	Name: "edit_file",
	Description: `Make edits to a text file.

Replaces 'old_str' with 'new_str' in the given file. 'old_str' and 'new_str' MUST be different from each other.

If the file specified with path doesn't exist, it will be created.
`,
	InputSchema: EditFileInputSchema,
	Function:    EditFile,
}

EditFile 함수의 규칙은 다음과 같다(코드 기준).

경우 동작
경로가 비었거나 old_str과 new_str이 같음 오류 "invalid input parameters"
파일이 없고 old_str이 빈 문자열 새 파일 생성(필요하면 폴더도 생성)
old_str이 빈 문자열, 파일은 있음 파일 끝에 덧붙이기
old_str이 0번 나옴 오류 "old_str not found in file"
old_str이 2번 이상 나옴 오류, "must be unique"
정확히 1번 그 한 곳만 바꾸고 "OK" 반환
go 
	// Count occurrences first to ensure we have exactly one match
	count := strings.Count(oldContent, editFileInput.OldStr)
	if count == 0 {
		log.Printf("EditFile failed: old_str not found in file %s", editFileInput.Path)
		return "", fmt.Errorf("old_str not found in file")
	}
	if count > 1 {
		log.Printf("EditFile failed: old_str found %d times in file %s, must be unique", count, editFileInput.Path)
		return "", fmt.Errorf("old_str found %d times in file, must be unique", count)
	}

	newContent = strings.Replace(oldContent, editFileInput.OldStr, editFileInput.NewStr, 1)
}
  • 실습 프롬프트(prompts/04-edit_tool.md): Node.js로 실행할 fizzbuzz.js를 만들고 실행하라는 요청. 원문 기록에서 Claude는 edit_file로 파일을 만들고, read_file로 확인한 뒤, bash로 node fizzbuzz.js를 실행해 1부터 20까지의 결과를 확인한다. 원문은 여기서 "이제 코딩 에이전트가 생겼다"고 말한다.

# 8. 6단계 code_search_tool.go: ripgrep 검색

하는 일: 패턴으로 코드베이스를 검색한다.

원문은 "소스 코드 색인에 마법이나 지능은 없다"며, 지금 나와 있는 거의 모든 코딩 도구가 오픈소스 ripgrep 바이너리를 쓴다고 말한다.

  • ripgrep(rg): 정규식으로 폴더 전체를 빠르게 검색하는 명령줄 도구.
go 
var CodeSearchDefinition = ToolDefinition{
	Name: "code_search",
	Description: `Search for code patterns using ripgrep (rg).

Use this to find code patterns, function definitions, variable usage, or any text in the codebase.
You can search by pattern, file type, or directory.`,
	InputSchema: CodeSearchInputSchema,
	Function:    CodeSearch,
}
go 
type CodeSearchInput struct {
	Pattern   string `json:"pattern" jsonschema_description:"The search pattern or regex to look for"`
	Path      string `json:"path,omitempty" jsonschema_description:"Optional path to search in (file or directory)"`
	FileType  string `json:"file_type,omitempty" jsonschema_description:"Optional file extension to limit search to (e.g., 'go', 'js', 'py')"`
	CaseSensitive bool `json:"case_sensitive,omitempty" jsonschema_description:"Whether the search should be case sensitive (default: false)"`
}
  • 함수는 rg --line-number --with-filename --color=never에 대소문자 무시(기본), 파일 형식, 경로를 붙여 실행한다. 일치가 없을 때 rg가 내는 종료 코드 1은 오류가 아니라 "No matches found"로 바꾼다. 결과가 50줄을 넘으면 앞 50줄만 돌려준다.
  • 주의: 이 파일의 도구 목록은 다음과 같다. edit_file이 빠져 있다. README 다이어그램도 마지막 단계를 read_file, list_files, bash, code_search로 그린다. 5단계에서 만든 편집 기능과 검색을 함께 쓰려면 직접 합쳐야 한다. 우리 메모.
go 
tools := []ToolDefinition{ReadFileDefinition, ListFilesDefinition, BashDefinition, CodeSearchDefinition}
  • 원문 실습 기록에서 Claude는 code_search({"pattern":"riddle"}), list_files({}), read_file을 차례로 불러 riddle.txt를 찾아낸다.

# 10.3 비용 (우리 메모)

원문과 README에는 비용 이야기가 없다. 아래는 이 페이지의 판단이다.

  • API는 쓴 토큰만큼 과금된다. 코드는 매 호출마다 대화 전체를 다시 보내므로, 대화가 길어지고 도구 결과(예: ps aux 출력, 원문 기록에서 87,344바이트)가 쌓일수록 한 번의 호출이 비싸진다.
  • 기본 모델은 ModelClaudeOpus4_6이다. 연습할 때는 runInference의 Model: 한 줄을 더 싼 모델로 바꾸면 비용을 줄일 수 있다. 원문은 에이전트용 모델로 Claude Sonnet을 꼽았다.
  • 실습이 끝나면 대화를 새로 시작해 맥락을 비운다(1.2절의 원칙과도 맞다).

# 11. 원문과 저장소가 어긋나는 곳

  • fizzbuzz.js가 없다: README는 "Sample Files (Already Included)"에 fizzbuzz.js를 적고 "Read fizzbuzz.js" 같은 시도를 권하지만, 저장소(커밋 fa3dd49)에는 이 파일이 없다. 원문 실습에서는 5단계에서 에이전트가 직접 만든다. 따라서 2~3단계에서 fizzbuzz.js를 읽으라는 README 제안은 파일을 먼저 만들어야 통한다. 대신 저장소에 있는 riddle.txt를 쓰면 된다.
  • edit_file.go 오타: 원문 블로그는 5단계 실행 명령을 go run edit_file.go로 적지만, 실제 파일은 edit_tool.go다.
  • 6단계에서 edit_file이 빠짐: 8절 참고.
  • AGENT.md와 Makefile: AGENT.md의 명령 목록과 Makefile의 빌드 대상에는 code_search_tool이 없다. AGENT.md에는 저장소에 없는 go run main.go도 적혀 있다.
  • 모델 표기: 원문은 에이전트형 모델로 Claude Sonnet을 권하지만, 현재 저장소 코드는 Opus 4.6을 부른다. 원문 이후 저장소가 바뀐 것으로 보인다(추정).
  • list_files 구현 차이: 3~5단계는 filepath.Walk, 6단계는 find 명령으로 목록을 만든다.
